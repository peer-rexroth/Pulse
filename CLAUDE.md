# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Pulse is a single-file, zero-dependency HTML application — the entire app (HTML, CSS, JavaScript) lives in `pulse.html`. There is no build step and no package manager. It's a local-first programme dashboard, organized into four top-level modes (see "Modes" below): **Planning** (workstreams, scope items, milestones — status board or timeline), **Review** (dated, per-workstream review cycles that require every item to be confirmed before completing), **Dashboard** (a read-only health rollup + attention-needed feed), and **Admin** (the category lookup table that seeds a new item's milestone checklist). It's also an installable PWA (manifest, service worker, icons), and has the same data-durability feature set as this author's other single-file apps (PromptLab, mytasks): JSON export/import, rolling local backups, deletion tombstones with undo, and optional File System Access API file sync — see "Data durability" below.

## Running it

A plain `file://` open of `pulse.html` works fine for quick checks, but PWA install/offline support requires serving it over http — browsers refuse to register a service worker for `file://` pages. `./start-pulse.command` serves the directory on `http://127.0.0.1:8936` and opens it in Chrome/Edge (Safari can't install this kind of PWA on macOS). `./stop-pulse.command` kills the server.

## Tests

There's no lint config, but there is a test suite at `tests/`: extract the inline `<script>` block, mock just enough of the DOM (`document.getElementById` returning cached fake elements with a settable `innerHTML`/`value`, plus `localStorage`, `navigator`, `window`, `location`, `Blob`/`URL` for the export/download path) and `eval()` the real code in a headless JS engine (`osascript -l JavaScript` — JavaScriptCore, no Node install needed). `indexedDB` is deliberately *not* mocked — see "File System Access API sync" below for which functions that rules out testing directly.

Run it with `./tests/run.sh` (optionally `./tests/run.sh someSubstring` to run only tests whose name contains that substring). No install step.

Add a test by dropping a `tests/cases/*.test.js` file with `test('description', function(){ ... })` calls. All app code plus every `tests/cases/*.test.js` file get concatenated and `eval()`'d *together* in one call, which is why a test can read/reassign `workstreams`, `items`, `categories`, `reviewCycles`, `mode`, `view`, `filterWorkstreamId` and the other top-level `let` state directly by bare name, and call any of the app's real functions — they're all sharing the same eval'd lexical scope. `tests/harness.js` calls `resetState()` (glue-defined: `seedDefaults()` + resets the UI-transient module vars + `normalizeData()`) and clears the fake DOM before every test, so tests never see state left over from another test — write fixtures at the top of each test rather than relying on run order.

Test files, by area: `workstreams.test.js`, `items.test.js`, `normalize.test.js`, `views.test.js` (status board/timeline rendering) predate categories/review/dashboard; `categories.test.js` (Admin CRUD, category-driven milestone seeding/reseeding), `review.test.js` (cycle start/confirm/complete/cancel, mid-cycle-add behavior, staleness), `dashboard.test.js` (rollup math, overdue/upcoming feeds), `modes.test.js` (mode switching, body visibility, tab active-state), and `sync.test.js` (tombstones, merge, export/import, backups) cover everything added since.

One mock limitation worth knowing: the fake `<select>`/`<input>` elements don't parse `innerHTML` into `.value` the way a real browser does, so a test that wants to assert "this option got preselected" must check the rendered `innerHTML` string for `selected`/`value="..."` rather than reading `.value` after a `populate*Select()` call — see `tests/cases/items.test.js`'s "preselects the given workstream" test for the pattern. Tests that set form values *before* calling `save*()` set `.value` directly instead, which the mock does support.

## Architecture

The file has three logical sections in order: CSS styles, HTML structure, and a `<script>` block containing all application logic.

### Data model

All state is stored in `localStorage` under the key `"pulse-v1"` and serialised as JSON with this shape:

```json
{
  "programme": { "name": "..." },
  "workstreams": [...],
  "items": [...],
  "categories": [...],
  "reviewCycles": [...],
  "mode": "planning" | "review" | "dashboard" | "admin",
  "view": "status" | "timeline",
  "theme": "light" | "dark",
  "filterWorkstreamId": null | "wsId",
  "deletedWorkstreamIds": [{"id": "...", "deletedAt": 0}],
  "deletedItemIds": [{"id": "...", "deletedAt": 0}]
}
```

A **workstream**:
```js
{ id: String, name: String, color: String, order: Number }  // color is a name key from WS_COLORS
```

An **item** (a scope item — the only top-level item type; see "Milestones" below):
```js
{
  id: String,
  workstreamId: String,
  categoryId: String,  // which Category's milestone template seeded this item — see "Categories (Admin mode)"
  name: String,
  owner: String,
  status: 'not-started' | 'green' | 'amber' | 'red' | 'complete', // computed from milestones if any exist — see "Item status roll-up"
  startDate: String,       // 'YYYY-MM-DD'
  dueDate: String,         // 'YYYY-MM-DD'
  actualDate: String|null, // 'YYYY-MM-DD' — when it was actually finished; manual, never inferred from status
  updatedAt: Number,       // Date.now() — last-write-wins timestamp for merge (see "Data durability")
  milestones: [Milestone],
  itStatus: 'green' | 'amber' | 'red',       // IT readiness tag — see "IT/Business/Budget tags" below
  businessStatus: 'green' | 'amber' | 'red', // Business readiness tag
  budgetStatus: 'green' | 'amber' | 'red'    // Budget/funding status tag
}
```

Workstreams have no `updatedAt` (mirroring mytasks' projects) — see "Merge and last-write-wins" below for what that means for a deleted workstream.

A **milestone** — nested inside its parent item, not a top-level array:
```js
{ id: String, name: String, dueDate: String, actualDate: String|null, status: 'not-started' | 'green' | 'amber' | 'red' | 'complete' }
```

**`actualDate` is deliberately manual, on both items and milestones** — it is never auto-filled when `status` is set to `'complete'`, and setting an `actualDate` never auto-sets `status` either. The two are independent: a PM might record the real finish date before formally marking something Complete (or vice versa, or never at all) — auto-linking them would take that judgment call away. `openItemModal()`/`saveItem()` read/write `#itemActualInput` the same way they do `startDate`/`dueDate`; `renderMilestonesEditor()` gives each milestone row its own actual-date input (`editingMilestones[idx].actualDate`) alongside its due-date input. Both default to `null` (not an empty string) when unset — `saveItem()` coerces the date input's `''` to `null` on save (`document.getElementById('itemActualInput').value || null`, and the same pattern per milestone), so "no actual date yet" is a single consistent falsy value rather than sometimes `''` and sometimes `null` depending on the code path.

Milestones don't have their own `owner`/`startDate` — they're a lightweight checklist against a single date, deliberately kept smaller than the item shape rather than reusing it. An item's own `status` **is** computed from its milestones whenever it has any — see "Item status roll-up" below.

A **category** (Admin mode's lookup table — see "Categories (Admin mode)" below):
```js
{ id: String, name: String, milestones: [String], order: Number }  // milestones here are plain name strings, a template — not the {id,dueDate,status} shape an item's own milestones have
```

A **review cycle** (see "Review mode" below):
```js
{
  id: String, workstreamId: String,
  startedAt: Number,              // Date.now()
  completedAt: Number | null,
  cancelledAt: Number | null,
  confirmations: [{ itemId: String, confirmedAt: Number }]
}
```
Review cycles are append-only history — nothing ever deletes one, `completedAt`/`cancelledAt` just get set once. Exactly one of `completedAt`/`cancelledAt` is non-null once a cycle is finished; both `null` means it's still active.

### Modes

`mode` (`'planning' | 'review' | 'dashboard' | 'admin'`, `MODES` array is the source of truth for the valid values) is the top-level navigation axis. Planning/Review/Dashboard are switched via the topbar's `.view-tabs` mode pill (`#tabPlanning`/`#tabReview`/`#tabDashboard`) and `setMode(m)`; Admin is deliberately **not** in that pill — it's a plain `.btn` (`#tabAdmin`) sitting in the topbar's right-hand cluster next to the Data dropdown, because it isn't workstream-scoped the way the other three are (see "The shared workstream selector" below) and grouping it with them would imply it was.

Planning, Review, and Dashboard share one container, `#scopedBody` (`.body-row` — sidebar + `#main`); Admin gets its own `#adminBody` (`.main` directly, no sidebar, since categories aren't workstream-scoped). `render()` is the single top-level dispatcher: it shows `#scopedBody` for every mode except `admin` (which shows `#adminBody` instead), toggles `#planningToolbar` (the Status/Timeline sub-tabs) visible only for `mode === 'planning'`, always calls `renderSidebar()` (the sidebar is shared, so it stays current regardless of which of the three modes is active), and then calls exactly one of `renderMain()` (planning), `renderReview()`, `renderDashboard()`, `renderAdmin()` — all four write into the same `#main` element except `renderAdmin()`, which writes into `#adminBody`.

**Every mutation should call the top-level `render()`**, not a mode-specific render function, *unless* the call site is only ever reachable while that mode is already showing (e.g. `cycleMilestoneStatus()` calls the narrower `renderMain()`, safe because a milestone status badge only exists inside Planning's status board — nothing outside Planning can trigger it). `saveItem()`/`deleteItem()` in particular call the general `render()` because `openItemModal()` is reachable from both Planning (its own rows) and Review (a checklist row's status badge) — a narrower call would leave whichever mode *isn't* Planning showing stale content after a save made from Review mode.

### The shared workstream selector

`filterWorkstreamId` is no longer Planning-only — it's the single selector Planning (status board/timeline), Review (which workstream's cycle to show), and Dashboard (scopes the whole rollup) all read from, set from the one shared sidebar (`renderSidebar()`/`#wsList`, `setFilterWorkstream(id)`) that's now visible in all three modes rather than duplicated per-mode. `null` means "All workstreams" for Planning/Dashboard; Review has no meaning for "all" (a review cycle is one workstream at a time — see "Review mode" below), so it's gated at three layers:

1. **Entry**: `setMode('review')` refuses (toast, no mode change) if `filterWorkstreamId` is falsy.
2. **Mid-session**: `setFilterWorkstream(id)` — if `mode === 'review'` and the newly-picked `id` is `null` ("All workstreams"), it falls back to `mode = 'planning'` immediately, since Review would otherwise be left showing nothing sensible.
3. **Load-time backstop**: `normalizeData()` does the same check after its own `filterWorkstreamId` validity pass, for data arriving with `mode: 'review'` and no workstream selected (an old save, a merged-in file, a hand-edited import).

The topbar's Review tab also reflects this visually — `render()` toggles a `.disabled` class on `#tabReview` whenever `filterWorkstreamId` is falsy — but the three guards above are what actually enforce it; the CSS class is just the affordance, not the mechanism (the tab's `onclick` still fires `setMode('review')`, which still refuses).

Planning additionally keeps its own Status/Timeline sub-toggle (`#tabStatus`/`#tabTimeline`, `setView()`), rendered as `#planningToolbar` above `#main`.

### RAG status

`STATUSES` (top of the `<script>` block) is the single source of truth for the five status values and their labels: Not Started, On Track (green), At Risk (amber), Off Track (red), Complete (blue). Status drives an item's color everywhere it appears — the status badge in the status board, and the bar/diamond fill in the timeline. Workstream color (`WS_COLORS`, a separate 8-hue palette) is used only for the sidebar dot, the status-board section header tint, and the timeline lane label dot — it never colors an item, since status is the signal a programme dashboard is meant to surface at a glance.

### Rendering pattern

Direct DOM re-renders (no virtual DOM or framework). `render()` does a full re-render (topbar bits + sidebar + main); `renderSidebar()` and `renderMain()` handle their halves independently. Every state mutation calls `save()` then one of these. `renderMain()` dispatches to `renderStatusView()` or `renderTimelineView()` based on the `view` flag — if you add a mutation that should be reflected live, make sure it calls `render()` (or at least the render function covering whatever it changed), not a narrower one that happens to work for today's call site.

### Status board (`renderStatusView`)

One `.ws-section` per visible workstream (filtered by `filterWorkstreamId` via `visibleWorkstreams()`), each showing a RAG count summary (`STATUSES` filtered to non-zero counts) and its items sorted by `dueDate` ascending. `itemRowHtml(it)` renders the item's own row plus, if `expandedItemIds` (a module-level `Set`, UI-only — not persisted, resets on reload) has that item's id, a small `milestoneHeaderHtml()` column-label row and its nested milestone rows (`milestoneRowsHtml`, sorted by `dueDate`) immediately after. Clicking a milestone's own status badge calls `cycleMilestoneStatus(itemId, milestoneId)`, which steps through `STATUSES` in array order and wraps — a quicker way to update a milestone's RAG than opening the item modal (and, per "Item status roll-up" below, recomputes the parent item's status too).

**Plan-date ranges always show the year** (`fmtDateY`, distinct from the plain `fmtDate` used for other, single-date, same-year-implied contexts like backup timestamps and review-cycle start dates) — a Start/Due range legitimately spans years (e.g. a scope item starting one calendar year and due the next), and a bare "Jul 26 → Jan 1" reads as backwards or same-year when it isn't. Used for the item row's computed range, the item modal's computed-range badge, and the review-mode item row — anywhere a Start→Due *range* is rendered as text.

**There is deliberately no page-wide column header.** An earlier version added one sticky `.item-row-header` above all `.ws-section`s, labeling all the shared columns once for the whole page — this got removed because it implied those labels applied uniformly to milestone rows too, when a milestone only ever populates a handful of them (Milestone/Due/Actual/Status). `milestoneHeaderHtml()` instead renders a small `.milestone-header` scoped to *one* expanded item, directly above that item's own milestone rows — appearing and disappearing with the same chevron toggle that shows/hides the milestones themselves, so the labels are only ever visible attached to the specific list they describe.

**Column layout is a real CSS grid, not flexbox** — `.item-row`, `.milestone-header`, and `.milestone-sub-row` all share one `grid-template-columns` value, `--item-grid-cols` (a `:root` custom property, currently 11 columns: Chevron, Name, Milestones-badge, Owner, Plan-dates, Actual-placeholder (always blank on both row types), a second always-blank spacer, Milestone-Due, Tags/Milestone-Actual (item-only Tags on the item's own row, the milestone's own Actual-date input on a milestone row), Status, Actions), so a milestone's Due/Actual/Status line up directly under its parent item's columns and `milestoneHeaderHtml()`'s labels line up over both. **This means every cell in every row must be a real element, even when empty** — an omitted element (the old code used to render the milestone-count badge as a plain empty string `''` when an item had zero milestones) collapses that grid column entirely for that row, shifting every subsequent cell left and breaking alignment with rows that do have content there. `itemRowHtml()`'s `milestoneBadge` and `milestoneRowsHtml()`'s several deliberately-empty `<span></span>` placeholders (for the columns a milestone row has nothing to put in) exist specifically to hold their column open — `tests/cases/views.test.js`'s "still renders the milestone-count-badge element (empty)" test guards this exact regression. `milestoneRowsHtml()` also reuses the `.item-chevron` class (holding a small diamond icon instead of a chevron) for its first cell, and explicitly spans its Name cell across the Name/Milestones/Owner/Plan-dates columns (`grid-column: 2 / 6`) since a milestone only ever has a name to put in that whole span and a single column's width was truncating longer milestone names. The one exception to "every cell must be a real element" is the "No items yet" placeholder row, which overrides `grid-template-columns:1fr` inline to span the full width as a single cell rather than trying to fill every column with one string.

**There is no Notes field** — items used to have a free-text `notes` field shown in its own row column, removed entirely (data model, item modal, row column) since it wasn't earning its column's width. If it comes back, it should be a deliberate re-add, not a resurrected dead column.

**`.ws-section` never clips its own content (`overflow: hidden` was removed from it)** — the rounded-card look comes from rounding `.ws-section-header`'s top corners and `.ws-section-add`'s bottom corners directly, not from clipping the section box. A row wider than the section (more columns than fit at the current window width) stays reachable via `.main`'s own `overflow: auto` instead of being silently cut off — this was a real bug once: the Due/Actual columns added for milestones pushed Status/Actions past the section's clipped edge with no way to reach them. Two of the 11 columns (Actual-placeholder and the second spacer) are deliberately kept narrow rather than removed outright, specifically to keep the row's total width comfortably under typical window widths so this scroll fallback rarely has to engage in practice.

**Dates are editable directly on the row, not only via the item modal — with one deliberate exception.** An item's own Plan dates (`.item-dates-inline` — Start/Due as two `<input type="date">` with a `→` between them, shown only when it has zero milestones — see "Item plan date range roll-up" below) and each milestone sub-row's Due/Actual dates render real `<input type="date">` elements (`.inline-date-input`, styled borderless/transparent until hovered or focused so they read as plain text at rest) rather than formatted text. Their `onchange` calls `updateItemDateField(itemId, field, value)` / `updateMilestoneDateField(itemId, milestoneId, field, value)`, which write straight into the matching `items`/`milestones` entry and `save(); renderMain()` — no modal round-trip needed for a quick date correction. Neither update function touches `status` — date edits are orthogonal to the milestone-status roll-up. An empty actual date stays empty (no inference/backfill) — `updateMilestoneDateField`'s `onchange` passes `this.value || null`, so clearing the native date picker writes `null` rather than today's date or the due date. Milestone actual-date inputs (`.milestone-sub-actual-inline`) show only the plain `<input type="date">`, no icon — an earlier checkmark icon was removed as purely decorative once the item's own actual-date input (see below) had already been dropped from the row, leaving it inconsistent to keep on milestones alone.

**An item's own `actualDate` is intentionally not shown or editable on the row at all** — only in the item modal. `itemRowHtml()`'s `actualDateHtml` is a plain empty `<span></span>` (a placeholder, not an omitted element — the "Actual" grid column is still real and meaningful for the milestone rows below it, just never populated by the item's own row). This was a deliberate simplification after the row briefly showed it as an always-present inline input (mirroring the milestone rows) — the item's own actual-completion-date is enough of an edge-case field, relative to the far-more-common per-milestone actual dates, that it didn't earn a permanent slot in the compact row view.

### IT/Business/Budget tags

Three item-level-only RAG flags — `itStatus`/`businessStatus`/`budgetStatus`, each one of `RAG3` (`['green','amber','red']` — no `not-started`/`complete` concept, unlike the main status). Rendered as icon-only badges (`fa-laptop-code`/`fa-briefcase`/`fa-euro-sign`, colored by the same `--stat-*` variables as the main status badge) in the item row's Tags column; clicking one calls `cycleItemAttr(itemId, field)`, which steps through `RAG3` and wraps — the same pattern as `cycleMilestoneStatus()` but scoped to a plain 3-value cycle instead of the full `STATUSES` list. These are item-only: `milestoneRowsHtml()` never renders them, and `ITEM_TAG_FIELDS` (top of the `<script>` block) is the single list normalizeData() walks to backfill any missing/invalid value back to `'green'`. A brand-new item gets its defaults at creation in `saveItem()`'s `else` branch (not as part of the shared `data` object also used for edits) specifically so re-saving an *existing* item through the modal — which never edits these fields — can't reset them back to green.

### Timeline (`renderTimelineView`)

One swimlane (`.lane`) per visible workstream, one `.lane-track` per item (not one per item+milestone — a milestone renders inside its parent item's track, not its own). The date axis is computed from the actual data: `minD`/`maxD` span the earliest `startDate`/`dueDate` and latest `dueDate` — including every nested milestone's `dueDate` — among *currently visible* items (10 days of padding each side), or the current-plus-next month if there are no items yet. `PX_PER_DAY` (26) is the single scale constant; `dayOffset(iso)` converts a date to a left-position in pixels relative to `minD`. An item renders as `.tl-bar` (positioned `left`/`width` from `startDate`→`dueDate`, minimum 18px width); each of its milestones renders as a `.tl-milestone` diamond (a 45°-rotated square, positioned at its own `dueDate`) painted into the *same* track, after the bar in markup so it stacks visually on top with no explicit `z-index` needed beyond what's already on `.tl-milestone`. Since the standard milestone set defaults every date to the item's due date, a freshly-created item's six diamonds start stacked at the same x position on the bar's right edge until dates are spread out in the item modal. A `.today-line` marks the current date across every lane. Month header segments (`months` array) are computed by walking `minD`→`maxD` one calendar month at a time and clipping the first/last segment to the actual data range.

Because the visible date range depends on `visibleWorkstreams()`, switching the sidebar filter to one workstream re-scales the whole timeline to that workstream's own items — this is intentional (a workstream with a tight 2-week range shouldn't be squeezed into a full programme's multi-month span), not a bug.

### Milestone checklist

A new item's milestone checklist is seeded from whichever **Category** is selected in the item modal (see "Categories (Admin mode)" below) — not a single fixed list. `milestonesForCategory(categoryId, dueDate)` builds a fresh `{id, name, dueDate, status}` array from `categoryById(categoryId).milestones` (plain name strings), each dated to the given due date and given its own freshly-generated `id`. `openItemModal(id)` seeds `editingMilestones` — a module-level working copy, not committed to `items` until Save — from `milestonesForCategory()` when creating a new item, or from a deep-ish copy of the existing item's `milestones` when editing one already saved. This is why editing never resets an item back to its category's template: `saveItem()` only ever writes whatever is currently in `editingMilestones`, regardless of how it originally got there.

The Category `<select>`'s `onchange` calls `onItemCategoryChange()`, which re-seeds `editingMilestones` from the newly-picked category — but only `if (!editingItemId)`. Switching category while *creating* an item is expected to reload the checklist to match (you haven't customized anything yet); switching it while *editing* an already-saved item must never silently discard whatever checklist customization is already in `editingMilestones` — `tests/cases/categories.test.js`'s "does nothing while editing an existing item" test guards this exact distinction. `DEFAULT_CATEGORY_MILESTONES` (top of the `<script>` block) is *not* a live default any more — it's only read once, by `normalizeData()`/`seedDefaults()`, to seed the one "Development" category a fresh install (or a pre-categories save) starts with.

`renderMilestonesEditor()` redraws the modal's milestone rows from `editingMilestones`; each row's `name`/`dueDate`/`status` field writes straight back into `editingMilestones[idx]` via inline `oninput`/`onchange` (no re-render on keystroke, so inputs never lose focus mid-edit) — `saveItem()` reads the array directly rather than re-scraping the DOM. `addMilestoneRow()`/`removeMilestoneRow(idx)` are the only two mutations that re-render the editor, since those are structural (row count changes, so every subsequent row's index shifts). None of this touches `items` until Save is clicked — Cancel (or closing the modal) just discards `editingMilestones`, which `closeItemModal()` also resets to `[]` for hygiene.

### Item status roll-up

An item's `status` is **computed, not hand-set, whenever it has at least one milestone** — `computedStatusFromMilestones(milestones)` picks whichever milestone ranks worst by `STATUS_SEVERITY` (`{red:0, amber:1, green:2, 'not-started':3, complete:4}`, lower = worse/weaker) and that becomes the item's status. This is a deliberate reversal of an earlier design (previously documented here as "no roll-up, status is always manual") — the product call was that a checklist item at Red should always be visible at the parent level, not silently masked by a manual status someone forgot to update.

The severity order is *not* the same as `STATUSES`' display order: `not-started` ranks near the *best* end (better than Green, worse only than Complete) rather than at the start — the reasoning is that "hasn't started yet" needs no attention the way an active Amber/Red does, so it shouldn't drag an otherwise-on-track item's rollup down the way a genuinely active problem should. Only Green/Amber/Red (milestones someone is actively tracking) can make an item look worse than "nothing to report yet."

**An item with zero milestones keeps a manual status** — there's nothing to compute from, so `computedStatusFromMilestones([])` returns `null` and callers fall back to whatever's hand-picked. Three places enforce/apply the rule, all calling the same helper so the logic lives in exactly one spot:
- `saveItem()`: `milestones.length ? computedStatusFromMilestones(milestones) : <Status select's value>`.
- `cycleMilestoneStatus()`: recomputes `it.status` immediately after changing one milestone's status, so the item row's badge is never stale even without reopening the modal.
- `normalizeData()`: recomputes `it.status` for every item with milestones on every load/merge/import — this is what self-heals a manual status saved before this rule existed, or one arriving from an external file that predates/ignores it, and is the actual source of truth the other two are just keeping in sync ahead of the next `normalizeData()` pass.

**The item modal's Status field switches between an editable `<select>` and a read-only computed badge**, live, based on whether the item currently has milestones — never both at once. `updateItemStatusFieldMode()` (name predates the date-range roll-up below, which it now also drives — see there for why it wasn't split into two functions) toggles `#itemStatusSelect`/`#itemStatusComputed`'s `display` and, in the computed case, fills `#itemStatusComputedBadge` from `computedStatusFromMilestones(editingMilestones)` (the in-progress working copy, not yet saved). It's called from `renderMilestonesEditor()` (covers modal-open, add-row, remove-row — anything that changes the milestone *count*) and separately from each milestone row's status `<select>` `onchange` (a status *change* without a count change, which wouldn't otherwise trigger a re-render). Since it only ever reads `editingMilestones` and writes a few small DOM nodes, it's cheap enough to call defensively from several places rather than trying to track more precisely which one actually changed.

### Item plan date range roll-up

An item's plan date range (`startDate`/`dueDate`) is **computed from its milestones whenever it has at least one**, the same "reversal of an earlier manual-only design" as status above and for the same reason — a milestone that slipped shouldn't be silently invisible at the parent level because nobody went back and adjusted the item's own dates by hand. `computedDateRangeFromMilestones(milestones)` returns `{startDate, dueDate}` spanning the earliest to the latest date across *every* milestone's `dueDate` **and, when set, its `actualDate`** — considering actual dates too means a milestone that actually finished earlier or later than planned widens the item's range to match reality, not just what was originally scheduled. Returns `null` for an empty list, same convention as `computedStatusFromMilestones`.

**An item with zero milestones keeps a manual date range** — same fallback pattern as status. The same three call sites keep it in sync, plus one more that status doesn't need:
- `saveItem()`: `milestones.length ? computedDateRangeFromMilestones(milestones) : <manual Start/Due inputs>`.
- `updateMilestoneDateField()`: recomputes `it.startDate`/`it.dueDate` immediately after a milestone's due or actual date changes inline on the status board — a milestone's date is exactly the kind of edit that can happen without ever opening the item modal (see "Status board" above), so this can't wait for `saveItem()`.
- `applyCategoryMilestoneSync()`: a category sync can add or remove milestones on an item without the item modal ever opening, so it recomputes the range (alongside status) right after mutating `it.milestones`.
- `normalizeData()`: recomputes on every load/merge/import, self-healing legacy/stale values — the actual source-of-truth pass the other three are just keeping ahead of.

**Both the item modal and the status-board row hide manual date editing once milestones exist**, mirroring the Status field exactly: `#itemDatesManual` (the Start/Due `<input>` pair) and `#itemDatesComputed` (a read-only badge + explanatory note) toggle together with `#itemStatusSelect`/`#itemStatusComputed` inside the same `updateItemStatusFieldMode()` — which is why that function wasn't split in two despite the name; Status and Plan-dates always change computed-vs-manual mode in lockstep, driven by the same "does this item have milestones" check. The function also keeps the (possibly hidden) `#itemStartInput`/`#itemDueInput` values in sync with the live-computed range, since `addMilestoneRow()` still reads `#itemDueInput`'s value as a new milestone's default due date. On the status board itself, `itemRowHtml()`'s `planDatesHtml` renders `.item-dates-computed` (plain text, a tooltip explains it's derived) instead of the editable `.item-dates-inline` pair whenever `it.milestones.length > 0` — the item's own separate `actualDate` field (see "Data model" above — a distinct concept from the plan range) stays independently editable on the row regardless, since it was never part of what's being computed here.

### Modals

Seven modals share the `.modal-bg` pattern (add `.open` class to show, remove to hide): `wsModalBg` (create/edit a workstream, with a delete button that cascades to that workstream's items — and, since milestones live nested inside items, to their milestones too), `itemModalBg` (create/edit a scope item, `.modal-wide` at 520px to fit the milestones editor — see "Milestone checklist" above), `categoryModalBg` (create/edit an Admin-mode category and its milestone template — see "Categories (Admin mode)" below), `confirmModalBg` (generic confirm-then-run-a-callback, used by every delete, by restore-from-backup, and by cancelling a review cycle — see "Deletion tombstones and undo" below), `importModalBg` (merge vs. replace choice after picking a file), `backupsModalBg` (list + restore local daily snapshots), and `fileSyncModalBg` (onboarding/reconnect for the linked-file feature). All seven close on Escape and on a background click (listeners near the end of the `<script>` block check `e.target.id`).

### Data integrity

`normalizeData()` (called from `load()`, from every merge/import/file-sync entry point, and, for tests, from the `resetState()` glue) is the single source of truth for schema defaults: workstream `id`/`color`/`order` backfilled and the array re-sorted by `order`; an item's `id`/`name`/`owner`/`status`/`updatedAt`/`itStatus`/`businessStatus`/`budgetStatus` backfilled, an orphaned `workstreamId` (pointing at a deleted workstream) reassigned to the first remaining workstream, an orphaned/missing `categoryId` reassigned to the first category, a missing `startDate` defaulted from `dueDate`, a non-string `actualDate` defaulted to `null`, a missing `milestones` defaulted to `[]`, and each milestone's own `id`/`name`/`status`/`actualDate` backfilled (same `null` default) and a missing `dueDate` defaulted from its *parent item's* `dueDate` — then, once milestones are backfilled, any item with `milestones.length > 0` has its `status` recomputed via `computedStatusFromMilestones()` regardless of whatever value was saved (see "Item status roll-up"). A stale `filterWorkstreamId` (the one selector shared by Planning/Review/Dashboard — see "The shared workstream selector" above) is cleared if it no longer resolves, a stale/invalid `mode` falls back to `'planning'` (checked against the `MODES` array), and — since Review mode requires a specific workstream — `mode` additionally falls back to `'planning'` if it's `'review'` with no `filterWorkstreamId` selected. `deletedWorkstreamIds`/`deletedItemIds` are coerced to arrays and filtered to well-formed `{id, ...}` entries; `categories` and `reviewCycles` get the same array-coercion, and every category's own `id`/`name`/`milestones`/`order` is backfilled the same way a workstream's is. **If `categories` ends up empty** (a pre-categories save, or every category somehow got deleted), `normalizeData()` reseeds exactly one default: `{name: 'Development', milestones: DEFAULT_CATEGORY_MILESTONES}` — this is also how a pre-categories item picks up a valid `categoryId` on first load after the upgrade, since the orphaned-`categoryId` backfill runs after categories are guaranteed non-empty. Review cycles get `id`/`startedAt`/`completedAt`/`cancelledAt`/`confirmations` backfilled but are otherwise left alone — there's no cross-referential repair needed since a cycle referencing a since-deleted workstream is simply unreachable through the shared sidebar (which only lists live workstreams), not actively cleaned up; see "Review mode" below for why that's the deliberate choice rather than an oversight.

It also runs a one-time schema migration: a pre-nested-milestones save could have a top-level item with `type: 'milestone'` (milestones used to be their own top-level item, siblings of scope items, before this became a nested checklist). Rather than silently dropping these on first load under the new schema, `normalizeData()` folds each one into its own new single-milestone item (`startDate`/`dueDate` both set to the old milestone's `dueDate`, `milestones: [{ ...that one milestone }]`) and strips the legacy rows out of `items`. `type` itself is `delete`d off every item as part of this pass, since it no longer means anything under the new schema.

**Every place that assigns `workstreams`/`items` from an external source calls `normalizeData()`, not just `load()`** — the current call sites are `load()`, both branches of `applyImport()`, `restoreBackup()`, `linkFile()`'s merge-on-first-link branch, `reconnectFile()`, and `initFileSync()`. If you add another data-loading path (e.g. a new sync mechanism), route it through `normalizeData()` too, or you'll reintroduce the exact bug class this fixed — a render function assuming a field exists that an older/hand-edited/externally-sourced save doesn't have.

`normalizeData()` is also the security boundary for ids: every workstream/item/milestone id is interpolated unescaped into `onclick` HTML attributes at render time (`esc()` only covers *content* fields — name, owner — never `id`). That's fine for locally-created data since `genId()` only ever produces plain alphanumeric strings, but `mergeData()` and `applyImport('replace')` trust ids from an external `.json` file as-is. `isSafeId(id)` (`/^[a-zA-Z0-9_-]+$/`) plus the per-entity checks in `normalizeData()`'s three loops (workstreams, items, milestones) regenerate anything that couldn't have come from `genId()`, closing that off at the one place every external-data path already routes through — see `tests/cases/sync.test.js`'s "regenerates a workstream/item/milestone id" tests.

## Data durability

Pulse now matches PromptLab/mytasks' full data-durability feature set: JSON export/import, rolling local backups, deletion tombstones with toast undo, and optional File System Access API file sync. The "Data" dropdown in the topbar (`toggleDataMenu()`/`closeDataMenu()`, closed by the document-level click listener when a click lands outside `#dataDropdown`) is the entry point for Export, Import, and Backups. File sync deliberately has no entry there — see "File System Access API sync" below for why it lives entirely in the topbar's `#fileSyncIndicator` instead.

### Toast with undo

`showToast(msg, isError, undoAction)` — the third argument is new. When present, the toast shows an "Undo" button (`#toastUndoBtn`) and stays up 6s instead of 2s; `triggerToastUndo()` (wired to the button's `onclick`) invokes it and dismisses the toast immediately. Only one undo action is live at a time (`toastUndoAction`, a single module-level slot) — showing any other toast overwrites it, matching the single visible toast.

### Confirm modal — replaces native `confirm()`

`openConfirmModal({title, body, action, confirmLabel})` / `confirmModalAction()` / `closeConfirmModal()` replace the plain `window.confirm()` dialogs earlier versions used for delete. `modalTarget = {action}` holds the pending callback; clicking the modal's action button (`#confirmModalActionBtn`) runs it and closes the modal. This exists specifically so confirmations can describe *what* will happen (e.g. cascade counts) and hand off into the undo-toast flow below, which a same-tick `confirm()` return value can't do.

**`confirmLabel` defaults to `"Delete"`** — this one shared modal backs every confirm-then-act flow in the app, not just deletes (cancelling a review cycle, restoring a backup, applying a category's milestone-template sync to its items), and for a while those non-delete callers didn't override it, so the button read "Delete" for an action that wasn't a delete at all — confusing enough that a user reported a category-sync as "not working" when they'd likely declined it via a button that looked like it would destroy something. Every caller whose action isn't literally a delete now passes an explicit `confirmLabel` (`'Cancel Review'`, `'Restore'`, `'Apply Changes'`) — `tests/cases/*.test.js` assert the label alongside each of those flows specifically to keep this from silently regressing back to "Delete" if a new confirm-gated action gets added without one.

### Deletion tombstones and undo

`deletedWorkstreamIds`/`deletedItemIds` (each `{id, deletedAt}[]`) record "this id used to exist and was intentionally removed" — without them, an id absent from `workstreams`/`items` is indistinguishable from an id a merge has simply never seen, and a stale copy from an old linked file or import could silently resurrect something the user deleted on purpose. `tombstone(list, id)`/`untombstone(list, id)` add/remove an entry.

`deleteItem(id)` opens the confirm modal; its `action` splices the item out, tombstones it, then calls `showToast('Item deleted', false, undoFn)` where `undoFn` untombstones it and splices it back to its original index. `deleteWorkstreamFromModal()` does the equivalent at cascade scale: it snapshots the *entire* `items` array (`items.slice()`) before filtering out the workstream's items, tombstones the workstream id plus every removed item id, and its undo callback restores both the workstream (spliced back to its original index) and the whole pre-delete `items` array in one assignment — simpler and equally correct compared to tracking each removed item's individual original index. The undo callback must clear the tombstone(s) it set, or a delete-then-undo would leave the workstream/item permanently un-mergeable from any linked file/import that still has it.

### Merge and last-write-wins

`mergeData(data, opts)` is the additive merge used by every "read data from outside `localStorage`" path (`linkFile()`, `reconnectFile()`, `initFileSync()`, `fileSyncWrite()`'s cross-tab-conflict branch, and `applyImport('merge')`). It merges incoming tombstones first (union by id, keeping the later `deletedAt`), then workstreams *and* categories (both additive, deduped by id *or* case-insensitive name, merged silently — not counted in the return value, mirroring how mytasks' projects merge), then review cycles (additive by id only, no dedup-by-name since they're anonymous history rather than named entities — an id that already exists locally is left untouched rather than overwritten, since a cycle is meant to be append-only), then items (additive by id; an existing item is `Object.assign`-updated only if the incoming copy's `updatedAt` is newer, and both counts are returned as `{added, updated}`).

Inside the items pass, a tombstoned incoming id is skipped *unless* the incoming `updatedAt` is newer than the tombstone's `deletedAt` — that case is treated as a genuine edit made elsewhere after the local delete, and the stale tombstone is cleared to let it back in. Workstreams have no `updatedAt` (see "Data model" above), so a deleted workstream has no such escape hatch inside `mergeData()` itself — the only way one comes back is through `opts.respectTombstones: false` (below).

**The one exception: `applyImport('merge')`.** `mergeData()` defaults `opts.respectTombstones` to `true`; `applyImport('merge')` is the only caller that passes `false`. Picking a specific file and clicking Import → Merge is a deliberate, one-off action — unlike `linkFile()`/`reconnectFile()`/`initFileSync()`/`fileSyncWrite()`, which merge automatically in the background, where silently resurrecting a deletion via a stale copy would be surprising. With the flag off, a matching tombstone is cleared and the incoming item (or workstream) is added regardless of relative timestamps.

### Export / Import

`downloadData(data, filename)` is the shared primitive (Blob → object URL → synthetic `<a download>` click). `exportProgramme()` calls it with `currentExportPayload()` (`{version, exported, programme, workstreams, items}` — deliberately no tombstones, same reasoning as PromptLab/mytasks' export format). `triggerImport()` clicks the hidden `#fileInput`; `handleFileImport(event)` reads the picked file, validates it has both `workstreams` and `items` before staging it in `pendingImportData` and opening `importModalBg`. `applyImport(mode)`: `'replace'` downloads a `pulse-backup-before-replace-<date>.json` safety copy first, then overwrites `programme`/`workstreams`/`items` outright; `'merge'` calls `mergeData(pendingImportData, {respectTombstones: false})`. Both branches call `normalizeData()` before `save(); render()`.

### Local backups

`save()` calls `maybeSnapshotBackup()` on every save, which takes at most one rolling snapshot per calendar day (keyed by `todayStr()`) into `localStorage["pulse-backups"]`, keeping the last `MAX_BACKUPS` (7) days — a local safety net distinct from file sync, which mirrors live state rather than preserving history. A backup taken earlier in the day isn't refreshed by later saves that same day. The "Data → Backups" modal (`openBackupsModal()`/`renderBackupsModal()`) lists snapshots newest-first; `restoreBackup(date)` opens the confirm modal, and on confirm downloads a safety backup of the *current* data first (same `downloadData()` primitive), then overwrites from the snapshot and calls `normalizeData()`. Backups don't carry tombstones (same reasoning as export/import — a restore is an explicit full replace, not a merge).

### File System Access API sync

`fileHandle` (module-level, `null` until linked) plus a tiny hand-rolled IndexedDB wrapper (`_fsIdb`/`_fsGet`/`_fsPut`/`_fsDel`, db `pulse-fs`) persist the linked file handle across reloads — Chrome/Edge only (`window.showOpenFilePicker`/`showSaveFilePicker` feature-detected; Safari has neither). `save()` calls `fileSyncWrite(data)` whenever `fileHandle` is set. `fileSyncWrite()` does a light conflict check first: if the file on disk has changed since Pulse's own `lastSyncedSnapshot` (another tab or device wrote to it), it merges that external copy in via `mergeData()` before writing, and toasts what changed.

`linkFile()`/`createNewLinkedFile()` (via `window.showOpenFilePicker`/`showSaveFilePicker`) pick or create the linked file; `linkFile()` merges any existing content in the picked file on first link. `reconnectFile()` re-requests write permission (browsers can silently revoke it, e.g. after a restart) and merges. `initFileSync()` runs at page load: if a handle was persisted in IndexedDB, it tries to reuse it (merging the file's content in if permission is still granted, or prompting to reconnect if not); if there's no persisted handle at all, it opens the onboarding modal (`openFileSyncModal()`) so a first-time user is prompted to link or explicitly dismiss with "Not now". `updateFileSyncUI()` swaps the topbar's `#fileSyncIndicator` between four states (no picker support → hidden entirely, unlinked → "Link file" button, linked-and-granted → filename + unlink button, linked-but-permission-lapsed → amber "Reconnect" button) via `fadeSwapHTML()` (a short opacity crossfade, skipped if the HTML is already identical). This indicator is the *only* entry point into `openFileSyncModal()` — there's deliberately no static "File sync" item in the Data dropdown, because a dropdown item can't reflect which of those four states is current the way the indicator does; a fixed menu entry would keep opening the "nothing's linked yet" onboarding copy (including the "will be lost if you clear browsing data" warning) even once a file *is* linked and auto-saving, which is exactly the bug this avoids.

**Testing caveat**: the JXA test harness doesn't mock `indexedDB` (its no-op `setTimeout` would leave any real async IndexedDB request forever unresolved, hanging a test). Every file-sync function that would touch it is gated on a `window.showOpenFilePicker`/`showSaveFilePicker`/`fileHandle` check first, and the harness's fake `window` has neither — so `linkFile()`, `createNewLinkedFile()`, `initFileSync()`, and `reconnectFile()` all safely no-op in tests. `unlinkFile()` is the one exception (it unconditionally calls into IndexedDB) and is deliberately not exercised by the test suite for that reason.

## Categories (Admin mode)

`renderAdmin()` lists every category (name, its milestone template as a `→`-joined preview string, and a live count of items currently using it) with an Edit button; "+ Category" opens the same `categoryModalBg` with nothing pre-filled. There's no separate "new" vs "edit" function — `openCategoryModal(id)` handles both, mirroring the workstream/item modal pattern (`editingCategoryId` is `null` for a new one).

`editingCategoryMilestones` is a working array of *plain strings* (not `{id, name, dueDate, status}` objects like an item's own milestones) — a category's `milestones` field is a template of names only, since a template has no dates or statuses yet. `renderCategoryMilestonesEditor()`/`addCategoryMilestoneRow()`/`removeCategoryMilestoneRow(idx)` mirror the item modal's milestone editor (same `.milestone-row` CSS class, just missing the date input and status select), including the "no re-render on keystroke, only on structural changes" discipline — see "Milestone checklist" above for why that matters for focus.

Order matters here (it's the sequence new items get seeded with), so each row also gets an up/down `.milestone-reorder` control — `moveCategoryMilestoneRow(idx, dir)` swaps `editingCategoryMilestones[idx]` with its neighbor at `idx + dir` (`dir` is `-1`/`1`) and re-renders; it no-ops (rather than wrapping around) if the target index would fall outside the array, and the first row's up-button / last row's down-button are rendered `disabled` so that boundary is visible rather than just silently inert. Like every other edit to this array, reordering only touches `editingCategoryMilestones` — the category's saved `milestones` array is untouched until `saveCategory()` commits it.

`deleteCategoryFromModal()` refuses outright (toast, no confirm modal) if `categories.length <= 1` — there must always be at least one category for an item to reference, the same invariant `normalizeData()` enforces on load. Otherwise it opens the confirm modal describing how many items will be reassigned, and on confirm reassigns every item using the deleted category to `categories.find(c => c.id !== catId)` (the first *other* category) before removing it. Unlike workstream/item delete, **this has no undo toast** — categories are an Admin-level structural concept rather than day-to-day content, so a plain "this cannot be undone" confirm was judged sufficient rather than adding tombstone/undo machinery for a rarely-used action.

### Category template edits sync to items already using that category

Editing an *existing* category's milestone template (add/rename/remove) propagates to every item with that `categoryId`, not just future new items — a deliberate reversal of this project's earlier stance (an item's checklist used to be a one-time snapshot, fully independent of its category after creation). `saveCategory()` diffs `editingCategoryOriginalMilestones` (the template as it was when the modal opened, captured by `openCategoryModal()`) against the final `editingCategoryMilestones` **by name, as sets** — there's no id linking one template entry across an edit, so a rename is indistinguishable from "the old name was removed and a new name was added," and is treated exactly that way.

**Reordering the template also syncs to existing items, but through a separate, non-destructive path.** A pure reorder (same names, different order — `added`/`removed` both empty but the arrays differ index-for-index) sets a `reordered` flag and, if any items use the category, calls `applyCategoryMilestoneSync(catId, [], [], milestones)` directly — no confirm modal, since nothing is added or removed, just resorted. `applyCategoryMilestoneSync`'s 4th parameter, `orderedNames`, is the template's current name order; after handling any add/remove, it sorts every affected item's `milestones` array by each milestone's index in `orderedNames` (a milestone whose name isn't in the template at all — a one-off custom milestone added by hand — ranks after every template-matched one, keeping its relative position via the sort's stability). This reorder is also applied on the *destructive* add/remove path, for the same reason: a newly-added milestone lands at its correct template position rather than always at the array's end.

Reordering an item's underlying `milestones` array doesn't always change what's visibly displayed — `milestoneRowsHtml()` sorts by `dueDate` for display, stably, so array order only wins the tiebreak when due dates are equal. That's exactly the common case for a freshly-seeded item (every milestone defaults to the same due date at creation — see "Milestone checklist" above), so reordering the template correctly reorders those items' display too; once a user has spread milestones across distinct due dates, display order legitimately tracks those dates instead, and the template's order no longer visibly matters for that item — this isn't a bug, it's the same date-driven display rule that's always applied.

If the diff is non-empty **and** at least one item currently has that `categoryId`, `saveCategory()` doesn't save at all yet — it closes the category modal and opens the confirm modal instead, describing the impact in plain terms ("add N milestones and/or remove M milestones... on K items... This cannot be undone"), with the actual save + `applyCategoryMilestoneSync()` call deferred into the confirm modal's `action`. Cancelling that confirm discards the *entire* category edit, including the name field — same as Cancel in the category modal itself, since by the time the confirm modal is showing, the category modal is already closed and there's no "back" state to return to. If there's no items-facing diff (new category, no name/add/remove changes, or a category nobody uses yet), it saves immediately with no confirm step — the confirm modal only exists to gate the destructive/item-affecting path.

`applyCategoryMilestoneSync(categoryId, addedNames, removedNames)` is the actual sync, run once per affected item: names in `removedNames` are filtered out of `it.milestones` by exact name match — **including a milestone that's already Complete with an actual date recorded**, since the user confirmed exactly this tradeoff up front; names in `addedNames` are appended fresh (`{status:'not-started', dueDate: it.dueDate, actualDate: null}`), skipped if the item already has a milestone with that exact name (so re-adding a name you'd already got manually doesn't duplicate it). It finishes by recomputing `it.status` via `computedStatusFromMilestones()` if any milestones remain — a sync that removes an item's single worst (weakest) milestone can genuinely change its computed status, same as any other milestone-list mutation (see "Item status roll-up").

## Review mode

A review cycle is scoped to exactly one workstream (`activeReviewCycle(wsId)` finds the one cycle for that workstream with both `completedAt` and `cancelledAt` still `null` — `startReviewCycle()` is a no-op if one's already active, so there's never more than one open cycle per workstream at a time). Review mode has no workstream picker of its own any more — it reads the shared `filterWorkstreamId` (see "The shared workstream selector" above), which is guaranteed non-null whenever `mode === 'review'` is actually showing. The shared sidebar (`renderSidebar()`, `#wsList` — same one Planning and Dashboard use) shows each workstream a small badge regardless of which of the three modes is active: amber "In review" if it has an active cycle, red "Overdue" if `isReviewOverdue(w.id)` (no completed cycle in the last `REVIEW_STALE_DAYS` (30) days, or never reviewed at all), otherwise no badge — so review staleness is visible while planning, not just while reviewing.

**Completion gate, and why it needs no extra bookkeeping for mid-cycle adds.** `canCompleteReviewCycle(cycle)` checks that *every item currently in `cycle.workstreamId`* has a matching entry in `cycle.confirmations` — it re-derives the live item list each call rather than snapshotting it when the cycle started. This is what makes "an item added mid-cycle automatically becomes an unconfirmed blocker" fall out for free (per the product requirement this was built against): there's no separate "which items does this cycle cover" list to keep in sync, so a newly-added item simply has no confirmation entry yet and the `.every()` check naturally fails until someone confirms it. The flip side: an item *deleted* mid-cycle just stops being checked (its stray confirmation entry, if any, is harmless orphaned data — never pruned, never causes a crash since nothing indexes into `confirmations` by array position).

`toggleReviewConfirm(cycleId, itemId)` is a toggle (add the confirmation if absent, remove it if present) rather than one-way, so a reviewer can un-confirm something they change their mind about before completing. `completeReviewCycle(cycleId)` re-checks `canCompleteReviewCycle()` itself (defense in depth — the UI already disables the button via the same check, but the guard lives in the mutating function, not just the render) and sets `completedAt`. `cancelReviewCycle(cycleId)` goes through the confirm modal (no undo — like category delete, this was judged a low-enough-stakes, infrequent action not to warrant tombstone/undo machinery) and sets `cancelledAt`; either outcome frees the workstream for `startReviewCycle()` to open a new one. Both `completedAt`/`cancelledAt` are permanent once set — a cycle is never un-completed or un-cancelled, and never deleted from `reviewCycles`, which is what makes it usable as history.

`renderReview()` writes into the shared `#main` (not a Review-only element): it renders, in order: the workstream header for `filterWorkstreamId`, either a "Start review cycle" button (no active cycle) or the live checklist (`reviewItemRowHtml()` per item — name, dates, its own status badge that opens `openItemModal()` for inline edit-then-confirm, and a confirm toggle button) plus a progress bar and Complete/Cancel buttons (active cycle), then a "History" section listing every `completedAt`/`cancelledAt` cycle for that workstream newest-first (`reviewHistoryRowHtml()`), regardless of how the active-cycle section above rendered. It defensively falls back and re-renders if `filterWorkstreamId` points at a workstream that's since been deleted — belt-and-suspenders alongside the three-layer gate described above, since nothing should actually reach `renderReview()` in that state.

## Dashboard mode

`renderDashboard()` is read-only — nothing on it mutates state, it only computes and displays — and, like Review, is scoped by the shared `filterWorkstreamId`: `visibleWorkstreams()` (the same helper Planning's status board/timeline already used) narrows everything on the page to just the selected workstream, or the whole programme if "All workstreams" is selected. `allMilestonesFlat(itemList)` takes an optional pre-filtered item list for this reason (defaults to the global `items` if omitted) rather than always flattening every milestone in the programme. Three cards up top: **Item Status** (item count *within the current scope* + a `.dash-bar` stacked bar of RAG counts, colored via the same `--stat-*` variables as everywhere else, plus a text legend), **Milestone Completion** (`% complete` across the scoped items' milestones), and **Overdue for Review** (count + names of *scoped* workstreams where `isReviewOverdue()` is true — the same helper the shared sidebar's badge uses, shared rather than duplicated; scoping to one workstream makes this card either 0 or 1). Below that: a per-workstream summary table (item count + milestone completion % — only rows for workstreams in scope), then two side-by-side attention-needed feeds — **Overdue** (scoped items/milestones with `status !== 'complete'` and `dueDate` before today) and **Upcoming** (same, but `dueDate` within the next 7 days) — each entry sorted by date and, for a milestone, labeled `"<item name> — <milestone name>"` so it's clear which item it belongs to without a nested list.

There's no persisted dashboard state and no separate "refresh" action — every value is recomputed from `items`/`workstreams`/`reviewCycles` (filtered through `visibleWorkstreams()`) at render time, so it's automatically current whenever `render()` calls it (i.e. every time `setMode('dashboard')` runs, `setFilterWorkstream()` changes the scope, or any other mutation happens while already in Dashboard mode).

## Conventions from this project's history

- Font Awesome 6.5 (`fa-solid`) via CDN, matching PromptLab/mytasks.
- `button:focus:not(:focus-visible) { outline: none; }` is global — focus rings only show for real keyboard navigation, not post-click.
- IDs are generated by `genId()` (timestamp + random suffix); `isSafeId()` plus `normalizeData()`'s regeneration passes are the guard against a crafted id from an external `.json` file (import, linked file) breaking out of an `onclick` attribute — see "Data integrity" above.
