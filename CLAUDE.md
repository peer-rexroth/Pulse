# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Pulse is a single-file, zero-dependency HTML application — the entire app (HTML, CSS, JavaScript) lives in `pulse.html`. There is no build step and no package manager. It's a local-first programme dashboard, organized into four top-level modes (see "Modes" below): **Planning** (workstreams, scope items, milestones — a status board), **Review** (dated, per-workstream review cycles that require every item to be confirmed before completing), **Dashboard** (a read-only health rollup + attention-needed feed), and **Admin** (the category lookup table that seeds a new item's milestone checklist). It's also an installable PWA (manifest, service worker, icons), and has the same data-durability feature set as this author's other single-file apps (PromptLab, mytasks): JSON export/import, rolling local backups, deletion tombstones with undo, and optional File System Access API file sync — see "Data durability" below.

## Running it

A plain `file://` open of `pulse.html` works fine for quick checks, but PWA install/offline support requires serving it over http — browsers refuse to register a service worker for `file://` pages. `./start-pulse.command` serves the directory on `http://127.0.0.1:8936` and opens it in Chrome/Edge (Safari can't install this kind of PWA on macOS). `./stop-pulse.command` kills the server.

## Tests

There's no lint config, but there is a test suite at `tests/`: extract the inline `<script>` block, mock just enough of the DOM (`document.getElementById` returning cached fake elements with a settable `innerHTML`/`value`, plus `localStorage`, `navigator`, `window`, `location`, `Blob`/`URL` for the export/download path) and `eval()` the real code in a headless JS engine (`osascript -l JavaScript` — JavaScriptCore, no Node install needed). `indexedDB` is deliberately *not* mocked — see "File System Access API sync" below for which functions that rules out testing directly.

Run it with `./tests/run.sh` (optionally `./tests/run.sh someSubstring` to run only tests whose name contains that substring). No install step.

Add a test by dropping a `tests/cases/*.test.js` file with `test('description', function(){ ... })` calls. All app code plus every `tests/cases/*.test.js` file get concatenated and `eval()`'d *together* in one call, which is why a test can read/reassign `workstreams`, `items`, `categories`, `reviewCycles`, `mode`, `filterWorkstreamId` and the other top-level `let` state directly by bare name, and call any of the app's real functions — they're all sharing the same eval'd lexical scope. `tests/harness.js` calls `resetState()` (glue-defined: `seedDefaults()` + resets the UI-transient module vars + `normalizeData()`) and clears the fake DOM before every test, so tests never see state left over from another test — write fixtures at the top of each test rather than relying on run order. `seedDefaults()` itself creates zero workstreams (see "Data model" below); `resetState()`'s glue pushes one (`{name: 'Workstream 1', ...}`) back in immediately after, purely so the many existing tests that assume `workstreams[0]` already exists as a baseline convenience don't all need touching — the real product's fresh-install behavior is what `seedDefaults()` alone does.

Test files, by area: `workstreams.test.js`, `items.test.js`, `normalize.test.js`, `views.test.js` (status board rendering) predate categories/review/dashboard; `categories.test.js` (Admin CRUD, category-driven milestone seeding/reseeding), `review.test.js` (cycle start/confirm/complete/cancel, mid-cycle-add behavior, staleness), `dashboard.test.js` (rollup math, overdue/upcoming feeds), `modes.test.js` (mode switching, body visibility, tab active-state), `sync.test.js` (tombstones, merge, export/import, backups), `theme.test.js` (color scheme persistence/picker — see "Color scheme system" below), and `role.test.js` (the role ladder, picker/switcher, and per-role UI gating — see "Roles (RBAC)" below) cover everything added since.

One mock limitation worth knowing: the fake `<select>`/`<input>` elements don't parse `innerHTML` into `.value` the way a real browser does, so a test that wants to assert "this option got preselected" must check the rendered `innerHTML` string for `selected`/`value="..."` rather than reading `.value` after a `populate*Select()` call — see `tests/cases/items.test.js`'s "preselects the given workstream" test for the pattern. Tests that set form values *before* calling `save*()` set `.value` directly instead, which the mock does support.

## Architecture

The file has three logical sections in order: CSS styles, HTML structure, and a `<script>` block containing all application logic.

### Data model

All state is stored in `localStorage` under the key `"pulse-v1"` and serialised as JSON with this shape:

```json
{
  "programme": { "name": "...", "rolePasswords": { "reviewer": null, "editor": {"salt": "...", "hash": "..."}, "admin": null } },
  "workstreams": [...],
  "items": [...],
  "categories": [...],
  "reviewCycles": [...],
  "mode": "planning" | "review" | "dashboard" | "admin",
  "theme": "light" | "dark",
  "colorScheme": "standard" | "modern" | "dracula" | "github" | "githubdimmed", // see "Color scheme system" below
  "filterWorkstreamId": null | "wsId",
  "deletedWorkstreamIds": [{"id": "...", "deletedAt": 0}],
  "deletedItemIds": [{"id": "...", "deletedAt": 0}]
}
```

`userRole` (`"visitor" | "editor" | "reviewer" | "admin"`, see "Roles (RBAC)" below) is deliberately **not** part of this blob — it lives under its own `localStorage` key entirely, and is never written to or read from a linked/synced data file at all.

A **workstream**:
```js
{ id: String, name: String, color: String, order: Number,  // color is a name key from WS_COLORS
  actionLog: [{ id: String, text: String, owner: String, dueDate: String|null,
                completed: Boolean, completedAt: Number|null, cycleId: String, addedAt: Number }],
  decisionLog: [{ id: String, text: String, cycleId: String, addedAt: Number }] }
  // actionLog/decisionLog are the workstream-wide, review-cycle-spanning
  // action item/decision lists — see "Review mode" below
```

An **item** — `itemType` distinguishes a plain scope item from a Journey (see "Journeys" below), but both share this one shape:
```js
{
  id: String,
  workstreamId: String|null, // null means "Unassigned" for a scope item (see "Quick-add scope items, the Unassigned bucket, and the Pending category") — always null for a Journey, which is never assigned to one at all (see "Journeys")
  categoryId: String|null,  // which Category's milestone template seeded this item — see "Categories (Admin mode)"; always null for a Journey (itemType 'journey' — see "Journeys"), which has no category at all
  name: String,
  status: 'not-started' | 'green' | 'amber' | 'red' | 'complete', // computed from milestones if any exist — see "Item status roll-up"
  startDate: String,       // 'YYYY-MM-DD'
  dueDate: String,         // 'YYYY-MM-DD'
  actualDate: String|null, // 'YYYY-MM-DD' — when it was actually finished; manual, never inferred from status
  updatedAt: Number,       // Date.now() — last-write-wins timestamp for merge (see "Data durability")
  milestones: [Milestone],
  itStatus: 'green' | 'amber' | 'red',       // IT readiness tag — see "IT/Business/Budget tags" below
  businessStatus: 'green' | 'amber' | 'red', // Business readiness tag
  budgetStatus: 'green' | 'amber' | 'red',   // Budget/funding status tag
  order: Number, // manual position within this item's workstream — see "Manual item order and drag-and-drop reordering"
  externalDelivery: Boolean,           // is this item delivered by an external party? — see "External Delivery" below
  externalDeliverySpoc: String|null,   // only ever non-null while externalDelivery is true
  itemType: 'scope' | 'journey',  // see "Journeys" below — defaults to 'scope', backfilled by normalizeData()
  journeyId: String|null          // set on a scope item connected to a Journey (toggleJourneyConnection()) — see "Journeys"
}
```

Workstreams have no `updatedAt` (mirroring mytasks' projects) — see "Merge and last-write-wins" below for what that means for a deleted workstream.

**An item used to also carry its own `owner: String` — removed entirely (an explicit user request), not just hidden from the modal.** The field, its modal input, and the row's icon+name display are all gone; `saveItem()` no longer reads or writes it, and `normalizeData()` no longer backfills it. A pre-existing save that still has a leftover `owner` string on some items (from before this change) isn't actively stripped — it's just an inert, never-read property from here on, same "orphaned field is harmless" stance already taken elsewhere in this file (an orphaned review-cycle reference, an unused legacy `type` field, etc.) rather than adding a one-time migration pass for a value nothing displays or edits anymore. This is a distinct, unrelated concept from the Action Log's own Owner column (`actionLog[].owner`, above) — that one is a real action item's assignee and was untouched.

A **milestone** — nested inside its parent item, not a top-level array:
```js
{ id: String, name: String, dueDate: String|null, actualDate: String|null, status: 'not-started' | 'green' | 'amber' | 'red' | 'complete', notApplicable: Boolean }
// dueDate is only ever null while notApplicable is true (see "Not Applicable milestones" below) — an applicable milestone always has one.
```

**`actualDate` is deliberately manual, on both items and milestones** — it is never auto-filled when `status` is set to `'complete'`, and setting an `actualDate` never auto-sets `status` either. The two are independent: a PM might record the real finish date before formally marking something Complete (or vice versa, or never at all) — auto-linking them would take that judgment call away. `openItemModal()`/`saveItem()` read/write `#itemActualInput` the same way they do `startDate`/`dueDate`; `renderMilestonesEditor()` gives each milestone row its own actual-date input (`editingMilestones[idx].actualDate`) alongside its due-date input. Both default to `null` (not an empty string) when unset — `saveItem()` coerces the date input's `''` to `null` on save (`document.getElementById('itemActualInput').value || null`, and the same pattern per milestone), so "no actual date yet" is a single consistent falsy value rather than sometimes `''` and sometimes `null` depending on the code path.

Milestones don't have their own `owner`/`startDate` — they're a lightweight checklist against a single date, deliberately kept smaller than the item shape rather than reusing it. An item's own `status` **is** computed from its milestones whenever it has any — see "Item status roll-up" below.

A **category** (Admin mode's lookup table — see "Categories (Admin mode)" below):
```js
{ id: String, name: String, milestones: [String], order: Number, pending: Boolean }
// milestones here are plain name strings, a template — not the {id,dueDate,status} shape an item's own milestones have.
// pending flags the one reserved category — see "Quick-add scope items..." below — default false.
// A Journey (see "Journeys" below) has no category at all — categoryId is null for one, not a
// reference to a reserved category the way an earlier version of this feature had.
```

A **review cycle** (see "Review mode" below):
```js
{
  id: String, workstreamId: String,
  startedAt: Number,              // Date.now()
  completedAt: Number | null,
  cancelledAt: Number | null, // legacy only — nothing sets this anymore; a cancelled cycle is deleted, not marked (see "Review mode")
  confirmations: [{ itemId: String, confirmedAt: Number }],             // zero-milestone items only
  milestoneConfirmations: [{ milestoneId: String, confirmedAt: Number }], // every milestone, across every item
  itemCountAtClose: Number | undefined,      // snapshotted at completedAt — see snapshotReviewCycleCounts()
  confirmedCountAtClose: Number | undefined, // undefined on a still-active cycle, or one closed before this field existed
  changeLog: [{                        // see logReviewChange()
    itemName: String, milestoneName: String | null, change: String, changedAt: Number,
    itemId: String, milestoneId: String | undefined, // stable ids, used only to re-sort for display — see orderedChangeLog()
    tagChange: { field: String, oldValue: String, newValue: String } | undefined,      // IT/Business/Budget
    statusChange: { oldValue: String, newValue: String } | undefined,                  // milestone status
    dateChange: { label: String, oldValue: String|null, newValue: String|null } | undefined // Due/Actual/Start
  }]
}
```
Review cycles are append-only history — nothing ever deletes one, `completedAt`/`cancelledAt` just get set once. Exactly one of `completedAt`/`cancelledAt` is non-null once a cycle is finished; both `null` means it's still active.

### Modes

`mode` (`'planning' | 'review' | 'dashboard' | 'journeys' | 'admin'`, `MODES` array is the source of truth for the valid values) is the top-level navigation axis. Planning/Review/Dashboard are switched via the topbar's `.view-tabs` mode pill (`#tabDashboard`/`#tabPlanning`/`#tabReview`, in that left-to-right order — Dashboard and Planning were swapped from their original order after a later request) and `setMode(m)`; Admin is deliberately **not** in that pill — it's its own plain `.btn` (`#tabAdmin`) sitting in the topbar's right-hand cluster, because it isn't workstream-scoped the way the other three are (see "The shared workstream selector" below) and grouping it with them would imply it was. Journeys used to sit right next to it as its own topbar `.btn` too, for the same reason (a Journey is never workstream-scoped either — see "Journeys" further down) — moved into the sidebar instead (`#journeysNav`, see "Journeys" below) per a later, explicit user request to relocate its entry point there, separate from the workstream list.

Planning, Review, Dashboard, and Journeys share one container, `#scopedBody` (`.body-row` — sidebar + `#main`); Admin alone gets its own sidebar-less container (`#adminBody`, a plain `.main`, no sidebar), since categories aren't workstream-scoped. `render()` is the single top-level dispatcher: it shows `#scopedBody` for every mode except `admin` (which shows `#adminBody` instead), toggles `#reviewToolbar` (Review's own Scope Item Review/Action Log sub-tabs — see "Review mode" below) visible only for `mode === 'review'`, always calls `renderSidebar()` (the sidebar now stays current, and visible, across all four of these modes — including Journeys, which reads nothing from it but still shows its own nav entry there), and then calls exactly one of `renderMain()` (planning), `renderReview()`, `renderDashboard()`, `renderJourneys()`, `renderAdmin()` — each writes into its own container (`#main` for the first four, `#adminBody` for the last).

**Every mutation should call the top-level `render()`**, not a mode-specific render function, *unless* the call site is only ever reachable while that mode is already showing (e.g. `cycleMilestoneStatus()` calls the narrower `renderMain()`, safe because a milestone status badge only exists inside Planning's status board — nothing outside Planning can trigger it). `saveItem()`/`deleteItem()` in particular call the general `render()` because `openItemModal()` is reachable from both Planning (its own rows) and Review (a checklist row's status badge) — a narrower call would leave whichever mode *isn't* Planning showing stale content after a save made from Review mode.

### The shared workstream selector

`filterWorkstreamId` is no longer Planning-only — it's the single selector Planning (status board), Review (which workstream's cycle to show), and Dashboard (scopes the whole rollup) all read from, set from the one shared sidebar (`renderSidebar()`/`#wsList`) that's now visible in all three modes rather than duplicated per-mode. `null` means "All workstreams" for Planning/Dashboard.

**Clicking a row in the sidebar — "All workstreams" or a real workstream — always lands on the Dashboard scoped to that selection, regardless of whatever mode was showing beforehand** — an explicit user request. This is `selectWorkstreamFromSidebar(id)`, not the plain `setFilterWorkstream(id)` the sidebar used to call directly: it sets `filterWorkstreamId` and `mode = 'dashboard'` together in one `save()`/`render()`, the same combined-fields pattern `setUserRole()` already uses for its own "jump to Dashboard, All workstreams" case (see "Roles (RBAC)" below). `setFilterWorkstream()` itself stays deliberately mode-agnostic — every other caller depends on it *not* touching mode: `reviewDatesOverviewHtml()`'s own rows (see "Review mode" below) call it directly so picking a workstream from that staleness ranking lands on its Scope Item Review, not Dashboard; and the many places elsewhere in this file (and its test suite) that just want to narrow the scope without navigating away from the current mode.

**The sidebar's "All workstreams" row is visually set apart from the real, per-workstream rows below it** (`.ws-row-all` — a user-reported readability request, since with the three sub-tab additions above it stopped being a plain fallback and became a real, frequently-used destination in its own right, not a row that should blend into the list): a thin `border-bottom` plus extra bottom padding separates it from the workstream rows, and it renders a neutral `fa-layer-group` icon (`.ws-row-all-icon`) in place of a real workstream's own colored `.ws-dot` — since it doesn't have (or stand in for) any single workstream's color, using one would misleadingly suggest it did.

**Review mode used to require a specific workstream unconditionally — a review cycle is one workstream at a time — but that stopped being true once every one of its sub-tabs grew an "All workstreams" view of its own.** The Action Log has no cycle dependency at all (it's `workstream.actionLog`, tracked independently of any cycle's own lifecycle — see "Action Log" below), so a user request for an "All workstreams" rollup of it (`allWorkstreamsActionLogHtml()`, see below) was the first crack in the old "Review always needs a workstream" gate — followed by the same request for Decision Log (`allWorkstreamsDecisionLogHtml()`), and finally by Scope Item Review itself gaining `reviewDatesOverviewHtml()` (see "Review mode" below) — a genuinely useful "All workstreams" landing view in its own right, not just a fallback. With all three sub-tabs covered, **the gate is gone entirely, at all three of the layers it used to live at**:

1. **Entry**: `setMode('review')` never touches `reviewTab` at all any more — it used to force `reviewTab = 'actionLog'` whenever `filterWorkstreamId` was falsy (back when Scope Item Review had nothing to show without one); now every sub-tab has something to show, so whichever one was already selected just stays selected.
2. **Mid-session**: `setFilterWorkstream(id)` no longer hops `reviewTab` when the newly-picked `id` is `null` — it used to jump Scope Item Review over to Action Log for the same reason as above; picking "All workstreams" while on Scope Item Review now just shows `reviewDatesOverviewHtml()` in place.
3. **Load-time backstop**: `normalizeData()` no longer falls back `mode` to `'planning'` for `mode: 'review'` with no `filterWorkstreamId` selected — that fallback existed only because `reviewTab: 'scope'` with no workstream used to be unrenderable; it isn't any more.

`renderReview()` itself reflects this: `!filterWorkstreamId` checks `reviewTab` and renders whichever "All workstreams" view that tab has — `allWorkstreamsActionLogHtml()`, `allWorkstreamsDecisionLogHtml()`, or `reviewDatesOverviewHtml()` — there's no empty-state fallback left in this branch at all, since all three cases are now covered.

The topbar's Review tab (`#tabReview`) was already never marked disabled; `#tabReviewScope` (Review's own Scope Item Review sub-tab) no longer is either — the `.disabled`-toggle it used to inherit for the same "nothing to show without a workstream" reason, and the now-unused `.view-tab.disabled` CSS rule itself, were both removed once that stopped being true.

### RAG status

`STATUSES` (top of the `<script>` block) is the single source of truth for the five status values and their labels: Not Started, On Track (green), At Risk (amber), Off Track (red), Complete (blue). Status drives an item's color everywhere it appears — the status badge in the status board. Workstream color (`WS_COLORS`, a separate 8-hue palette) is used only for the sidebar dot and the status-board section header tint — it never colors an item, since status is the signal a programme dashboard is meant to surface at a glance.

### Rendering pattern

Direct DOM re-renders (no virtual DOM or framework). `render()` does a full re-render (topbar bits + sidebar + main); `renderSidebar()` and `renderMain()` handle their halves independently. Every state mutation calls `save()` then one of these. `renderMain()` always renders the status board (`renderStatusView()`) — if you add a mutation that should be reflected live, make sure it calls `render()` (or at least the render function covering whatever it changed), not a narrower one that happens to work for today's call site.

### Status board (`renderStatusView`)

One `.ws-section` per visible workstream (filtered by `filterWorkstreamId` via `visibleWorkstreams()`), each showing a RAG count summary (`STATUSES` filtered to non-zero counts) and its items sorted by `order` (see "Manual item order and drag-and-drop reordering" below — this used to be `dueDate`, but a reviewer/planner reordering the list by hand needs that order to actually stick, not get re-sorted out from under them the moment a due date changes). Review's own `renderReview()` sorts its item list the exact same way, for the same reason: it's meant to be *the same list* as Planning's, not an independently-sorted one. `itemRowHtml(it)` renders the item's own row plus, if `expandedItemIds` (a module-level `Set`, UI-only — not persisted, resets on reload) has that item's id, a small `milestoneHeaderHtml()` column-label row and its nested milestone rows (`milestoneRowsHtml`, in plain array order — see "Category template edits sync to items already using that category" below for why this is *not* sorted by `dueDate`) immediately after. Clicking a milestone's own status badge calls `cycleMilestoneStatus(itemId, milestoneId)`, which steps through `STATUSES` in array order and wraps — a quicker way to update a milestone's RAG than opening the item modal (and, per "Item status roll-up" below, recomputes the parent item's status too).

**Plan-date ranges always show the year** (`fmtDateY`, distinct from the plain `fmtDate` used for other, single-date, same-year-implied contexts like backup timestamps and review-cycle start dates) — a Start/Due range legitimately spans years (e.g. a scope item starting one calendar year and due the next), and a bare "Jul 26 → Jan 1" reads as backwards or same-year when it isn't. Used for the item row's computed range, the item modal's computed-range badge, and the review-mode item row — anywhere a Start→Due *range* is rendered as text.

**There is deliberately no page-wide column header.** An earlier version added one sticky `.item-row-header` above all `.ws-section`s, labeling all the shared columns once for the whole page — this got removed because it implied those labels applied uniformly to milestone rows too, when a milestone only ever populates a handful of them (Milestone/Due/Actual/Status). `milestoneHeaderHtml()` instead renders a small `.milestone-header` scoped to *one* expanded item, directly above that item's own milestone rows — appearing and disappearing with the same chevron toggle that shows/hides the milestones themselves, so the labels are only ever visible attached to the specific list they describe.

**Column layout is a real CSS grid, not flexbox** — `.item-row`, `.milestone-header`, and `.milestone-sub-row` all share one `grid-template-columns` value, `--item-grid-cols` (a `:root` custom property, currently 10 columns: Chevron, Name, an always-blank column (formerly Owner — see below), Milestones-badge, Plan-dates, an always-blank spacer, Milestone-Due, Tags/Milestone-Actual (item-only Tags on the item's own row, the milestone's own Actual-date input on a milestone row), Status, Actions), so a milestone's Due/Actual/Status line up directly under its parent item's columns and `milestoneHeaderHtml()`'s labels line up over both. **Owner was removed as a concept entirely (an explicit user request) — the modal field, the row's icon+name display, and the `owner` property on the item's own data shape are all gone — but its grid column stays, now permanently empty (`<span></span>`), rather than collapsing `--item-grid-cols` further and renumbering every explicit `grid-column:N` reference that comes after it (milestone name's own span, the review confirm toggle's `grid-column`, etc.).** That renumbering would touch several already-tuned, comment-documented spots across `itemRowHtml()`/`milestoneRowsHtml()`/`milestoneHeaderHtml()`/Review markup for a request that was really about the *field*, not the layout geometry — an empty placeholder cell is the same safe, established pattern already used everywhere else in this grid for a column a given row has nothing to put in (see below). The `.item-owner` CSS class itself is untouched, since Action Log's own, unrelated Owner column (a real, still-present concept for action items) still uses it. **A later user request moved the Milestones-count badge from column 3 to column 4, swapping widths with the blank former-Owner column next to it** — the badge only needs 90px, so the extra width is better spent letting `.item-name` itself span columns 2-3 (`grid-column: 2 / 4`, set inline in `itemRowHtml()`) instead of sitting in column 2 alone. A separate, later request removed the grid's old "Actual" placeholder column outright (it used to sit right after Plan-dates, reserved for the item's own `actualDate` field even though nothing was ever rendered there — that field is only ever edited in the item modal) rather than leaving it shrunk-but-present the way the Owner column was kept — every explicit `grid-column:N` reference from that point on (the review confirm toggle, the Status/N/A spanning cell) shifted down by one accordingly. **This means every cell in every row must be a real element, even when empty** — an omitted element (the old code used to render the milestone-count badge as a plain empty string `''` when an item had zero milestones) collapses that grid column entirely for that row, shifting every subsequent cell left and breaking alignment with rows that do have content there. `itemRowHtml()`'s `milestoneBadge` and `milestoneRowsHtml()`'s several deliberately-empty `<span></span>` placeholders (for the columns a milestone row has nothing to put in) exist specifically to hold their column open — `tests/cases/views.test.js`'s "still renders the milestone-count-badge element (empty)" test guards this exact regression. `milestoneRowsHtml()` also reuses the `.item-chevron` class (holding a small diamond icon instead of a chevron) for its first cell, and explicitly spans its Name cell across the Name/blank/Milestones/Plan-dates columns (`grid-column: 2 / 6`) since a milestone only ever has a name to put in that whole span and a single column's width was truncating longer milestone names. The one exception to "every cell must be a real element" is the "No items yet" placeholder row, which overrides `grid-template-columns:1fr` inline to span the full width as a single cell rather than trying to fill every column with one string.

**There is no Notes field** — items used to have a free-text `notes` field shown in its own row column, removed entirely (data model, item modal, row column) since it wasn't earning its column's width. If it comes back, it should be a deliberate re-add, not a resurrected dead column.

**`.ws-section` never clips its own content (`overflow: hidden` was removed from it)** — the rounded-card look comes from rounding `.ws-section-header`'s top corners and `.ws-section-add`'s bottom corners directly, not from clipping the section box. A row wider than the section (more columns than fit at the current window width) stays reachable via `.main`'s own `overflow: auto` instead of being silently cut off — this was a real bug once: the Due/Actual columns added for milestones pushed Status/Actions past the section's clipped edge with no way to reach them. One of the 10 columns (the always-blank spacer) is deliberately kept narrow rather than removed outright, specifically to keep the row's total width comfortably under typical window widths so this scroll fallback rarely has to engage in practice — a second such column, an "Actual" placeholder that used to sit right after Plan-dates, was later removed entirely rather than just kept narrow, per an explicit user request ("remove column 6" — see "Column layout is a real CSS grid" above).

**`.item-row`/`.milestone-header`/`.milestone-sub-row` all use asymmetric padding — `20px` on the right, `14px` on the left** (`padding: 9px 20px 9px 14px` / `5px 20px 5px 14px` / `7px 20px 7px 14px`) — a user-reported fix: the trailing Actions column (and, in Review, the confirm/complete toggle sitting beyond it at `grid-column:11`) read as uncomfortably flush against the card's own right edge with the original symmetric `14px`. All three share the wider right value specifically because they share `--item-grid-cols` — changing just `.item-row` would have left milestone rows sitting a visible few pixels further right than their parent item's own row, breaking the "everything lines up" invariant the whole shared-grid design depends on (see "Column layout is a real CSS grid" above). Action Log inherits the same padding via its shared `.item-row` class, but its own trailing columns are a fully bespoke grid unrelated to `--item-grid-cols` — see "Action Log" below.

**Dates are editable directly on the row, not only via the item modal — with one deliberate exception.** An item's own Plan dates (`.item-dates-inline` — Start/Due as two date fields with a `→` between them, shown only when it has zero milestones — see "Item plan date range roll-up" below) and each milestone sub-row's Due/Actual dates all render through `dateInputHtml(value, attrs)` rather than formatted text. Their `onblur` (not `onchange`) calls `updateItemDateField(itemId, field, value)` / `updateMilestoneDateField(itemId, milestoneId, field, value)`, which write straight into the matching `items`/`milestones` entry and `save(); render()` — no modal round-trip needed for a quick date correction. `onblur` specifically, not `onchange`: Chrome fires `change`/`input` on a date input for every partial keystroke while a segment is still incomplete (`this.value` reads `''` until all three segments are filled), so `onchange` would save/re-render (destroying the focused input) after a single digit — `onblur` only commits once the user actually leaves the field. Both update functions additionally no-op (no save, no render, no history log entry) when the new value equals the field's current value, so a bare focus+blur that never actually changed anything — including revealing then abandoning an empty Actual ghost, see below — doesn't get recorded as a change. Neither update function touches `status` — date edits are orthogonal to the milestone-status roll-up. Start/Due don't accept an empty value (`onblur="if(this.value) ..."` guards the call) since a blank plan date isn't meaningful; Actual does accept empty (`this.value || null`) since clearing a previously-set actual date is a real, intentional action.

**The Start/Due `if(this.value)` guard used to leave an incomplete edit completely silent — a user-reported bug that read as spontaneous, unexplained data loss.** If a segment was left unfinished when the input blurred (`this.value` still `''`), the guard correctly skipped the write — but did nothing else either, so the input kept *displaying* whatever partial text had been typed, which looks exactly like a successfully saved edit. The real, unchanged stored date only resurfaced on the next unrelated `render()` (switching to Dashboard and back, cycling a milestone's status, anything that redraws the row from `items` again) — by then looking like the date had silently "reset itself" with no visible cause, rather than what actually happened: the edit never committed in the first place. Fixed by adding an `else this.value = '<the real stored date>'` alongside the existing guard on all three call sites (item Start, item Due, milestone Due — Actual is unaffected, since it already always commits via `this.value || null` rather than guarding on emptiness) — an incomplete edit now snaps the input back to the true value immediately on blur, visibly rejecting it right away instead of silently discarding it and letting a later, unrelated render "reveal" the loss.

**A second, separate bug shared the exact same "silent revert" symptom but a completely different cause, only found by reviewing a screen recording of it happening: picking a date from the native calendar popup (`showPicker()`, opened via the pill's own calendar icon) doesn't reliably fire this input's `blur` afterward.** The popup updates the input's own displayed value immediately (confirmed on video: the pill visibly showed the newly-picked date right away), but since `onblur` was the *only* handler that ever wrote a date into `items`/`milestones`, and it never ran, the edit was never actually committed — the display just happened to already show the right value, coincidentally, as an artifact of the native input's own internal state, completely independent of the app's data. This looked identical to the first bug (the edit "worked," then silently reverted on the next unrelated render — a mode switch, in the reported case) but survived the first fix untouched, since the value was never incomplete — it was complete and valid the whole time, just never delivered to the app. Confirmed directly: dispatching `input`+`change` on a date field's real DOM node with a complete value, *without ever dispatching `blur`*, left `items`/`milestones` completely unchanged — proving `onblur` alone isn't a reliable commit point regardless of the value's completeness. Fixed by adding `onchange="if(this.value) update...(...)"` (the same guarded call as `onblur`, minus the reset-on-incomplete `else`) to every date input in the app — item Start, item Due, milestone Due, and milestone Actual (the one field that didn't need the first fix still needed this one, since it has exactly the same picker-doesn't-blur exposure). `change` fires the moment the popup commits a value, regardless of whatever focus/blur quirk that popup has; `onblur` stays alongside it — it's still what a completed keyboard edit relies on when the user tabs/clicks away, and what resets an incomplete one back per the first fix above. Both functions already no-op when the incoming value equals the field's current one, so `onchange` and a later `onblur` both firing for the same edit is harmless, not a double-commit.

**Every inline date field renders as a "pill", not a bare `<input>`.** `dateInputHtml(value, attrs)` wraps a small calendar icon and the native `<input type="date" class="inline-date-input">` in one `.date-pill` span — this is the single place all of them are built, used identically for item Plan dates, milestone Due/Actual, and (disabled) the before/after pair in a review's change log. The input itself has no visible border/background of its own (the pill provides both); its own native calendar-picker icon is hidden (`::-webkit-calendar-picker-indicator { display: none }`) since the pill's own icon opens the picker instead (`showPicker()`, feature-detected and only wired to the icon specifically). Clicking anywhere else in the pill (its padding/gap, not just the narrow input) also focuses the input, via an `onclick` on the `.date-pill` span itself guarded to skip when the click landed on the `<input>` or `<i>` directly — this exists because `.inline-date-input`'s width is deliberately snug to its `DD.MM.YY` content (no dead trailing space), which leaves less native click-target room than the old wider box did. **Do not set `-webkit-appearance: none` on `.inline-date-input`** to try to shrink it further — it strips Chrome's segmented day/month/year keyboard editing entirely (typing one digit ends up committing/exiting instead of advancing to the next segment); sizing it via a plain explicit `width` is the only safe lever. None of this touches the date *text* itself, which a native `<input type="date">` always renders in whatever format the OS/browser locale uses (`DD.MM.YY` for this author) — only the surrounding chrome changed.

**An unset milestone Actual date starts hidden behind a muted "+" button (`.actual-date-ghost`), not an empty editable pill.** Actual is only meant to be touched when a milestone finishes on a different date than planned — an always-present empty date pill for the common case (finished on time, no override needed) read as a required field waiting to be filled in. `milestoneRowsHtml()` renders the ghost whenever `!m.actualDate && !revealedActualIds.has(m.id)`; clicking it calls `revealActualDate(milestoneId)`, which adds the id to `revealedActualIds` (module-level `Set`, UI-only, not persisted — mirrors `expandedItemIds`), re-renders, and focuses the now-real input (`id="actual-input-${m.id}"`). Pressing Escape while it's revealed but still empty calls `cancelRevealActualDate(milestoneId)`, which removes the id and re-renders back to the ghost, discarding whatever was mid-typed (nothing was saved yet — only `onblur` commits). That Escape handler is only wired up in the revealed-and-still-empty case (`isRevealedEmpty` in `milestoneRowsHtml()`) — once a real `actualDate` exists, the field is a genuine saved value, not a "reveal" state, so there's nothing to cancel back out of. `tests/harness.js`'s `resetState()` resets `revealedActualIds` between tests for the same reason it resets `expandedItemIds` — several test files reuse fixed milestone ids (`'m1'`, `'m2'`) across different tests, so a leaked reveal would silently affect an unrelated later test.

**Manual item order and drag-and-drop reordering.** Every item has an `order: Number`, assigned once at creation (`saveItem()`: `items.filter(i => i.workstreamId === workstreamId).length`, i.e. one past every existing item in that workstream — always the bottom of the list, regardless of due date) and otherwise touched only by dragging. `renderStatusView()`/`renderReview()` both sort by it (see above). The drag handle (`.drag-handle`, a small grip icon, `draggable="true"`) lives inside `.item-actions` next to Edit/Delete — same hover-reveal, same Planning-only gating (hidden during Review, since restructuring order isn't a review action). `.item-actions`'s hover-reveal toggles `visibility`, not `display` — it's always laid out (`display: flex` unconditionally) and only its visibility flips on `.item-row:hover`, specifically so the row never reflows the instant you hover it; toggling `display: none/flex` instead let the column claim its real width (three icon buttons) only on hover, shifting the row every time. `dragStartItem(e, id)` stashes the dragged id in `draggedItemId` (module-level, UI-only, mirroring `expandedItemIds`); the *row* itself (not just the handle) is the drop target (`ondragover`/`ondrop`), so dropping anywhere on a target row works, not just precisely on its own handle. `dropOnItem(e, targetId)` hands off to `reorderItem(fromId, targetId)`, which is a no-op across two different workstreams (dragging isn't how an item's workstream changes — that's still the item modal's job) and otherwise moves the dragged item to the target's position and reassigns clean, contiguous `order` values (`0,1,2,…`) to every item in that workstream — so `order` never needs a repair pass and always exactly matches array position once sorted. `normalizeData()` backfills a missing `order` (legacy data predating this field) from current array position per workstream, in a pass that runs *after* the orphaned-`workstreamId` reassignment above it, so a formerly-orphaned item is never counted against the wrong workstream's counter.

**Workstreams themselves are drag-and-drop reorderable in the shared sidebar (`renderSidebar()`/`#wsList`) — an explicit user request, mirroring items' own reordering above almost exactly.** Every workstream already had an `order: Number` (assigned at creation, `workstreams.length`, i.e. always the bottom of the list) and `normalizeData()` already re-sorted the array by it on every load — reordering just needed the drag interaction wired up, no new data-model work. `dragStartWs(e, id)`/`dropOnWs(e, targetId)`/`reorderWorkstream(fromId, targetId)` are `draggedItemId`/`dragStartItem`/`dropOnItem`/`reorderItem`'s counterparts, over `draggedWsId` and the flat `workstreams` array directly — there's no per-workstream "same group" guard the way items need `dragged.workstreamId === target.workstreamId`, since workstreams aren't nested inside anything else to stay grouped by; a drop just moves the dragged workstream to the target's position and reassigns clean, contiguous `order` values to the whole array, same "never needs a repair pass" reasoning as `reorderItem()`. The drag handle (`.ws-row-drag`, reusing the shared `.drag-handle` grip-icon class) sits right before `.ws-row-edit`, both hover-revealed the same way (`display: none` at rest, `.ws-row:hover` reveals both) and both gated to Editor+ — matching workstream CRUD's own tier, not a new one. Unlike `.item-actions`'s `visibility` toggle (chosen specifically so a *fixed-width* actions column never reflows the row on hover), `.ws-row-drag`/`.ws-row-edit` use plain `display: none`/`inline-flex`, since neither one reserves dedicated column width to begin with — there's no layout to preserve either way, they're just absent from flow until hovered. The drop target is the whole row (`ondragover`/`ondrop` on `.ws-row` itself), same reasoning as an item row's own: a much bigger, easier target than the grip handle alone. The "All workstreams" pseudo-row (`filterWorkstreamId === null`) has no `id` and isn't part of `workstreams`, so it never gets a drag handle or drop target at all — nothing to reorder relative to.

**An item's own `actualDate` is intentionally not shown or editable on the row at all** — only in the item modal. `itemRowHtml()`'s `actualDateHtml` is a plain empty `<span></span>` (a placeholder, not an omitted element — the "Actual" grid column is still real and meaningful for the milestone rows below it, just never populated by the item's own row). This was a deliberate simplification after the row briefly showed it as an always-present inline input (mirroring the milestone rows) — the item's own actual-completion-date is enough of an edge-case field, relative to the far-more-common per-milestone actual dates, that it didn't earn a permanent slot in the compact row view.

### IT/Business/Budget tags

Three item-level-only RAG flags — `itStatus`/`businessStatus`/`budgetStatus`, each one of `RAG3` (`['green','amber','red']` — no `not-started`/`complete` concept, unlike the main status). Rendered as icon-only badges (`fa-laptop-code`/`fa-briefcase`/`fa-euro-sign`, colored by the same `--stat-*` variables as the main status badge) in the item row's Tags column; clicking one calls `cycleItemAttr(itemId, field)`, which steps through `RAG3` and wraps — the same pattern as `cycleMilestoneStatus()` but scoped to a plain 3-value cycle instead of the full `STATUSES` list. These are item-only: `milestoneRowsHtml()` never renders them, and `ITEM_TAG_FIELDS` (top of the `<script>` block) is the single list normalizeData() walks to backfill any missing/invalid value back to `'green'`. A brand-new item gets its defaults at creation in `saveItem()`'s `else` branch (not as part of the shared `data` object also used for edits) specifically so re-saving an *existing* item through the modal — which never edits these fields — can't reset them back to green.

### External Delivery

**A plain boolean flag, `externalDelivery`, marking whether a scope item is delivered by an external party — an explicit user request — plus a conditional `externalDeliverySpoc` text field for that party's point of contact once the flag is on.** Unlike the IT/Business/Budget tags above, this is a modal-only pair, not a row-level badge: `itemModalBg` gets a plain checkbox (`#itemExternalDeliveryInput`) right before the Milestones editor, and a second field (`#itemExternalDeliverySpocField`/`#itemExternalDeliverySpocInput`) that only *shows* while the checkbox is checked — `onItemExternalDeliveryChange()` toggles its `display`, called both from the checkbox's own `onchange` and once at the end of `openItemModal()` so a reopened item starts in the right state. This mirrors the Not Applicable milestone pattern (a field only shown, not just disabled, while conditional on a flag) rather than the IT/Business/Budget tags' own always-visible-badge treatment, since a SPOC name has nowhere sensible to sit in the row's already-full grid the way a single RAG icon does — see "Column layout is a real CSS grid" above for why that grid resists casually adding another column.

`saveItem()` reads the checkbox directly into `externalDelivery`, and reads the SPOC input **only while the checkbox is checked** — `externalDeliverySpoc` is forced back to `null` the moment `externalDelivery` is unchecked and saved, the same "a field that's no longer applicable doesn't keep a stale value" stance Not Applicable milestones take with their own Due/Actual dates (see "Not Applicable milestones" below). Both fields live in the same shared `data` object every other directly-editable field does (unlike `itStatus`/etc. above, which are cycle-only and deliberately excluded from `data`) — a brand-new item and an edit to an existing one both go through the identical read/write path. `openItemModal()`/the `editable` disabling loop treat both new inputs exactly like every other field: seeded from the item (or blank/unchecked for a new one) and `.disabled = !hasRole('editor')`, so the modal stays viewable but not editable below Editor, same as everything else in it. `normalizeData()` backfills `externalDelivery` to `false` for legacy data missing the field, and self-heals `externalDeliverySpoc` back to `null` whenever `externalDelivery` is falsy (or the stored value isn't a string) — the same invariant `saveItem()` enforces on save, just also covering data that arrived from an older export, a hand-edited import, or a linked file predating this feature.

### Milestone checklist

A new item's milestone checklist is seeded from whichever **Category** is selected in the item modal (see "Categories (Admin mode)" below) — not a single fixed list. `milestonesForCategory(categoryId, dueDate)` builds a fresh `{id, name, dueDate, status}` array from `categoryById(categoryId).milestones` (plain name strings), each dated to the given due date and given its own freshly-generated `id`. `openItemModal(id)` seeds `editingMilestones` — a module-level working copy, not committed to `items` until Save — from `milestonesForCategory()` when creating a new item, or from a deep-ish copy of the existing item's `milestones` when editing one already saved. This is why editing never resets an item back to its category's template: `saveItem()` only ever writes whatever is currently in `editingMilestones`, regardless of how it originally got there.

The Category `<select>`'s `onchange` calls `onItemCategoryChange()`, which re-seeds `editingMilestones` from the newly-picked category — but only `if (!editingItemId)`. Switching category while *creating* an item is expected to reload the checklist to match (you haven't customized anything yet); switching it while *editing* an already-saved item must never silently discard whatever checklist customization is already in `editingMilestones` — `tests/cases/categories.test.js`'s "does nothing while editing an existing item" test guards this exact distinction. `DEFAULT_CATEGORIES` (top of the `<script>` block — an array of `{name, milestones}`, one entry per out-of-the-box category: Development, Artefact, Integration, Activity, content taken from `Milestone_Lookup_Table.xlsx`) is *not* a live default any more — it's only read once, by `normalizeData()`/`seedDefaults()`, to seed the categories a fresh install (or a pre-categories save) starts with, alongside the separately-seeded, reserved Pending category (see "Quick-add scope items, the Unassigned bucket, and the Pending category" below). `DEFAULT_CATEGORY_MILESTONES` is kept only as an alias for `DEFAULT_CATEGORIES[0].milestones` (Development's own template), for the handful of call sites/tests that only ever cared about "the first/default category's milestones" from back when Development was the only one seeded.

`renderMilestonesEditor()` redraws the modal's milestone rows from `editingMilestones`; each row's `name`/`dueDate`/`status` field writes straight back into `editingMilestones[idx]` via inline `oninput`/`onchange` (no re-render on keystroke, so inputs never lose focus mid-edit) — `saveItem()` reads the array directly rather than re-scraping the DOM. `removeMilestoneRow(idx)` is the only mutation that re-renders the editor, since that one's structural (row count changes, so every subsequent row's index shifts). None of this touches `items` until Save is clicked — Cancel (or closing the modal) just discards `editingMilestones`, which `closeItemModal()` also resets to `[]` for hygiene. **There used to be a matching `addMilestoneRow()`/"+ Add milestone" button here too, letting an existing item's checklist grow beyond its category's template — removed outright (an explicit user request), not hidden: the button, the function, and its test coverage are all gone.** A milestone can still be renamed, reordered, removed, or marked Not Applicable, and a brand-new item's checklist can still be reseeded by switching category *while still creating it* (`onItemCategoryChange()`) — but once an item is saved, its set of milestones is fixed at whatever the category template gave it minus whatever's been removed; there's no way back into the modal to hand-add one more. `updateItemStatusFieldMode()`'s own comment (below) previously cited `addMilestoneRow()` as the reason `#itemDueInput` stays kept in sync even while hidden — that's now `onItemCategoryChange()`'s own read of the same field, still a real, current reason, just a different call site.

**Delayed-milestone color coding on the status board's Due/Actual pills** (`milestoneRowsHtml()`, an explicit user request): this is a purely visual signal layered on top of a milestone's own hand-set `status` (RAG) field, not a replacement for it — a milestone can be "On Track" and still show a red Due pill if its target date has quietly slipped by. Two independent flags:
- `dueOverdue` — `!m.notApplicable && m.status !== 'complete' && m.dueDate && m.dueDate < todayStr()`, the exact same "overdue" definition the dashboard already uses for whole items (`renderDashboard()`'s `overdue` filter) — a milestone still open past its own Due date. Reads on the Due pill only; a Complete milestone is never flagged here regardless of how late it finished (see the next flag for that).
- `actualLate` — `!m.notApplicable && m.actualDate && m.dueDate && m.actualDate > m.dueDate && m.actualDate <= todayStr()` — the Actual date itself was recorded after the Due date, whether or not `status` was ever marked Complete. Reads on the Actual pill only. The `<= todayStr()` half is an explicit user request, added after the first cut flagged *any* Actual later than Due, including one still in the future: an Actual date is sometimes logged ahead of time (a planned completion date), and a plan that hasn't happened yet isn't a late finish — red is reserved for one that's already occurred. `<=`, not `<`, since an Actual date of today has by definition already happened (unlike `dueOverdue`'s own `<` on Due, where today's target hasn't necessarily passed yet).
  Both use the same red: `.date-pill.pill-overdue` (background/text recolored to `--stat-red`/`--stat-red-bg`, same palette as `.attention-tag.overdue` on the dashboard). `dateInputHtml(value, attrs, pillClass)` grew a third, optional parameter for this — every other call site (item Start/Due, the Minutes/Actions modal, a review-history before/after pair) just omits it and gets the plain pill, unaffected. During a review (`reviewCycle` passed in), Due renders as a read-only `<span class="item-dates-computed">` rather than a pill (see "Review mode" below) — `dueOverdue` still applies there too, just as a plain inline `color:var(--stat-red)` on that span instead of the `pill-overdue` class, since there's no pill to attach it to. A `notApplicable` milestone is excluded from both flags outright, matching every other "notApplicable freezes/ignores this field" convention on this row (see the Status badge and Due-cell comments just above).

### Item status roll-up

An item's `status` is **computed, not hand-set, whenever it has at least one milestone** — `computedStatusFromMilestones(milestones)` picks whichever milestone ranks worst by `STATUS_SEVERITY` (`{red:0, amber:1, green:2, 'not-started':3, complete:4}`, lower = worse/weaker) and that becomes the item's status. This is a deliberate reversal of an earlier design (previously documented here as "no roll-up, status is always manual") — the product call was that a checklist item at Red should always be visible at the parent level, not silently masked by a manual status someone forgot to update.

The severity order is *not* the same as `STATUSES`' display order: `not-started` ranks near the *best* end (better than Green, worse only than Complete) rather than at the start — the reasoning is that "hasn't started yet" needs no attention the way an active Amber/Red does, so it shouldn't drag an otherwise-on-track item's rollup down the way a genuinely active problem should. Only Green/Amber/Red (milestones someone is actively tracking) can make an item look worse than "nothing to report yet."

**An item with zero milestones keeps a manual status** — there's nothing to compute from, so `computedStatusFromMilestones([])` returns `null` and callers fall back to whatever's hand-picked. Three places enforce/apply the rule, all calling the same helper so the logic lives in exactly one spot:
- `saveItem()`: `milestones.length ? computedStatusFromMilestones(milestones) : <Status select's value>`.
- `cycleMilestoneStatus()`: recomputes `it.status` immediately after changing one milestone's status, so the item row's badge is never stale even without reopening the modal.
- `normalizeData()`: recomputes `it.status` for every item with milestones on every load/merge/import — this is what self-heals a manual status saved before this rule existed, or one arriving from an external file that predates/ignores it, and is the actual source of truth the other two are just keeping in sync ahead of the next `normalizeData()` pass.

**The item modal's Status field switches between an editable `<select>` and a read-only computed badge**, live, based on whether the item currently has milestones — never both at once. `updateItemStatusFieldMode()` (name predates the date-range roll-up below, which it now also drives — see there for why it wasn't split into two functions) toggles `#itemStatusSelect`/`#itemStatusComputed`'s `display` and, in the computed case, fills `#itemStatusComputedBadge` from `computedStatusFromMilestones(editingMilestones)` (the in-progress working copy, not yet saved). It's called from `renderMilestonesEditor()` (covers modal-open, add-row, remove-row — anything that changes the milestone *count*) and separately from each milestone row's status `<select>` `onchange` (a status *change* without a count change, which wouldn't otherwise trigger a re-render). Since it only ever reads `editingMilestones` and writes a few small DOM nodes, it's cheap enough to call defensively from several places rather than trying to track more precisely which one actually changed.

### Item plan date range roll-up

An item's plan date range (`startDate`/`dueDate`) is **computed from its milestones whenever it has at least one**, the same "reversal of an earlier manual-only design" as status above and for the same reason — a milestone that slipped shouldn't be silently invisible at the parent level because nobody went back and adjusted the item's own dates by hand. `computedDateRangeFromMilestones(milestones)` returns `{startDate, dueDate}` spanning the earliest to the latest date across *every* milestone's `dueDate` **and, when set, its `actualDate`** — considering actual dates too means a milestone that actually finished earlier or later than planned widens the item's range to match reality, not just what was originally scheduled. Returns `null` for an empty list, same convention as `computedStatusFromMilestones`.

**An item with zero milestones keeps a manual date range** — same fallback pattern as status. The same three call sites keep it in sync, plus one more that status doesn't need:
- `saveItem()`: `milestones.length ? computedDateRangeFromMilestones(milestones) : <manual Start/Due inputs>`.
- `updateMilestoneDateField()`: recomputes `it.startDate`/`it.dueDate` immediately after a milestone's due or actual date changes inline on the status board — a milestone's date is exactly the kind of edit that can happen without ever opening the item modal (see "Status board" above), so this can't wait for `saveItem()`.
- `applyCategoryMilestoneSync()`: a category sync can add or remove milestones on an item without the item modal ever opening, so it recomputes the range (alongside status) right after mutating `it.milestones`.
- `normalizeData()`: recomputes on every load/merge/import, self-healing legacy/stale values — the actual source-of-truth pass the other three are just keeping ahead of.

**Both the item modal and the status-board row hide manual date editing once milestones exist**, mirroring the Status field exactly: `#itemDatesManual` (the Start/Due `<input>` pair) and `#itemDatesComputed` (a read-only badge + explanatory note) toggle together with `#itemStatusSelect`/`#itemStatusComputed` inside the same `updateItemStatusFieldMode()` — which is why that function wasn't split in two despite the name; Status and Plan-dates always change computed-vs-manual mode in lockstep, driven by the same "does this item have milestones" check. The function also keeps the (possibly hidden) `#itemStartInput`/`#itemDueInput` values in sync with the live-computed range, since `onItemCategoryChange()` still reads `#itemDueInput`'s value when re-seeding a still-being-created item's milestones from a newly-picked category. On the status board itself, `itemRowHtml()`'s `planDatesHtml` renders `.item-dates-computed` (plain text, a tooltip explains it's derived) instead of the editable `.item-dates-inline` pair whenever `it.milestones.length > 0` — the item's own separate `actualDate` field (see "Data model" above — a distinct concept from the plan range) stays independently editable on the row regardless, since it was never part of what's being computed here.

### Not Applicable milestones

**A milestone can be marked Not Applicable — an explicit user request ("in planning view, allow setting a milestone to not applicable") — via a standalone `notApplicable: Boolean` field, independent of `status`, not a 6th value added to `STATUSES`/the status click-cycle.** Two interaction models were considered and discussed with the user up front: extending the existing status cycle (reusing the exact click-to-cycle pattern already used everywhere, but adding an occasional-use value to a rotation optimized for the common 5), versus a separate toggle that leaves that cycle completely untouched. The user picked the separate toggle, specifically to avoid diluting the fast, frequent status-cycling interaction with a 6th stop most clicks would never want. Keeping it a boolean rather than a status value also means the milestone's own `status` is *preserved*, not reset, while marked Not Applicable — `toggleMilestoneNotApplicable()`/`toggleEditingMilestoneNotApplicable()` never touch it — so un-marking restores whatever it was before, rather than snapping back to "Not Started".

**Excluded from every roll-up a milestone would otherwise feed into** — the same "never counts toward or against anything" treatment applied everywhere it's relevant:
- `computedStatusFromMilestones(milestones)` filters `notApplicable` milestones out of the weakest-link reduce entirely. If literally every milestone on the item is marked Not Applicable, there's nothing left to reduce over, but the item still *has* milestones (so its Status field must stay in computed mode, never reverting to manual) — `'not-started'` is the fallback there, same neutral value a brand-new milestone already starts at. A genuinely empty list (no milestones at all) still returns `null`, unchanged from before this existed.
- `computedDateRangeFromMilestones(milestones)` excludes a Not Applicable milestone's `dueDate`/`actualDate` from the earliest/latest scan — its date shouldn't stretch the item's displayed plan range for something that was never really going to happen. Returns `null` if every milestone is excluded (same as an empty list); callers (`updateMilestoneDateField()`, `saveItem()`, `applyCategoryMilestoneSync()`, `normalizeData()`) already treat a `null` range as "leave the existing dates alone", so this needed no changes at any of those call sites.
- `itemRowHtml()`'s "X/Y milestones" badge counts only applicable milestones on **both** sides of the fraction (`applicableMilestones = it.milestones.filter(m => !m.notApplicable)`) — counting a Not Applicable milestone in the denominator would make 100% permanently unreachable, and counting it as done would overstate real progress. The chevron/expand toggle and `total` (used for that, and for whether Plan-dates render as computed at all) deliberately stay keyed off the *real*, unfiltered milestone count — an item whose milestones are all Not Applicable must still be expandable, so any of them can be reached and un-marked; the badge just renders empty in that edge case, same as having zero milestones at all.
- `renderDashboard()`'s `milestones` (feeding completion %, the per-workstream summary rows, and the Overdue/Upcoming feeds) is filtered to exclude `notApplicable` right where it's first assembled from `allMilestonesFlat()`, so every downstream calculation inherits the exclusion for free rather than needing its own filter.
- `isItemConfirmedInCycle(cycle, it)` filters to `applicable = it.milestones.filter(m => !m.notApplicable)` before checking "every milestone confirmed" — a Not Applicable milestone can never be the thing blocking an item from reading as confirmed. If `applicable` is empty (every milestone Not Applicable) `applicable.every(...)` is vacuously `true` — confirmed by default, matching "nothing left here that needs reviewing" — and deliberately does **not** fall through to the item's own direct `cycle.confirmations` the zero-milestone case below it uses, since nothing ever writes an entry there for an item that still has real milestones (see `itemRowHtml()`'s `reviewCellHtml`, which always wires an all-N/A item's button to `toggleConfirmAllMilestones()`, never `toggleReviewConfirm()`). `toggleConfirmAllMilestones()` mirrors this: it operates only on `applicable`, and is a no-op (not a 0-length push/splice) when `applicable` is empty. `milestoneRowsHtml()`'s own per-milestone confirm cell renders an inert `fa-ban` placeholder instead of a real `.review-confirm-toggle` for a Not Applicable milestone during a review — not omitted (same column-collapse reason as everywhere else), just never a toggle, since there's nothing to confirm.

**UI, in both the places the user asked for** (status board row + item modal's milestone editor):
- `milestoneRowsHtml()` places the toggle immediately *after* the Status badge — the order was swapped (N/A before Status) and then swapped back again, both times per user request, so this is back to the original Status-then-N/A order — inside one shared `.milestone-status-cell`, a CSS Grid spanning **both** of the row's trailing tracks (`grid-column:9/11` — the Status track at 90px plus the Actions track at 56px, 146px combined) rather than each control claiming a whole track of its own. That combined cell followed a separate user report ("the n/a column is to broad... make it as small as possible"): giving the icon-only toggle its own full 90px track (sized for Status's text label, e.g. "Off Track") left it visibly stretched/floating in mostly-empty space no matter how it was aligned *within* that track, since the track's own width doesn't shrink to content — a `justify-self` tweak was tried first and rejected for exactly that reason (it only repositions content inside a still-90px box, it can't shrink the box). The cell's own internal grid (`grid-template-columns: 92px auto`, see below) sizes the toggle tight against its fixed-width first column instead, so it stays put regardless of which one comes first — that ordering question and the "make the track fit the content" question turned out to be independent, which is why swapping the order back again didn't need to touch the sizing fix at all. `milestoneHeaderHtml()`'s own "Status"/"MS Req." labels (the header's text for the Not Applicable toggle's column was renamed from "N/A" to "MS Req." — a later, purely cosmetic user request; the toggle itself, its function name, and the frozen "N/A" status-badge text it produces are all unchanged) share the identical `grid-column:9/11` cell, for the same reason a header label and the data beneath it losing sync would misalign the same way an omitted cell would (see "Column layout is a real CSS grid" above) — and neither of these spanning cells touches `itemRowHtml()`, which still separately auto-places its own Status(9)/Actions(10) content untouched, so nothing here affects the item row's own column widths. (These grid-column numbers shifted down by one — from `10/12` and `9`/`10` respectively — when the grid's old "Actual" placeholder column was removed outright per a later user request; see "Column layout is a real CSS grid" above.) The toggle always renders an icon (`fa-regular fa-ban` off, `fa-solid fa-ban` on, colored `var(--stat-not-started)` when on) rather than being omitted when off — the same "always a real, visible icon, just not clickable below the gating role" convention `.review-confirm-toggle` already uses — clickable only at Editor+ (`toggleMilestoneNotApplicable(itemId, milestoneId)`, `requireRole('editor')`-guarded, direct-to-data + immediate `save()`/`render()`, same shape as `cycleMilestoneStatus()`). `renderMilestonesEditor()`'s own row in the item modal mirrors the same order (Status then N/A, next to Remove) for consistency between the two places this toggle lives.
- While on: the status badge freezes to a plain grey "N/A" (not whatever RAG color `m.status` still holds underneath — showing e.g. "Off Track" and "Not Applicable" at once would read as contradictory rather than "this one's on hold") and is no longer clickable/cycleable; the milestone name mutes (`opacity:.55`); Due and Actual date **values are cleared outright** — a second explicit user request ("if i switch a task to n/a, remove due date and actual date"). `toggleMilestoneNotApplicable()` sets `m.dueDate = null; m.actualDate = null` the moment it's turned on; un-marking does **not** try to restore whatever they were — they stay blank, so a milestone brought back into scope gets a deliberate fresh date rather than an easy-to-miss stale one. This is one of only two fields Not Applicable actually mutates (`status` is the other kind of field — deliberately preserved, not touched, per above); everything else about the milestone (name, id) is untouched.
- **`milestoneRowsHtml()`'s Due cell collapses to a genuinely empty element (not a disabled-but-still-visible pill) whenever `m.notApplicable`** — a third user report, pointing out the inconsistency directly against Actual: a disabled icon+`"tt.mm.jjjj"`-placeholder pill still *read* as a real, if inert, field for a value that's deliberately gone, unlike Actual, which already collapses to nothing once it has nothing to show (the ghost "+" only appears when *editable and empty* — see below). Due now takes the same branch structure Actual's own emptiness check does, just unconditional on `m.notApplicable` rather than on the date being merely absent — because normally toggling *always* clears `dueDate` to `null` in the same breath, the two conditions coincide for anything actually toggled through the UI. They can still diverge for a milestone whose `notApplicable`/dates were set directly (an import, a hand-edited file) rather than through the toggle — Due hides unconditionally regardless of what `dueDate` happens to hold, while Actual only hides when it's genuinely empty, so a leftover non-null `actualDate` on such a record still renders as a disabled pill. This wasn't requested to be equally strict, so it wasn't changed to match.
- Clearing `dueDate` needed two follow-on fixes, since a milestone's `dueDate` had never been nullable before this: `normalizeData()`'s `if (!m.dueDate) m.dueDate = it.dueDate` backfill (meant for a genuinely missing/legacy value) would otherwise silently refill a deliberately-cleared one on the very next load — now gated on `&& !m.notApplicable`. `saveItem()`'s milestone mapping (`dueDate: m.dueDate || manualDueDate`, meant so an *applicable* milestone never ends up dateless) would do the same thing on Save via the item's own manual Due input — now conditioned on `m.notApplicable` to skip that fallback entirely for a Not Applicable row.
- The item modal's `renderMilestonesEditor()` mirrors all of this on the detached `editingMilestones` working copy (not committed until Save): the status `<select>` swaps for the same frozen "N/A" label while on, Due/Actual disable, and the toggle button (`toggleEditingMilestoneNotApplicable(idx)`) sits right after the status field, before Remove — matching the status board's own Status-then-N/A order. `toggleEditingMilestoneNotApplicable()` clears `dueDate`/`actualDate` the same way `toggleMilestoneNotApplicable()` does. Toggling triggers a full `renderMilestonesEditor()` re-render (unlike a plain name/date/status edit, which just writes the value and calls `updateItemStatusFieldMode()`) since the row's own markup shape changes here — the `<select>` becomes a `<span>` or back.
- **`.milestone-status-cell` is a CSS Grid, `grid-template-columns: 92px auto`, not a flex box** — a fixed-width first column is what keeps the N/A toggle sitting at the same x position regardless of "Complete" vs "Not Started" (this cell's shortest and longest labels), a user-reported alignment complaint (without a fixed width, a flex/grid child sizes to its own text, so the toggle would sit at a different x position row to row). An earlier version put that same 92px as a `min-width` on the first *child* itself (the `.status-badge` pill, plus `text-align:center`/`white-space:nowrap`) rather than on the column — which fixed the N/A alignment, but stretched the milestone pill itself to fill 92px, making it visibly bigger than the item row's own (unconstrained, content-sized) status pill — a second, later user-reported complaint ("status pills for scope item and milestone have different sizes"). Reserving the width on the *grid column* instead (`.milestone-status-cell > :first-child { justify-self: start }`, no forced width on the child) keeps every status pill the same size everywhere it appears, just positioned within its reserved 92px slot — which also means `milestoneHeaderHtml()`'s "Status" label sits in the exact same slot the pill below it does, so the header and the data stay visually locked together horizontally, not just column-aligned. `justify-self` here was briefly `center` (a matching user request to center Due/Actual/Status/N/A headers over their columns), then reverted back to `start` along with Due/Actual's own header alignment once the user asked for every header in this table to go back to left-aligned — the two values were swapped in lockstep both times, since the header and data row share this one rule by design (see the comment on the rule itself for why they can't be split apart without reintroducing the original misalignment bug).
- Both toggles are logged to the active review cycle's change log the same way a status change is (`logReviewChange()`), just as plain text ("Marked as Not Applicable" / "Marked as Applicable again") rather than a structured `statusChange`/`tagChange`/`dateChange` — `reviewHistoryRowHtml()` already falls back to plain text for any entry without one of those three shapes, so nothing there needed to change.

`milestonesForCategory()` (seeding a new item's checklist from its category template), `applyCategoryMilestoneSync()` (adding milestones on template sync), and `openItemModal()`'s existing-item seeding path all construct fresh milestone objects with `notApplicable: false` explicitly — every place in this file that builds a milestone object needed this field added, not just the toggle functions themselves.

### Modals

Eight modals share the `.modal-bg` pattern (add `.open` class to show, remove to hide): `wsModalBg` (create/edit a workstream, with a delete button that cascades to that workstream's items — and, since milestones live nested inside items, to their milestones too), `itemModalBg` (create/edit a scope item, `.modal-wide` at 520px to fit the milestones editor — see "Milestone checklist" above), `categoryModalBg` (create/edit an Admin-mode category and its milestone template — see "Categories (Admin mode)" below), `confirmModalBg` (generic confirm-then-run-a-callback, used by every delete, by restore-from-backup, and by cancelling a review cycle — see "Deletion tombstones and undo" below), `importModalBg` (merge vs. replace choice after picking a file), `backupsModalBg` (list + restore local daily snapshots), `fileSyncModalBg` (onboarding/reconnect for the linked-file feature), and `backupFolderModalBg` (the second step of that same launch-time onboarding sequence — see "Launch-time onboarding" under "Daily backups to a linked folder" below). All eight close on Escape and on a background click (listeners near the end of the `<script>` block check `e.target.id`) — the one exception elsewhere in this file is `scopeAssignModalBg`, deliberately excluded from both, since it has no dismiss path at all (see its own section above).

### Data integrity

`normalizeData()` (called from `load()`, from every merge/import/file-sync entry point, and, for tests, from the `resetState()` glue) is the single source of truth for schema defaults: workstream `id`/`color`/`order` backfilled and the array re-sorted by `order`; an item's `id`/`name`/`owner`/`status`/`updatedAt`/`itStatus`/`businessStatus`/`budgetStatus` backfilled, `order` backfilled from current array position per workstream (a separate pass, after `workstreamId` reassignment below so it's never keyed by a stale one — see "Manual item order and drag-and-drop reordering"), an orphaned/stale `workstreamId` (pointing at a workstream that no longer exists) reset to `null` — Unassigned, same as an item deliberately created that way (see "Quick-add scope items, the Unassigned bucket, and the Pending category" below) — rather than an arbitrary real workstream, so a broken reference surfaces for triage instead of silently landing wherever `workstreams[0]` happens to be; an orphaned/missing `categoryId` reassigned to the first category, a missing `startDate` defaulted from `dueDate`, a non-string `actualDate` defaulted to `null`, a missing `milestones` defaulted to `[]`, and each milestone's own `id`/`name`/`status`/`actualDate`/`notApplicable` backfilled (`false` for `notApplicable` — see "Not Applicable milestones" below) and a missing `dueDate` defaulted from its *parent item's* `dueDate` — then, once milestones are backfilled, any item with `milestones.length > 0` has its `status` recomputed via `computedStatusFromMilestones()` regardless of whatever value was saved (see "Item status roll-up"). A stale `filterWorkstreamId` (the one selector shared by Planning/Review/Dashboard — see "The shared workstream selector" above) is cleared if it no longer resolves, a stale/invalid `mode` falls back to `'planning'` (checked against the `MODES` array), and — since Review mode requires a specific workstream — `mode` additionally falls back to `'planning'` if it's `'review'` with no `filterWorkstreamId` selected. `deletedWorkstreamIds`/`deletedItemIds` are coerced to arrays and filtered to well-formed `{id, ...}` entries; `categories` and `reviewCycles` get the same array-coercion, and every category's own `id`/`name`/`milestones`/`order` is backfilled the same way a workstream's is. **If `categories` ends up empty** (a pre-categories save, or every category somehow got deleted), `normalizeData()` reseeds the whole out-of-the-box set — `DEFAULT_CATEGORIES` (see "Quick-add scope items, the Unassigned bucket, and the Pending category" below for where that constant comes from) — this is also how a pre-categories item picks up a valid `categoryId` on first load after the upgrade, since the orphaned-`categoryId` backfill runs after categories are guaranteed non-empty. Review cycles get `id`/`startedAt`/`completedAt`/`cancelledAt`/`confirmations`/`milestoneConfirmations` backfilled but are otherwise left alone — there's no cross-referential repair needed since a cycle referencing a since-deleted workstream is simply unreachable through the shared sidebar (which only lists live workstreams), not actively cleaned up; see "Review mode" below for why that's the deliberate choice rather than an oversight.

It also runs a one-time schema migration: a pre-nested-milestones save could have a top-level item with `type: 'milestone'` (milestones used to be their own top-level item, siblings of scope items, before this became a nested checklist). Rather than silently dropping these on first load under the new schema, `normalizeData()` folds each one into its own new single-milestone item (`startDate`/`dueDate` both set to the old milestone's `dueDate`, `milestones: [{ ...that one milestone }]`) and strips the legacy rows out of `items`. `type` itself is `delete`d off every item as part of this pass, since it no longer means anything under the new schema.

**Every place that assigns `workstreams`/`items` from an external source calls `normalizeData()`, not just `load()`** — the current call sites are `load()`, both branches of `applyImport()`, `restoreBackup()`, `linkFile()`'s merge-on-first-link branch, `reconnectFile()`, and `initFileSync()`. If you add another data-loading path (e.g. a new sync mechanism), route it through `normalizeData()` too, or you'll reintroduce the exact bug class this fixed — a render function assuming a field exists that an older/hand-edited/externally-sourced save doesn't have.

`normalizeData()` is also the security boundary for ids: every workstream/item/milestone id is interpolated unescaped into `onclick` HTML attributes at render time (`esc()` only covers *content* fields — name, owner — never `id`). That's fine for locally-created data since `genId()` only ever produces plain alphanumeric strings, but `mergeData()` and `applyImport('replace')` trust ids from an external `.json` file as-is. `isSafeId(id)` (`/^[a-zA-Z0-9_-]+$/`) plus the per-entity checks in `normalizeData()`'s three loops (workstreams, items, milestones) regenerate anything that couldn't have come from `genId()`, closing that off at the one place every external-data path already routes through — see `tests/cases/sync.test.js`'s "regenerates a workstream/item/milestone id" tests.

## Data durability

Pulse now matches PromptLab/mytasks' full data-durability feature set: JSON export/import, rolling local backups, deletion tombstones with toast undo, and optional File System Access API file sync. The "Data" dropdown in the topbar (`toggleDataMenu()`/`closeDataMenu()`, closed by the document-level click listener when a click lands outside `#dataDropdown`) is the entry point for Export, Import, and Backups. File sync deliberately has no entry there — see "File System Access API sync" below for why it lives entirely in the topbar's `#fileSyncIndicator` instead.

### Toast with undo

`showToast(msg, isError, undoAction)` — the third argument is new. When present, the toast shows an "Undo" button (`#toastUndoBtn`) and stays up 6s instead of 2s; `triggerToastUndo()` (wired to the button's `onclick`) invokes it and dismisses the toast immediately. Only one undo action is live at a time (`toastUndoAction`, a single module-level slot) — showing any other toast overwrites it, matching the single visible toast.

### Confirm modal — replaces native `confirm()`

`openConfirmModal({title, body, action, confirmLabel})` / `confirmModalAction()` / `closeConfirmModal()` replace the plain `window.confirm()` dialogs earlier versions used for delete. `modalTarget = {action}` holds the pending callback; clicking the modal's action button (`#confirmModalActionBtn`) runs it and closes the modal. This exists specifically so confirmations can describe *what* will happen (e.g. cascade counts) and hand off into the undo-toast flow below, which a same-tick `confirm()` return value can't do.

**`confirmLabel` defaults to `"Delete"`** — this one shared modal backs every confirm-then-act flow in the app, not just deletes (cancelling a review cycle, restoring a backup, applying a category's milestone-template sync to its items), and for a while those non-delete callers didn't override it, so the button read "Delete" for an action that wasn't a delete at all — confusing enough that a user reported a category-sync as "not working" when they'd likely declined it via a button that looked like it would destroy something. Every caller whose action isn't literally a delete now passes an explicit `confirmLabel` (`'Cancel Review'`, `'Restore'`, `'Apply Changes'`) — `tests/cases/*.test.js` assert the label alongside each of those flows specifically to keep this from silently regressing back to "Delete" if a new confirm-gated action gets added without one.

### Deletion tombstones and undo

`deletedWorkstreamIds`/`deletedItemIds` (each `{id, deletedAt}[]`) record "this id used to exist and was intentionally removed" — without them, an id absent from `workstreams`/`items` is indistinguishable from an id a merge has simply never seen, and a stale copy from an old linked file or import could silently resurrect something the user deleted on purpose. `tombstone(list, id)`/`untombstone(list, id)` add/remove an entry.

`deleteItem(id)` opens the confirm modal; its `action` splices the item out, tombstones it, then calls `showToast('Item deleted', false, undoFn)` where `undoFn` untombstones it and splices it back to its original index. `deleteWorkstreamFromModal()` does the equivalent at cascade scale: it snapshots the *entire* `items` array (`items.slice()`) before filtering out the workstream's items, tombstones the workstream id plus every removed item id, and its undo callback restores both the workstream (spliced back to its original index) and the whole pre-delete `items` array in one assignment — simpler and equally correct compared to tracking each removed item's individual original index. The undo callback must clear the tombstone(s) it set, or a delete-then-undo would leave the workstream/item permanently un-mergeable from any linked file/import that still has it.

**`deleteItem(id)` allows deleting a still-Pending (Unassigned) item, same as any other** — an explicit user request. An earlier version of this function refused outright (a toast, the confirm modal never even opening) for a Pending-category item, on the reasoning that one still waiting on real triage (see "Quick-add scope items, the Unassigned bucket, and the Pending category" below) shouldn't be able to just disappear before that triage happens; a later, separate user request reversed that, so a not-yet-triaged item now goes through the exact same confirm-modal-and-undo-toast flow as everything else. Both places `deleteItem()` is reachable from — the row's own trash icon (`itemRowHtml()`'s `.item-actions`) and the full edit modal's Delete button (`deleteItemFromModal()`) — funnel through this one function, so this applies to both without a second check anywhere else.

### Merge and last-write-wins

`mergeData(data, opts)` is the additive merge used by every "read data from outside `localStorage`" path (`linkFile()`, `reconnectFile()`, `initFileSync()`, `doFileSyncWrite()`'s cross-tab-conflict branch, `pollFileSync()`, and `applyImport('merge')`). It merges incoming tombstones first (union by id, keeping the later `deletedAt`, now covering `deletedWorkstreamIds`/`deletedItemIds`/`deletedMilestoneIds`), then workstreams *and* categories (both additive, deduped by id *or* case-insensitive name, merged silently — not counted in the return value, mirroring how mytasks' projects merge), then review cycles (additive by id only, no dedup-by-name since they're anonymous history rather than named entities — an id that already exists locally is left untouched rather than overwritten, since a cycle is meant to be append-only), then items. Returns `{added, updated, conflicts}` — `conflicts` is covered under "Conflict detection" below.

**An existing item's milestones and its own scalar fields (name/owner/status/dates/tags) merge independently of each other**, not as one all-or-nothing snapshot. `mergeMilestonesArray(existingList, incomingList, respectTombstones)` merges the `milestones` array by milestone `id`: an incoming milestone with a newer `updatedAt` than its local counterpart replaces it; one whose id isn't found locally is appended (tombstone-gated the same way items are, via `deletedMilestoneIds` — see below); one absent from the incoming list simply isn't touched (mirroring how a remotely-deleted *item* also isn't actively removed locally — see the next paragraph). Only *then* does `mergeData()` decide the item's own scalar fields, comparing the item's own top-level `updatedAt` (`Object.assign`-ing everything except `milestones`, which was already handled). This split is what lets two people editing *different* milestones on the same item — or one editing a milestone while another renames the item — both keep their change, instead of whichever side's `updatedAt` happened to be newer winning the entire item, milestones included. Each milestone carries its own `updatedAt`, stamped wherever its content actually changes: `updateMilestoneDateField()`/`cycleMilestoneStatus()` (direct row edits), `saveItem()` (see `stampChangedMilestones()` below), and `applyCategoryMilestoneSync()` for a freshly-appended one. `normalizeData()` backfills a missing `updatedAt` (legacy data) from the *parent item's* `updatedAt`, not `Date.now()` — see its own comment for why arriving-late data shouldn't look freshly edited to a merge just because this device happened to load it first.

**`stampChangedMilestones(newList, prevList)`** (used only by `saveItem()`) is what keeps the modal save from defeating the point of the above: the modal edits a detached working copy (`editingMilestones`) and writes the *whole* array back on Save, so naively stamping every milestone's `updatedAt` there would make an untouched milestone look freshly edited to a later merge — silently outranking a genuine edit someone else made to it elsewhere in the meantime. It diffs each new milestone's `name`/`dueDate`/`status`/`actualDate`/`notApplicable` against the item's current (pre-save) copy and only bumps `updatedAt` for the ones that actually changed; unchanged ones keep their prior timestamp exactly. A milestone present in the item before the save but missing from the new list was removed in the modal, and gets tombstoned into `deletedMilestoneIds` (same shape as `deletedItemIds`) so a merge can't resurrect it from a stale external copy. `applyCategoryMilestoneSync()` follows the same rule at the template-sync level: a newly-appended milestone gets `updatedAt: Date.now()`, and every milestone removed by the sync (this is the destructive add/remove path, not the reorder-only one) is tombstoned the same way.

Inside the items pass, a tombstoned incoming id is skipped *unless* the incoming `updatedAt` is newer than the tombstone's `deletedAt` — that case is treated as a genuine edit made elsewhere after the local delete, and the stale tombstone is cleared to let it back in. Workstreams have no `updatedAt` (see "Data model" above), so a deleted workstream has no such escape hatch inside `mergeData()` itself — the only way one comes back is through `opts.respectTombstones: false` (below). **Note this same limitation applies to items and milestones too, one level up**: `mergeData()` merges the *tombstone lists* themselves (so the deletion is now known locally), but never actively removes a locally-existing item/milestone just because an incoming file's tombstone says it was deleted elsewhere — it only ever *prevents re-adding* something already known to be deleted. A device that already had the item/milestone before the remote deletion keeps its own copy until it independently deletes it too. This is a pre-existing, accepted scope limit, not something the per-milestone merge work changed.

### Conflict detection

`lastSyncedAt` (module-level, starts at `0`, reset to `0` whenever the file link is cleared) is the merge "base" — the last time this browser is known to have successfully reconciled with the linked file (a link, reconnect, write-time merge, or background poll). `mergeMilestonesArray()`/`mergeData()` use it to tell a *genuine* concurrent edit apart from "their copy just happened to be newer": an item or milestone only counts as conflicting if **both** sides' `updatedAt` are newer than `lastSyncedAt` — i.e. both were touched since the two sides last agreed. `lastSyncedAt === 0` disables this entirely, which matters specifically for the very first merge against a freshly-linked file: with no prior sync, "since the last sync" has no meaning yet, and everything existing locally would otherwise look freshly edited relative to a base that never happened. Conflict detection is deliberately per-milestone-id, not "did anything change on each side of the whole array" — two *different* milestones each independently edited on their own side merge cleanly and are correctly not a conflict, even though naively checking "something changed on both sides" for the array as a whole would say otherwise (a bug caught in the test that specifically distinguishes the two).

Detecting a conflict never changes how it's resolved — the merge above already picked a winner (newer `updatedAt`, per-item or per-milestone) regardless. `conflicts` (an array of `{itemName, milestoneName, note}`) is purely a plain-English audit trail so "resolved automatically" doesn't also mean "invisibly": `reportSyncConflicts(conflicts)` appends timestamped entries to `syncConflictLog` (module-level, session-only — not persisted, since this is a heads-up for whoever's at the keyboard right now, not permanent history), shows a toast with a "Review" action (see `showToast()`'s generalized `actionLabel` param below), and updates a small amber badge next to `#fileSyncIndicator` (`updateSyncConflictsUI()`) that stays up for as long as anything is unreviewed, since the toast itself is easy to miss. `openSyncConflictsModal()`/`closeSyncConflictsModal()`/`renderSyncConflictsModal()`/`clearSyncConflictLog()` follow the same open/render/close pattern as the Backups modal. `showToast(msg, isError, undoAction, actionLabel)` gained the 4th parameter for this — every other caller omits it and keeps the original "Undo" label; conflicts is the one case where that label would be a lie about what the button does.

**The one exception: `applyImport('merge')`.** `mergeData()` defaults `opts.respectTombstones` to `true`; `applyImport('merge')` is the only caller that passes `false`. Picking a specific file and clicking Import → Merge is a deliberate, one-off action — unlike `linkFile()`/`reconnectFile()`/`initFileSync()`/`doFileSyncWrite()`, which merge automatically in the background, where silently resurrecting a deletion via a stale copy would be surprising. With the flag off, a matching tombstone is cleared and the incoming item (or workstream) is added regardless of relative timestamps.

### Export / Import

`downloadData(data, filename)` is the shared primitive (Blob → object URL → synthetic `<a download>` click). `exportProgramme()` calls it with `currentExportPayload()` (`{version, exported, programme, workstreams, items}` — deliberately no tombstones, same reasoning as PromptLab/mytasks' export format). `triggerImport()` clicks the hidden `#fileInput`; `handleFileImport(event)` reads the picked file, validates it has both `workstreams` and `items` before staging it in `pendingImportData` and opening `importModalBg`. `applyImport(mode)`: `'replace'` downloads a `pulse-backup-before-replace-<date>.json` safety copy first, then overwrites `programme`/`workstreams`/`items` outright; `'merge'` calls `mergeData(pendingImportData, {respectTombstones: false})`. Both branches call `normalizeData()` before `save(); render()`.

### Export to Excel

**A second, distinct export path (an explicit user request) — a formatted, human-facing `.xlsx` report, not the plain-data JSON above.** The plain Export is a lossless backup/interchange format meant to come back in through Import; this one is meant to be opened, read, filtered, or handed to someone who will never open Pulse itself, so it prioritizes looking like a real report over being a complete data dump — no tombstones, no ids, no raw field names.

**ExcelJS (`exceljs.bare.min.js`, cdnjs, pinned to 4.4.0) is this app's one and only external JS dependency** — everything else in this otherwise zero-build, zero-dependency PWA is hand-written. The `.bare` build specifically (not the plain/full build) skips ExcelJS's Node-only stream/fs polyfills that a browser-only page never needs. Loaded eagerly via a `<script>` tag in `<head>` (not lazily on first use of the feature) so it's one predictable, always-precached thing for `sw.js`'s `APP_SHELL` to fetch on install, same as Font Awesome. `exportToExcelReport()` guards against it not having loaded (`typeof ExcelJS === 'undefined'` — a first launch with no network, or the CDN being blocked) with a clear toast rather than a crash; `tests/cases/sync.test.js` exercises exactly that guard, since the real library is never loaded inside the JXA test harness at all.

Three sheets, each with a bold white-on-`#2D3648` header row, a frozen top row, and an autofilter (`excelStyleHeaderRow()`):
- **Scope Items** (`buildScopeItemsSheet()`): Workstream / Category / Scope Item / Status / Start / Due / Actual / IT / Business / Budget. Unassigned first, then real workstreams in their own display order, items within each in their own manual `order` — matching the status board's own section/row order exactly. Each item's row is bold, followed by one indented, italic row per milestone (`alignment: { indent: 2 }`) with just Name/Due/Actual/Status filled in — the same "item row, then its milestones underneath" shape the status board itself uses, just flattened into rows instead of an expand/collapse. A `notApplicable` milestone shows a plain grey italic "N/A", no status fill — mirroring the app's own frozen-N/A-badge treatment for exactly the same milestone.
- **Action Log** (`buildActionLogSheet()`): Workstream / Action Item / Owner / Due Date / Source / Created / Closed, across every workstream (reuses `sortedActionLog()`, the same open-first/soonest-due-first-then-most-recently-closed ordering the in-app "All workstreams" Action Log view already uses). A completed row's whole line gets a struck-through grey font rather than a separate "done" column.
- **Decision Log** (`buildDecisionLogSheet()`): Workstream / Decision / Source / Logged, across every workstream, reusing `sortedDecisionLog()` (most recent first).

**Status/RAG cells are colored with a fixed, hardcoded hex palette (`EXCEL_RAG_COLORS`), not by reading the page's current CSS custom properties** — a report exported today should look identical regardless of which of Pulse's several color schemes (Dracula, GitHub, …) happened to be selected in the browser at export time; the values are simply copied from the "standard" scheme's own `--stat-*` block at the very top of the stylesheet, and are the only thing this feature hardcodes rather than deriving live. `excelRagCellStyle(cell, ragId)` applies both the fill and a matching bold font color in one call, used for Status *and* the IT/Business/Budget tag cells alike, all four being the same `'not-started'|'green'|'amber'|'red'|'complete'` (or plain `'green'|'amber'|'red'` for the tags) vocabulary.

**`excelDateCell(row, key, iso)` builds a real Excel date value (so it sorts/formats/filters as one, not inert text), and deliberately does *not* reuse this app's own `fmtDate()`-style local-time parsing (`new Date(iso + 'T00:00:00')`) to do it.** ExcelJS converts a JS `Date` to an Excel serial number using that Date's *UTC* fields — a `Date` built from local-time parts (as every other date-parsing spot in this app correctly does, since those all stay inside the browser's own local-time rendering) silently rolls back to the *previous* calendar day once serialized, for anyone exporting from a UTC+ timezone (confirmed directly: opened the generated file and read a `2026-07-29` due date back as `2026-07-28`). The fix is `new Date(Date.UTC(y, m - 1, d))` — a Date whose *UTC* representation is exactly midnight on the intended calendar date, so ExcelJS's own UTC-based conversion round-trips it correctly regardless of the exporting browser's timezone. This is the one place in the whole app that has to think about UTC at all, specifically because it's the one place handing a date to something outside the browser's own local-time rendering path.

The download itself follows `downloadData()`'s own Blob-URL-synthetic-`<a>` pattern by hand (rather than reusing that helper directly, since its body is JSON-specific): `wb.xlsx.writeBuffer()` (a `Promise<ArrayBuffer>`) wrapped in a `Blob` with the real OOXML MIME type, filename `<slugified programme name>-<date>.xlsx` (falling back to `Pulse` if the name has no alphanumeric characters left after slugifying).

### Local backups

`save()` calls `maybeSnapshotBackup()` on every save, which takes at most one rolling snapshot per calendar day (keyed by `todayStr()`) into `localStorage["pulse-backups"]`, keeping the last `MAX_BACKUPS` (7) days — a local safety net distinct from file sync, which mirrors live state rather than preserving history. A backup taken earlier in the day isn't refreshed by later saves that same day. The "Data → Backups" modal (`openBackupsModal()`/`renderBackupsModal()`) lists snapshots newest-first; `restoreBackup(date)` opens the confirm modal, and on confirm downloads a safety backup of the *current* data first (same `downloadData()` primitive), then overwrites from the snapshot and calls `normalizeData()`. Backups don't carry tombstones (same reasoning as export/import — a restore is an explicit full replace, not a merge).

### File System Access API sync

`fileHandle` (module-level, `null` until linked) plus a tiny hand-rolled IndexedDB wrapper (`_fsIdb`/`_fsGet`/`_fsPut`/`_fsDel`, db `pulse-fs`) persist the linked file handle across reloads — Chrome/Edge only (`window.showOpenFilePicker`/`showSaveFilePicker` feature-detected; Safari has neither). `save()` calls `queueFileSyncWrite()` whenever `fileHandle` is set. `doFileSyncWrite()` (the actual write) does a light conflict check first: if the file on disk has changed since Pulse's own `lastSyncedSnapshot` (another tab or device wrote to it), it merges that external copy in via `mergeData()` before writing, and toasts what changed. It builds its own `data` snapshot from the live globals itself, right before writing, rather than accepting one as a parameter — see below for why that matters.

**Writes are serialized and always reflect the latest state, not a stale snapshot.** `save()` fires on nearly every mutation in the app — a keystroke, a status cycle, a rename — and each one used to kick off its own unawaited `fileSyncWrite(data)` with a snapshot captured at that exact moment. Since a single write does several `await`s (`requestPermission`, reading the file back for the conflict check, `createWritable`) before it ever touches disk, two overlapping writes could finish in either order — and if the one carrying *older* data happened to win, whatever the newer write should have persisted (a just-typed rename, say) would silently be overwritten back to the stale value, with no error and nothing visibly wrong in the app itself (`localStorage` — checked on next load — still had the correct value). `queueFileSyncWrite()`/`fileSyncWriteInFlight`/`fileSyncWritePending` fix this: at most one write is ever in flight; a `save()` that lands mid-write just sets a pending flag rather than starting a second overlapping write, and when the in-flight write finishes, exactly one more write starts if anything was flagged — reading `programme`/`workstreams`/etc. fresh at that later moment, not whatever they were when originally queued. This collapses any burst of rapid saves into the minimum necessary writes, and guarantees the file always converges on the true latest state. A write that fails for any other reason (not just a lost permission, which already has its own reconnect flow) now also toasts an error, instead of failing completely silently — a `catch` with no toast previously meant a change could look saved in the app while never actually reaching the linked file, with no way to notice.

`linkFile()`/`createNewLinkedFile()` (via `window.showOpenFilePicker`/`showSaveFilePicker`) pick or create the linked file; `linkFile()` merges any existing content in the picked file on first link. `reconnectFile()` re-requests write permission (browsers can silently revoke it, e.g. after a restart) and merges. `initFileSync()` runs at page load: if a handle was persisted in IndexedDB, it tries to reuse it (merging the file's content in if permission is still granted, or prompting to reconnect if not); if there's no persisted handle at all, it opens the onboarding modal (`openFileSyncModal()`) so a first-time user is prompted to link or explicitly dismiss with "Not now". Every one of these four (plus `doFileSyncWrite()`) sets `lastSyncedSnapshot` *and* `lastSyncedAt` together at the point they've just reconciled with the file — see "Conflict detection" above for why the latter matters. `updateFileSyncUI()` swaps the topbar's `#fileSyncIndicator` between four states (no picker support → hidden entirely, unlinked → "Link file" button, linked-and-granted → filename + unlink button, linked-but-permission-lapsed → amber "Reconnect" button) via `fadeSwapHTML()` (a short opacity crossfade, skipped if the HTML is already identical). This indicator is the *only* entry point into `openFileSyncModal()` — there's deliberately no static "File sync" item in the Data dropdown, because a dropdown item can't reflect which of those four states is current the way the indicator does; a fixed menu entry would keep opening the "nothing's linked yet" onboarding copy (including the "will be lost if you clear browsing data" warning) even once a file *is* linked and auto-saving, which is exactly the bug this avoids.

**Background polling.** Every write-triggering path above only ever notices an external change (a teammate's edit, synced down by something like OneDrive/SharePoint) at the moment *this* browser itself writes — someone just reading the board, or with it open in an idle tab, would otherwise never see anything new until they touched something or reloaded. `startFileSyncPolling()`/`stopFileSyncPolling()` run `pollFileSync()` on a `setInterval` (`FILE_SYNC_POLL_MS`, 45s) for as long as `fileHandle` is set — started from every successful link/reconnect/init path above, stopped in `_clearFileLink()`. `pollFileSync()` is deliberately a separate, lighter path from `queueFileSyncWrite()` rather than just calling that on the same timer: `doFileSyncWrite()` unconditionally rewrites the file at the end of every call (bumping its mtime, re-triggering a cloud-sync client) even when nothing actually changed, which would mean needlessly re-uploading an unchanged file every interval forever. `pollFileSync()` instead reads the file, bails immediately if its text matches `lastSyncedSnapshot` (nothing external changed), and only merges + `save()`s (which *does* trigger a real write, through the normal path) when it finds something worth reconciling. It uses `queryPermission`, never `requestPermission` — a background timer has no user gesture behind it, so it must never risk popping an OS permission prompt on its own; a lapsed permission surfaces through the existing "Reconnect" affordance instead, same as any other permission loss.

**Testing caveat**: the JXA test harness doesn't mock `indexedDB` (its no-op `setTimeout` would leave any real async IndexedDB request forever unresolved, hanging a test) or `setInterval` (stubbed as a no-op, same as `setTimeout`, purely so nothing throws — it never actually fires in a test). Every file-sync function that would touch IndexedDB or the real filesystem is gated on a `window.showOpenFilePicker`/`showSaveFilePicker`/`fileHandle` check first, and the harness's fake `window` has neither — so `linkFile()`, `createNewLinkedFile()`, `initFileSync()`, `reconnectFile()`, `doFileSyncWrite()`, and `pollFileSync()` all safely no-op in tests. `unlinkFile()` is the one exception (it unconditionally calls into IndexedDB) and is deliberately not exercised by the test suite for that reason. What *is* tested directly, since none of it touches `fileHandle`/IndexedDB: `mergeData()`'s per-milestone merge and conflict detection, `stampChangedMilestones()`/`saveItem()`'s and `applyCategoryMilestoneSync()`'s `updatedAt`-stamping and tombstoning, and `reportSyncConflicts()`/`syncConflictLog`.

### Daily backups to a linked folder

**A second, independent copy of every linked-file write — dated, and written directly into a separately-chosen folder — an explicit user request, distinct from both the linked file itself and the existing localStorage-based "Local backups" above.** Where the linked file is a live mirror of current state (one file, always overwritten), this is a growing history of dated snapshots on real disk, the same "one per day, self-heals from a prior state" instinct as `maybeSnapshotBackup()`, just written to the filesystem instead of `localStorage` — and, unlike that 7-day-capped rolling window, kept forever: nothing here ever deletes an old dated file. **Files land directly in the chosen folder, not inside a nested `Backup` subfolder** — an earlier version created one; removed after a user correction, since the user picking a folder specifically for this purpose already communicates the intent, and a subfolder they didn't ask for just adds a level of nesting to dig through.

**Getting a folder handle needed its own, separate permission grant.** The File System Access API has no way to walk from `fileHandle` (a handle to one specific file, picked via `showOpenFilePicker`/`showSaveFilePicker`) up to that file's own parent folder — there's no `getParent()` on a file handle. So "the folder the linked file lives in" can't be derived automatically; the user has to point at it directly via a second, separate picker (`window.showDirectoryPicker({mode:'readwrite'})`). `chooseBackupFolder()` is that flow: it stores the result in a second module-level handle, `backupDirHandle`, deliberately independent of `fileHandle` — unlinking the main file doesn't clear it, so relinking a file later resumes backups into the already-chosen folder with no need to pick it again. `dir.resolve(fileHandle)`, when supported, is used as a soft sanity check right after picking — it tells us whether the chosen folder actually contains the linked file, so picking the wrong one surfaces as a toast ("that folder doesn't contain `<file>`") rather than silently backing up somewhere unexpected; a mismatch doesn't block anything, since a user might deliberately want backups somewhere other than right next to the linked file.

`backupDirHandle` persists across reloads the same way `fileHandle` does — the same tiny IndexedDB wrapper (`_fsIdb`/`_fsGet`/`_fsPut`/`_fsDel`, db `pulse-fs`) now takes an optional `key` parameter (defaulting to the linked-file slot, so every pre-existing call site is unaffected) and stores the backup folder handle under a second key, `_FS.backupKey`, in the same object store. `initFileSync()` restores it in its own isolated `try`/`catch` block, run before (and independent of) the rest of the function's own `fileHandle` restoration, so a problem reconnecting one handle can never trip the other's error handling; restoration only uses `queryPermission` (never `requestPermission`), the same background-safe convention `pollFileSync()` already follows — a lapsed backup-folder permission just means backups silently stop rather than popping an unprompted OS dialog.

**`writeBackupCopy(data)` is called from `doFileSyncWrite()`, right after the primary write to the linked file succeeds** — same `payload` (the actual final state just written, post-merge if one happened), so the backup and the linked file always agree on content. It's deliberately best-effort and silent on any failure: by the time it runs, the primary write has already succeeded, so a backup-side problem (permission lapsed, folder deleted, disk full) must never surface as an error over a save that otherwise worked fine. Gated on `lastBackupWrittenDate !== todayStr()` — the first save of each calendar day writes that day's file; every other save that same day is a no-op here, mirroring `maybeSnapshotBackup()`'s own "one snapshot per day" rule.

**It checks whether today's file already exists on disk before writing it, rather than unconditionally overwriting — an explicit user request.** `lastBackupWrittenDate` alone only guards against *this one session* writing more than once a day: it's plain in-memory state, never persisted, so a page reload — or, more importantly, a genuinely different session/user pointed at the same shared/synced folder — starts with it back at `null` and would otherwise go ahead and write again regardless of what's already there. The original version called `backupDirHandle.getFileHandle('pulse-backup-<date>.json', {create:true})` unconditionally, which always succeeds (handing back a handle to the existing file if there is one, or creating a fresh one if not) and proceeds to overwrite either way — so two sessions saving on the same day would silently clobber whichever wrote last, with no error, no merge, and no way for either side to know it happened (the same "best-effort and silent" trait that protects a genuine failure from surfacing also meant a *collision* looked identical to success). Fixed by checking first: a plain `getFileHandle(name)` with no `{create:true}` throws if the file is missing, which is now used purely as an existence probe before ever calling the `{create:true}` version. Finding it already there is treated the same as this session having written it itself — `lastBackupWrittenDate` is set either way, so the rest of the day's saves skip straight past the (cheap, but not free) existence check too, same as before. This narrows, but can't fully close, the race between two sessions saving at nearly the same instant — the File System Access API has no atomic "create only if missing" primitive to check-and-write in a single step — but it turns "always overwrites" into "only the very first writer each day wins," which is what was asked for.

Because backups are wired in as a side effect of `doFileSyncWrite()`, they only ever happen while a main file is actively linked and syncing — unlinking the main file stops them too (silently, same as any other consequence of `queueFileSyncWrite()`'s own `if (!fileHandle) return` guard), even though `backupDirHandle` itself stays remembered for whenever a file is linked again.

**Day-to-day UI is entirely in the topbar, not a modal** — `#backupSyncIndicator`, sitting right next to `#fileSyncIndicator`, an explicit user request for the same at-a-glance visibility the linked file itself already has. (An earlier version put a matching row inside `fileSyncModalBg`, `#fileSyncBackupSection`/`fileSyncBackupSectionHtml()` — removed once this indicator made it redundant; the modal's three options went back to just Link/Create/Reconnect, its original scope — see "Launch-time onboarding" below for the separate, later modal that *did* eventually come back, for a different reason.) `updateBackupSyncUI()` is `updateFileSyncUI()`'s own counterpart, same `fadeSwapHTML()`-driven crossfade and the identical `.sync-linked`-span-plus-unlink-button markup for the "on" state, but with only two states rather than four: hidden outright when `window.showDirectoryPicker` isn't supported (mirroring `updateFileSyncUI()`'s own `showOpenFilePicker` check), a plain "Backups off" button when `backupDirHandle` is unset, or the chosen folder's name plus an unlink button once it's set. Unlike `fileSyncIndicator`'s own "off" state (which opens a modal offering three different ways to link a file), the topbar's own "Backups off" button calls `chooseBackupFolder()` directly, not a modal — there's only ever one action to reach this way, so routing through one with nothing else in it would just be an extra click. There's also no third "permission lapsed" state the way the linked file's own indicator has (its amber "Reconnect" button) — a lapsed backup-folder grant has no dedicated reconnect flow at all (see `writeBackupCopy()`'s own comment above); it just silently stops backing up until `chooseBackupFolder()` is run again. Called from `chooseBackupFolder()`/`unlinkBackupFolder()` (so the badge updates the moment the folder changes) and twice from `initFileSync()` — once immediately (so the badge doesn't sit blank while IndexedDB restoration is still in flight) and once after `backupDirHandle` is actually restored. Like every other file-sync action, none of this has a role gate (see "Roles (RBAC)" below) — daily backups are a workflow/device setting in the same spirit as linking itself, not a data mutation.

**Launch-time onboarding is a second, separate modal (`backupFolderModalBg`), shown right after the file-sync onboarding modal closes — an explicit user request ("handle file link and backup link in 2 modals after each other... ask when launching the app").** This is deliberately *not* folded back into `fileSyncModalBg` (which the paragraph above already explains was tried once and reverted) — it's a distinct modal for a distinct moment: only at launch, only once, chained specifically off the file-sync modal's own close rather than living as a permanent option inside it. `openFileSyncModal(reconnectHandle, isLaunch)` gained a second parameter for this: `isLaunch` is `true` only at the three call sites inside `initFileSync()`/`maybeShowPendingFileSyncPrompt()` that represent genuine startup onboarding, and omitted (falsy) at the topbar indicator's own manual "Link file"/reconnect calls — `closeFileSyncModal()` reads the resulting `fileSyncModalIsLaunchFlow` flag to decide whether to call `maybeShowBackupFolderOnboarding()` right after removing its own `open` class, so a modal reopened manually later in the session never unexpectedly cascades into a second one on close. This fires regardless of *how* the file-sync modal was closed — "Not now", or after successfully linking/creating/reconnecting — the backup-folder step is asked about either way, the same "doesn't gate on what was chosen" shape the file-link step itself already has relative to the mandatory role picker before it. `maybeShowBackupFolderOnboarding()` itself is a no-op if daily backups aren't supported at all, or a folder's already chosen (restored from IndexedDB earlier in the same `initFileSync()` call) — so a returning user who already has both linked never sees either onboarding modal again. **The one case with no file-sync modal to chain off of** — the file link is already present and fully working (`initFileSync()`'s `perm === 'granted'` branch, which reads and syncs the file without ever opening a modal) — calls `maybeShowBackupFolderOnboarding()` directly instead, right after that branch (guarded on neither `pendingFileSyncPrompt` being set nor the file-sync modal currently being open, so it can't double-fire against the two branches that *do* open one). Like `fileSyncModalBg`, the new modal closes on Escape and backdrop click (unlike `scopeAssignModalBg`'s own deliberately inescapable design elsewhere in this file — this one's a soft, dismissable prompt, not a mandatory gate).

**Testing caveat, in addition to the one above**: `chooseBackupFolder()`/`unlinkBackupFolder()` and the backup-restoration half of `initFileSync()` all touch IndexedDB or `window.showDirectoryPicker` and so are gated the same way the rest of file sync is — safely un-reachable under the JXA harness's fake `window`. `unlinkBackupFolder()` is a second instance of `unlinkFile()`'s own documented exception (it unconditionally calls into IndexedDB) and isn't exercised for the same reason. What *is* tested directly, since none of it touches either: `backupFileName()` (the pure filename builder), `writeBackupCopy()`'s two early-return guards (no folder chosen; today's copy already written) — both fire before ever calling a method on `backupDirHandle`, so they're safe to exercise even with a plain fake object standing in for a real `FileSystemDirectoryHandle` — and `updateBackupSyncUI()` hiding `#backupSyncIndicator` outright, since the harness's fake `window` has no `showDirectoryPicker` either. `writeBackupCopy()`'s own existence-check logic (the paragraph above) goes further than either of those guards and *does* call methods on `backupDirHandle`, so it's outside what the JXA harness can exercise at all — verified instead with a real Chromium instance (Playwright), substituting a plain JS object for `backupDirHandle` whose `getFileHandle()` either always resolves (simulating the file already existing) or only resolves when called with `{create:true}` (simulating it not existing yet), confirming the write is skipped in the first case and happens exactly once in the second.

## Roles (RBAC)

**This is a soft, UI-level permission ladder, not real access control.** Pulse has no server, no accounts, and no auth of any kind — every byte of app state lives in this browser's `localStorage` (or a linked file the browser itself has read/write access to), so anyone with the browser's dev tools, or direct access to the data file, can already see and change everything regardless of which role is showing. The feature exists purely to guide day-to-day workflow on a shared device or a small team (keep a Visitor from *accidentally* editing a scope item) — not to keep anyone out on purpose. This was an explicit, deliberate tradeoff confirmed with the user up front, not an oversight.

**`ROLES` is an increasing ladder — `['visitor', 'reviewer', 'editor', 'admin']` — never a set of independent, non-overlapping permissions.** Each role can do everything the one before it can, plus more:
- **Visitor** — view Planning, Review, and Dashboard; no edits anywhere.
- **Reviewer** — + start/confirm/complete/cancel review cycles, attach/edit/remove meeting minutes, manage the Action Log.
- **Editor** — + create/edit/delete workstreams, scope items, milestones, and categories.
- **Admin** — + import/restore data.

File sync (linking, creating, unlinking, reconnecting a synced file, plus choosing/turning off the daily-backup folder — see "Daily backups to a linked folder" above) is deliberately **not** part of this ladder at all — it's available at every role, including Visitor (an explicit user request). Unlike the ladder's other tiers, there's no "who's meant to own this" framing here: connecting/disconnecting the shared data file is treated as closer to a workflow/device setting than a data-mutating action a role should gate.

Reviewer sits *below* Editor on the ladder — a user-requested swap from the original order (`['visitor', 'editor', 'reviewer', 'admin']`), since a Reviewer running review cycles shouldn't automatically also be able to restructure the plan (add/delete workstreams, scope items, milestones) the way the original ordering implied. Because every `requireRole('editor')`/`requireRole('reviewer')` guard and every `hasRole('editor')`/`hasRole('reviewer')` UI-gating check throughout this file reference role *names*, not positions, reordering `ROLES` (plus rewording each `ROLE_META[...].desc`'s "Everything a `<X>` can do, plus..." chain to match) was the entire fix — every call site automatically picked up the new hierarchy with no changes of its own. This is the actual payoff of `roleLevel(r) { return ROLES.indexOf(r); }` being the *only* thing that knows the ladder's order: the ladder's shape lives in exactly one place.

`roleLevel(r)` is just `ROLES.indexOf(r)`; `hasRole(minRole)` is `roleLevel(userRole) >= roleLevel(minRole)` — true for the given role *or anything above it* on the ladder, which is what makes it a ladder rather than a flag check. `requireRole(minRole)` is the defense-in-depth guard called as the very first line of every state-mutating function gated by role (`if (!requireRole('editor')) return;` etc.) — it shows a toast (`"<Role> role or higher required for this action"`) and returns `false` rather than throwing, so a stray call (e.g. typed into the console) fails quietly instead of corrupting anything. **This guard is the second layer, not the primary one** — the real, user-facing gate is that the render functions never show the control in the first place (see "UI gating by role" below); `requireRole()` exists so a control that's merely disabled-but-still-clickable (a `disabled` input) or reachable by some path the UI pass missed still fails safely rather than silently mutating state.

**`userRole` is `null` until a role is chosen, and its persistence is deliberately isolated from every other piece of state.** Unlike `mode`/`theme`/`colorScheme` (which live inside the same blob `save()` writes to `localStorage['pulse-v1']`, and even get written out to a linked sync file by `queueFileSyncWrite()`/`doFileSyncWrite()` — just never read back from one), `userRole` lives under its own key, `ROLE_STORAGE_KEY = 'pulse-role-v1'` (`loadRole()`/`saveRole()`), and is never folded into `save()`'s data object or `doFileSyncWrite()`'s payload at all. This was an explicit requirement: a role chosen on one device must never leak into the shared/synced data file and silently change what role another device's picker defaults to, or what a teammate sees when they open that same file. `loadRole()` validates against `ROLES.includes(raw)` the same defensive way `load()` validates `colorScheme` against `THEME_SCHEMES` — an invalid/missing stored value just leaves `userRole` at `null` (i.e., the picker gate fires) rather than crashing.

**The role picker (`#roleModalBg`, `renderRoleModal()`/`openRoleModal()`/`closeRoleModal()`/`setUserRole(role)`) doubles as two different things depending on whether a role has ever been chosen on this browser.** With `userRole` still `null` (a brand-new browser, or `localStorage` cleared), it's a mandatory, undismissable first-launch gate: `closeRoleModal()` itself checks `if (!userRole) return;` before closing anything, and both the backdrop-click handler and the global Escape handler call `closeRoleModal()` the same way every other modal's does — so both just no-op rather than closing the app's very first, load-bearing choice. `renderRoleModal()` also disables/greys out the modal's own "Done" button (`#roleModalDoneBtn`) while `userRole` is still null, for the same reason. The init sequence (`load(); loadRole(); ...; render(); initFileSync(); if (!userRole) openRoleModal();`) deliberately calls `openRoleModal()` *last* — after everything else has already rendered underneath — so the very first thing a brand-new user sees is a role prompt sitting on top of a normal (if role-gated-down-to-Visitor-looking) UI, not a blank/broken page. Once a role exists, the exact same modal is reachable anytime via the topbar's shield icon (`#roleBtn`, `onclick="openRoleModal()"`) — an explicit, confirmed design decision that switching roles should need no confirmation or reload, since this is a workflow aid, not a login.

**`updateRoleBtn()` keeps that topbar icon itself in sync with the current role — a user-reported bug, since it used to be a single hardcoded `fa-user-shield` glyph regardless of which role was active, so switching roles visibly changed nothing there.** It sets `#roleBtnIcon`'s class to `ROLE_META[userRole].icon` (falling back to `fa-user-shield` if `userRole` is still `null`, pre-first-pick) and `#roleBtn`'s `title` to `"Role: <Label> (click to switch)"`. Called from `render()` itself, not just from `setUserRole()`, so it's also correct immediately after the very first pick, after a page reload, and after any other state change that happens to call `render()`.

**`initFileSync()`'s auto-onboarding/reconnect prompt is deferred via `pendingFileSyncPrompt` until a role actually exists, to avoid a first-launch race with the mandatory role picker.** All three of `initFileSync()`'s `openFileSyncModal()` call sites (no previously-linked file at all; a previously-linked file whose permission has lapsed and needs reconnecting; a hard error reading the previously-linked file) used to call `openFileSyncModal()` immediately — including on a *brand-new* browser where `userRole` is still `null`. Since `initFileSync()` runs (and its internal `await`s resolve) concurrently with the init sequence's own `if (!userRole) openRoleModal()` call right after it, this raced the mandatory, undismissable role-picker gate: the file-sync modal could get visually buried behind the role modal, appearing before the user had picked *any* role yet. Fixed by checking `!userRole` at each of the three call sites: instead of opening immediately, they stash what they wanted to show in `pendingFileSyncPrompt` (`'link'`, or the handle needing reconnect/re-read) and return. `closeRoleModal()` calls `maybeShowPendingFileSyncPrompt()` right after removing the modal's `open` class, which opens the parked prompt now that a role exists — any role, since file sync isn't gated by role at all (see below). On a **returning** browser (`userRole` already set from `loadRole()` before `initFileSync()` ever runs), none of this deferral triggers — `!userRole` is false immediately, so the modal opens exactly as it always did, with no race to avoid.

**`openFileSyncModal(reconnectHandle)` has no role-gated content — file sync is available at every role, including Visitor (an explicit user request).** It previously swapped its entire body below Admin (hiding `#fileSyncOptions` behind a plain "Admin required" notice), matching `reconnectFile()`/`linkFile()`/`createNewLinkedFile()`/`unlinkFile()` each being `requireRole('admin')`-guarded themselves — all four of those guards, and the modal's admin-notice branch, were removed together. The modal now always shows the real Reconnect/Link existing/Create new options regardless of who's looking, and `#fileSyncIndicator` in the topbar is likewise no longer hidden below Admin (`updateFileSyncUI()`'s only remaining hide condition is lack of picker support, i.e. not Chrome/Edge).

**UI gating by role** — the render-time half of the system, which is what actually determines what a given role sees, not just what it can successfully submit:
- **Sidebar** (`renderSidebar()`): the "+ new workstream" button (`#addWsBtn`), each row's edit pencil (`.ws-row-edit`), and its drag handle (`.ws-row-drag`, see "Manual item order and drag-and-drop reordering" above) all only render at Editor+.
- **Planning status board** (`itemRowHtml()`/`milestoneRowsHtml()`): the Unassigned section's own "+ Add item" affordance (`unassignedSectionHtml()` — see "Quick-add scope items, the Unassigned bucket, and the Pending category" below), the item row's Edit/Delete/drag-handle actions, the IT/Business/Budget tag badges, and every inline date pill (item Plan dates, milestone Due/Actual) are all editable only at Editor+ — below that, tags/status badges render as plain, non-interactive `<span>`s (not omitted — see "Column layout is a real CSS grid" above for why an omitted cell would break alignment) and date pills render with `disabled` rather than an `onblur` handler. A milestone's status badge (`cycleMilestoneStatus`) follows the same span-vs-button split. The item-level and milestone-level review confirm toggles (`grid-column:11`) render as an inert `<span>` — still showing the real confirmed/unconfirmed icon, just not clickable — below Reviewer, rather than Editor: seeing review progress while planning is fine, changing it isn't.
- **Item/Workstream/Category modals** stay reachable to *view* regardless of role — `openItemModal()`/`openWorkstreamModal()`/`openCategoryModal()` are never role-gated themselves, since reading an item's full detail is exactly what "view only" should still allow. What role gates is editability: every input/select/textarea in the modal gets `.disabled = !hasRole('editor')`, the Save/Add-milestone/Add-category-milestone buttons are hidden outright below Editor, and the Delete button is hidden below Editor *and* when there's nothing to delete yet (both conditions already existed independently — a new `it`-less modal never showed Delete either). `renderMilestonesEditor()`/`renderCategoryMilestonesEditor()` apply the same `disabled`/hidden-button treatment to each dynamically-rendered row.
- **Review mode**: "Start review cycle" is replaced with a plain explanatory line below Reviewer; the "Complete review"/"Cancel review" button row is omitted entirely (not just disabled) below Reviewer.
- **Meeting Minutes modal**: reachable to view (past minutes are worth reading regardless of role) but every field (`disabled`) and every action button (Auto-fill/Clear all fields/Add action item/Save/Remove, plus each Action Item row's own inputs and its per-row Remove button) is hidden/disabled below Reviewer.
- **Action Log** (`actionLogRowHtml()`): the Delete button and the complete/reopen toggle both fall back to the same "real empty span" / "inert icon-only span" pattern used elsewhere, below Reviewer.
- **Admin mode / Categories** (`renderAdmin()`): the "+ Category" button and each row's Edit pencil only render at Editor+ (categories are Editor-tier, same as scope items/workstreams — there's nothing Admin-specific about a milestone template).

**The category row's Edit pencil was rendering but permanently invisible — an Editor/Admin genuinely could not edit a category once created, despite the gating above being correct.** Root cause: `renderAdmin()`'s category row wraps its Edit pencil in `<span class="item-actions">` (line ~4718), reusing the same class the item row uses for its own Edit/Delete/drag icons. But `.item-actions`'s hover-reveal (`visibility: hidden` at rest, flipped to `visible`) was only ever wired up for `.item-row:hover .item-actions` — there was no equivalent `.category-row:hover` rule, so on a category row the button sat in the DOM, fully functional, at `visibility: hidden` with no hover state that ever cleared it. Fixed with one added rule, `.category-row:hover .item-actions { visibility: visible; }`, right next to `.item-row`'s own — same reasoning as `.item-row`'s (visibility, not display, so the row never reflows on hover).
- **Data menu**: the Import and Backups dropdown items (`#dataMenuImportItem`/`#dataMenuBackupsItem`) are hidden below Admin — set directly in `render()`, since they're static markup rather than something a mode-specific render function owns. Export is deliberately left available to every role: it's a read-only download, not a mutation, so there's nothing to gate.

**Role passwords add an optional per-role password gate on top of the picker — an explicit user request ("add a password mechanism for all roles except Viewer"), still deliberately just a *soft* deterrent, not real access control.** `programme.rolePasswords` (`{ reviewer: {salt,hash}|null, editor: {salt,hash}|null, admin: {salt,hash}|null }`, backfilled by `normalizeData()` — Visitor has no entry at all, since it's never gated) is part of `programme` itself, which — unlike `userRole` — *is* written out to the shared/synced data file (see `doFileSyncWrite()`'s payload above): an Admin-set password is meant to apply for every teammate opening that same file, not just this one browser, so it has to live in the synced blob rather than `ROLE_STORAGE_KEY`. `null` (the default) means "no password set for this role yet" — picking it still switches immediately, exactly like before this existed, so a brand-new programme has no bootstrapping deadlock (an Admin has to be able to freely reach Admin *before* setting any passwords, including the Admin one). A follow-up request ("can the password be stored as a hash in the file, not plain text?") is why it's `{salt, hash}` rather than the plain string an earlier version of this used: real, meaningful protection for the password's own *storage* (opening the shared file or `localStorage` no longer just hands it over), but **not** a different category of protection overall — the check itself (`verifyRolePassword()`, below) still runs in this same page's own client-side JS, so anyone technical enough to read it, or to just call `setUserRole('admin')` from the console, bypasses the whole thing regardless of how the password is stored. Both the in-app copy (`#roleModalBg`'s own paragraph) and this doc say so explicitly, since a password specifically invites the assumption that it's real access control more than the rest of RBAC already does.

**Hashing (`hashRolePassword()`/`verifyRolePassword()`/`sha256Hex()`/`randomSaltHex()`) uses the real Web Crypto API (`crypto.subtle.digest('SHA-256', ...)`, `crypto.getRandomValues()`), not a hand-rolled algorithm.** `hashRolePassword(password)` generates a fresh random 16-byte salt (hex-encoded) *every time a password is set or changed* and hashes `` `${salt}:${password}` ``, returning `{salt, hash}`; `verifyRolePassword(password, stored)` re-hashes the candidate with `stored.salt` and compares the hex digest to `stored.hash` (`false` if `stored` is falsy, rather than throwing). The fresh-salt-per-password choice specifically matters here: without it, two roles given the *same* password would land on identical hashes, visibly revealing the match to anyone comparing `programme.rolePasswords` even without ever knowing either password. `crypto.subtle` only exists in a secure context (https, or a `localhost`/`127.0.0.1` origin — exactly how `start-pulse.command` already serves this app, but not a plain `file://` open); `hasSecureCrypto()` is checked up front by both `submitRolePassword()` and `saveRolePasswords()`, which show a plain-language error/toast instead of letting a missing `crypto.subtle` throw from deep inside an `await` chain. Both of those functions are themselves `async` now (hashing is inherently asynchronous), called straight from their `onclick`/`onkeydown` handlers same as any other handler — nothing about the surrounding UI needed to change to accommodate that.

`pickRole(role)` is what the role modal's tiles now call instead of `setUserRole(role)` directly: for `'visitor'`, or any role whose `programme.rolePasswords[role]` is still `null`, it just calls `setUserRole(role)` immediately, same as before. Otherwise it doesn't switch yet — it sets `pendingRolePick`, hides `#roleOptions`/`#roleModalDoneRow`, and shows `#roleModalPasswordStep` (a masked `<input type="password">` and Cancel/Unlock buttons) in their place, all still inside the same `#roleModalBg` rather than a second modal. `submitRolePassword()` awaits `verifyRolePassword()` against `programme.rolePasswords[pendingRolePick]`; a match calls `cancelRolePasswordStep()` (resetting the step UI back to the tile grid) then `setUserRole(role)`; a mismatch clears the input and shows an inline error, leaving the step open to retry. `cancelRolePasswordStep()` (also called by `openRoleModal()` itself, so a modal freshly opened never shows a stale password step left over from a previous abandoned attempt) just resets the UI with no role change. A role with a password set also renders a small lock icon next to its label in the tile grid (`renderRoleModal()`) — the affordance that a password will be asked for, rather than a surprise after clicking.

**`pickRole()`/`cancelRolePasswordStep()` also swap the modal's own title and hide its intro paragraph while the password step is showing — a user-reported issue: "Choose your role" plus its full paragraph explaining the whole password system stayed on screen while someone was just trying to type one password in, reading as a much bigger dialog than the single field it actually needed.** `#roleModalTitle`/`#roleModalIntro` (the `<h3>`/`<p>` at the top of the modal) and a new `#roleModalPasswordIntro` (a one-line "Enter the password to switch to `<Role>`." sitting inside `#roleModalPasswordStep` itself) replace the password step's old, redundant `#roleModalPasswordLabel` field label. `pickRole(role)` sets `#roleModalTitle`'s text to `` `${ROLE_META[role].label} password` `` and hides `#roleModalIntro`; `cancelRolePasswordStep()` restores both back to "Choose your role" / visible, so the tile grid always reopens looking like the full picker again, never mid-password-step framing.

**Setting the passwords themselves is Admin-only, both to view and to edit — a Reviewer/Editor being able to see *which* roles are currently password-protected (even without the values) would narrow down what's worth guessing against.** `rolePasswordsSectionHtml()`, appended to the end of `renderAdmin()`'s output, returns `''` outright below Admin; at Admin it renders a "Role Passwords" header, a "Manage" button (`openRolePasswordsModal()`), and a summary line naming which roles currently have a password set (never the values, and never the hash either — there's genuinely nothing to show, since only the hash exists, not the password). The actual editing happens in a real modal (`rolePasswordsModalBg`/`openRolePasswordsModal()`/`closeRolePasswordsModal()`/`saveRolePasswords()`, both `requireRole('admin')`-guarded) rather than inputs living directly in that admin-page section, deliberately: `renderAdmin()` re-renders on every `render()` call while in Admin mode — including background ones, like the file-sync poll's — and a live input sitting directly in that output would have its in-progress, unsaved keystrokes (and cursor focus) wiped out from under whoever's mid-typing the moment any unrelated `render()` fired; every other editable field in this app (categories included, just above) already lives in a modal for exactly this reason. The modal's three fields are plain `type="text"`, not masked — this is an Admin *setting* the values (not someone else entering one to unlock a role, which `pickRole()`'s own step does mask) — but they always open blank regardless, since only a hash is stored and there's no plain password left to pre-fill even for a role that already has one set; `openRolePasswordsModal()` sets each field's `placeholder` instead, to whichever of "Currently set — type a new password to change it" / "No password set — type one to require it" actually applies. Because the fields can't reflect the current value, blank-and-Save can no longer mean "clear this role's password" the way it did with a plain string — it now means "leave this role's password unchanged" instead, and Reviewer/Editor each have their own "Remove password requirement" checkbox for the (now explicit, unambiguous) case of actually wanting to drop one back to `null`; `saveRolePasswords()`'s internal `applyOne(role, inputId, clearId)` checks that checkbox first (wins outright over anything typed alongside it), then hashes and writes a non-blank field, and otherwise leaves that role's existing entry untouched.

**Admin has no "Remove" checkbox at all — an explicit user request ("for Admin this should not be deactivatable"), unlike Reviewer/Editor, which can be freely turned on and off.** `saveRolePasswords()` calls `applyOne('admin', 'rolePasswordAdminInput', null)` — a hardcoded `null` `clearId`, not a real checkbox's id — and `applyOne` only ever nulls a role out when `clearId && document.getElementById(clearId).checked`, so there is no code path capable of clearing Admin's password at all, independent of whatever markup happens to exist; `saveRolePasswords()` is still the *only* function that ever writes to `programme.rolePasswords`, so this one `null` is the entire enforcement. Admin can still be freely *changed* to a different password (typing a new one and saving hashes and replaces it, same as any other role) — only removing it back to "no password required" is foreclosed. This doesn't reopen the bootstrapping problem `normalizeData()`'s all-`null` default exists to avoid: a brand-new programme still starts with Admin unset, so the very first Admin can freely reach Admin and choose whether to lock it down — this only forecloses undoing that choice once actually made, not the initial free pick.

**`setUserRole(role)` leaves Admin mode for the All-workstreams Dashboard whenever the newly picked role isn't Admin and `mode` is currently `'admin'` — an explicit user request.** Without this, switching away from Admin while actually sitting on the Admin page would leave Admin-gated content (the Role Passwords section especially — see above) disappear out from under whoever's looking, mid-page, the next `render()`. Gated on the role having *actually changed* (`role !== userRole`, checked before reassigning it) so re-picking the role already active — clicking your own current tile in the modal — doesn't boot you off the Admin page for no reason; and on `role !== 'admin'` so picking Admin (from Admin or otherwise) never triggers it. When it does fire, both `mode = 'dashboard'` and `filterWorkstreamId = null` are set together — landing specifically on "All workstreams", not whatever happened to be filtered before — and `save()` is called directly (mode/`filterWorkstreamId` are normally persisted by `setMode()`/`setFilterWorkstream()`, neither of which `setUserRole()` goes through here, so this is the one place that needs its own explicit `save()` for a mode/filter change).

**Testing**: `tests/harness.js`'s `resetState()` defaults `userRole = 'admin'` — every test written before RBAC existed (i.e. almost the entire suite) is testing *functionality*, not permissions, and would otherwise fail on the very first `requireRole()` guard it hit. Tests that specifically cover role gating (`tests/cases/role.test.js`) set `userRole` to a lower tier themselves before exercising the behavior they're checking, and reset nothing else about the fixture — same pattern as any other test that deviates from the shared baseline.

## Categories (Admin mode)

**The topbar tab for this mode is labeled "Settings" in the UI — an explicit user request to rename the page — but every internal identifier still says `admin`**: `mode === 'admin'`, `#tabAdmin`, `#adminBody`, `renderAdmin()`, `MODES`. Only the tab's own visible text changed (`#tabAdmin`'s `<button>` text, plus the role modal's "under Settings &gt; Role Passwords" reference — see "Roles (RBAC)" above); nothing about the *Admin role* changed, since that's a separate concept from this page and wasn't part of the request — `ROLE_META.admin.label` is still `"Admin"`, and every other visible "Admin" in this file (the role picker, the Role Passwords modal's own "Admin password" field) refers to that role, not this page. This doc keeps calling it "Admin mode" throughout, matching the code's own internal naming, the same way `ROLE_META[r].label` already differs from the bare role string it's keyed by (`'reviewer'` → `"Reviewer"`) elsewhere in this app.

`renderAdmin()` lists every category (name, its milestone template as a `→`-joined preview string, and a live count of items currently using it) with an Edit button; "+ Category" opens the same `categoryModalBg` with nothing pre-filled. There's no separate "new" vs "edit" function — `openCategoryModal(id)` handles both, mirroring the workstream/item modal pattern (`editingCategoryId` is `null` for a new one).

`editingCategoryMilestones` is a working array of *plain strings* (not `{id, name, dueDate, status}` objects like an item's own milestones) — a category's `milestones` field is a template of names only, since a template has no dates or statuses yet. `renderCategoryMilestonesEditor()`/`addCategoryMilestoneRow()`/`removeCategoryMilestoneRow(idx)` mirror the item modal's milestone editor (same `.milestone-row` CSS class, just missing the date input and status select), including the "no re-render on keystroke, only on structural changes" discipline — see "Milestone checklist" above for why that matters for focus.

Order matters here (it's the sequence new items get seeded with), so each row is drag-and-drop reorderable — an explicit user request replacing an earlier up/down-arrow `.milestone-reorder` control (removed outright, not kept as a fallback). It's the same grip-handle/whole-row-drop-target split as `dragStartItem()`/`dropOnItem()` and `dragStartWs()`/`dropOnWs()`: only the small grip icon is `draggable="true"` (`dragStartCategoryMilestoneRow(e, idx)`, stashing `idx` in module-level `draggedCategoryMilestoneIdx`), so dragging doesn't fight with clicking into the name `<input>` next to it, while the whole `.milestone-row` is the drop target (`ondragover`/`ondrop` → `dropOnCategoryMilestoneRow(e, idx)`), so dropping anywhere on the row works, not just precisely on its own handle. Unlike `reorderItem()`/`reorderWorkstream()`, there's no id to key off — `editingCategoryMilestones` is a plain array of strings, in-memory only until `saveCategory()` commits it, and it's always fully re-rendered after every change anyway — so `dropOnCategoryMilestoneRow()` just splices the dragged name out of `fromIdx` and back in at the drop target's `idx` (a no-op if dropped back on itself) and calls `renderCategoryMilestonesEditor()` directly, rather than reassigning an `order` field the way the id-keyed arrays do. Both the grip handle and the row's drop-target attributes are gated to Editor+ (`requireRole('editor')` inside `dropOnCategoryMilestoneRow()` itself, defense-in-depth behind `renderCategoryMilestonesEditor()` only ever rendering them for `hasRole('editor')` in the first place) — reordering the template is still an edit, same tier as adding/removing/renaming a row. Like every other edit to this array, reordering only touches `editingCategoryMilestones`; the category's saved `milestones` array is untouched until `saveCategory()` commits it.

`deleteCategoryFromModal()` refuses outright (toast, no confirm modal) if the category is the reserved Pending one (see "Quick-add scope items, the Unassigned bucket, and the Pending category" below — deleting it would strand any item still waiting on the scope-assign prompt), or if `categories.filter(c => !c.pending).length <= 1` — there must always be at least one *real, selectable* category for an item to reference, the same invariant `normalizeData()` enforces on load (Pending itself doesn't count toward that minimum, since it's never a destination a real item is meant to stay in). Otherwise it opens the confirm modal describing how many items will be reassigned, and on confirm reassigns every item using the deleted category to `categories.find(c => c.id !== catId && !c.pending)` (the first *other, non-Pending* category) before removing it. Unlike workstream/item delete, **this has no undo toast** — categories are an Admin-level structural concept rather than day-to-day content, so a plain "this cannot be undone" confirm was judged sufficient rather than adding tombstone/undo machinery for a rarely-used action.

### Category template edits sync to items already using that category

Editing an *existing* category's milestone template (add/rename/remove) propagates to every item with that `categoryId`, not just future new items — a deliberate reversal of this project's earlier stance (an item's checklist used to be a one-time snapshot, fully independent of its category after creation). `saveCategory()` diffs `editingCategoryOriginalMilestones` (the template as it was when the modal opened, captured by `openCategoryModal()`) against the final `editingCategoryMilestones` **by name, as sets** — there's no id linking one template entry across an edit, so a rename is indistinguishable from "the old name was removed and a new name was added," and is treated exactly that way.

**Reordering the template also syncs to existing items, but through a separate, non-destructive path.** A pure reorder (same names, different order — `added`/`removed` both empty but the arrays differ index-for-index) sets a `reordered` flag and, if any items use the category, calls `applyCategoryMilestoneSync(catId, [], [], milestones)` directly — no confirm modal, since nothing is added or removed, just resorted. `applyCategoryMilestoneSync`'s 4th parameter, `orderedNames`, is the template's current name order; after handling any add/remove, it sorts every affected item's `milestones` array by each milestone's index in `orderedNames` (a milestone whose name isn't in the template at all — a one-off custom milestone added by hand — ranks after every template-matched one, keeping its relative position via the sort's stability). This reorder is also applied on the *destructive* add/remove path, for the same reason: a newly-added milestone lands at its correct template position rather than always at the array's end.

`milestoneRowsHtml()` renders milestones in plain array order (not sorted by `dueDate`) specifically so this reorder sync is actually visible — an earlier version sorted milestone rows by `dueDate` for display, which meant reordering the template only changed anything for a freshly-seeded item (every milestone defaults to the same due date at creation, so a date sort's stable tiebreak happened to preserve array order); for any item whose milestones already had distinct due dates — i.e. almost anything actually planned out — the reorder silently had no visible effect at all. Array order is now the single source of truth for milestone row order everywhere; due dates are shown as data on each row, not used to decide row order.

If the diff is non-empty **and** at least one item currently has that `categoryId`, `saveCategory()` doesn't save at all yet — it closes the category modal and opens the confirm modal instead, describing the impact in plain terms ("add N milestones and/or remove M milestones... on K items... This cannot be undone"), with the actual save + `applyCategoryMilestoneSync()` call deferred into the confirm modal's `action`. Cancelling that confirm discards the *entire* category edit, including the name field — same as Cancel in the category modal itself, since by the time the confirm modal is showing, the category modal is already closed and there's no "back" state to return to. If there's no items-facing diff (new category, no name/add/remove changes, or a category nobody uses yet), it saves immediately with no confirm step — the confirm modal only exists to gate the destructive/item-affecting path.

`applyCategoryMilestoneSync(categoryId, addedNames, removedNames)` is the actual sync, run once per affected item: names in `removedNames` are filtered out of `it.milestones` by exact name match — **including a milestone that's already Complete with an actual date recorded**, since the user confirmed exactly this tradeoff up front; names in `addedNames` are appended fresh (`{status:'not-started', dueDate: it.dueDate, actualDate: null}`), skipped if the item already has a milestone with that exact name (so re-adding a name you'd already got manually doesn't duplicate it). It finishes by recomputing `it.status` via `computedStatusFromMilestones()` if any milestones remain — a sync that removes an item's single worst (weakest) milestone can genuinely change its computed status, same as any other milestone-list mutation (see "Item status roll-up").

### Quick-add scope items, the Unassigned bucket, and the Pending category

`unassignedSectionHtml()` renders a `.ws-section` pinned above every real workstream's own section (`renderStatusView()` prepends it: `main.innerHTML = unassignedSectionHtml() + sections + noWorkstreamsHint`) — always shown regardless of the current sidebar filter (`visibleWorkstreams()` only affects the real per-workstream sections below it), since an item sitting there doesn't belong to any workstream yet and shouldn't require switching to "All workstreams" to see or triage. It holds every item with `workstreamId == null` (`unassignedItemsSorted()`), and below Editor it's omitted entirely once empty — nothing to show and no way to add anything, so there's no point rendering an empty heading. It still shows (read-only, no add affordance) below Editor once there's at least one item in it. This is also the *only* place a brand-new scope item is created — there's no longer a per-workstream "Add item" button (every workstream's own `.ws-section` lost the one it used to have).

**Adding an item is a deliberately minimal, name-only inline capture — no modal, no workstream picker.** The section's own "+ Add item" button (`onclick="openInlineQuickAdd()"`) swaps in a plain text input in its place (`unassignedQuickAddOpen`, a UI-only module-level flag, not persisted) rather than opening any dialog. `saveInlineQuickAddItem()` (Enter, or blurring the input) creates the item with **`workstreamId: null`** — "Unassigned", the same idea as the Pending category below, just for workstream instead of category — straight into the one category flagged `pending: true` (`pendingCategory()`/`isPendingCategory(categoryId)`, next to `categoryById()`), seeded with that category's own milestone template — just `['Scope Item Confirmed']` — via the normal `milestonesForCategory()`. Both the item's real workstream *and* its real category are decided together, later, once the scope is actually confirmed (see below) — nothing about either is asked up front.

`cancelInlineQuickAdd()` (Escape) discards whatever was typed and closes the input back to the button, unconditionally. Because closing the input this way (either function calls `render()`, which tears the focused `<input>` out of the DOM) fires that same input's own `onblur` right back — which is wired to `saveInlineQuickAddItem()` — both functions flip `unassignedQuickAddOpen` to `false` *before* calling `render()`, and `saveInlineQuickAddItem()`'s very first line is `if (!unassignedQuickAddOpen) return;`. So whichever call happens first (Enter, or Escape's `cancelInlineQuickAdd()`) does the real work; the second call the resulting blur triggers sees the flag already `false` and no-ops instead of reviving or double-creating anything. Blurring with nothing typed is the same "quietly close, nothing created" outcome, just without an explicit key press.

**A stale/unknown `workstreamId` (a deleted workstream, a broken merge, a hand-edited import) now normalizes to `null`/Unassigned too**, not an arbitrary real workstream (`normalizeData()`: `if (it.workstreamId != null && !wsIds.has(it.workstreamId)) it.workstreamId = null;`) — a genuinely intentional `null` is left alone, but a broken reference surfaces in the Unassigned bucket for a human to actually re-triage, rather than silently landing wherever `workstreams[0]` happens to be. Dashboard's per-workstream rollups (`scopedItems = items.filter(it => wsIds.has(it.workstreamId))`) already exclude anything with no real, valid workstream, so Unassigned items simply don't participate in workstream-scoped stats until they're assigned one — consistent with them not really belonging to a workstream yet.

**The out-of-the-box, real/selectable categories themselves come from `DEFAULT_CATEGORIES`** (top of the `<script>` block, see "Categories (Admin mode)" above) — an array of `{name, milestones}`, one per category (Development, Artefact, Integration, Activity), sourced from `Milestone_Lookup_Table.xlsx`. `seedDefaults()`/`normalizeData()`'s zero-category fallback both seed straight from it (`DEFAULT_CATEGORIES.map((c, i) => ({..., order: i}))`), so adding, removing, or reordering an out-of-the-box category only ever means editing this one constant.

**The Pending category is reserved, not a normal user category**, even though it lives in the same `categories` array and Admin's category list (with a "Reserved" badge — `renderAdmin()`). `seedDefaults()` always creates it (right after every `DEFAULT_CATEGORIES` entry, at `order: DEFAULT_CATEGORIES.length`) and `normalizeData()` adds one back (`categories.push(...)`) on any save that predates it or has somehow lost it — the quick-add flow assumes exactly one `pending: true` category always exists. `deleteCategoryFromModal()` refuses to delete it outright (see above), and `openScopeAssignModal()`'s category `<select>` filters it out of the choices — it's a one-way waypoint, never a destination to assign *to*.

**Marking the item's "Scope Item Confirmed" milestone Complete is the trigger that asks what it really is.** This is checked by `maybeOfferScopeAssign(it, prevStatus)` — `prevStatus !== 'complete' && it.status === 'complete' && isPendingCategory(it.categoryId)` — called from both places a milestone's status can change into that state: `cycleMilestoneStatus()` (the board's inline click-to-cycle badge, the normal path for a quick-added item with just one milestone) and `saveItem()` (covers editing the milestone's status via the full item modal's dropdown instead). Capturing `prevStatus` before the mutation and only firing on the actual not-complete-to-complete transition means Applying the resulting modal doesn't re-trigger it on some later unrelated save while the item is still sitting at Complete — it only fires again if the status genuinely leaves and re-enters Complete.

`openScopeAssignModal(itemId)` populates a Workstream select (preset to the item's current one — nothing is preselected for a still-Unassigned item, since none of the options match `null`) and a Category select (every category except Pending). **It has no dismiss/"Later" option at all — Apply is the only way to close it** (an explicit user request, "do not allow to later in the assigning step"): the modal's own "Later" button is gone, and `scopeAssignModalBg` is deliberately excluded from both the global Escape-key handler and the generic backdrop-click-to-close wiring at the bottom of the script (every other modal in this app has both) — the same "must complete before closing" treatment the role picker's own mandatory first-launch gate already uses (see "The role picker..." below). It still stays reachable afterward through `itemRowHtml()`'s own status badge — not as a "skip for now" affordance any more, but as a page-reload-recovery path (the page could have been closed/refreshed before Apply was ever clicked): whenever `hasRole('editor') && it.status === 'complete' && isPendingCategory(it.categoryId)`, that badge's `onclick` is `openScopeAssignModal(it.id)` instead of the usual `openItemModal(it.id)` (the pencil "Edit" button in `.item-actions` still opens the full modal regardless, unaffected).

**A still-Pending item's category can never be changed through the full item modal either — only `applyScopeCategory()` (i.e. this same scope-assign flow) is allowed to move an item out of Pending**, an explicit user request ("prevent change category from unassigned scope items... only the assignment process triggered by completed can change it"). `openItemModal()` disables `#itemCategorySelect` whenever the item being edited currently has `isPendingCategory(it.categoryId)` true — layered on top of, not folded into, the existing role-based disable loop, since this is conditional on the item's own data rather than on who's looking at it, and stays locked even at Editor/Admin. `saveItem()` enforces the same rule server-side as defense-in-depth: for an existing item that's still Pending, `categoryId` is forced to stay whatever it already was, regardless of what the (disabled, but not un-tamperable) select reports.

**The Workstream select gets the identical lock, for the identical reason — a later, explicit user request** ("do not allow to assign a workstream to a pending scope item"). A still-Pending item's `workstreamId` is always `null`/Unassigned (see above); allowing this select to assign a real workstream ahead of `applyScopeCategory()` would let someone half-triage an item — a real workstream, but still the placeholder Pending category and its single-milestone checklist — outside the one flow meant to set both together. `openItemModal()` disables `#itemWorkstreamSelect` under the same `stillPending` flag the Category lock already computes (no second condition needed), and `saveItem()` mirrors `categoryId`'s own defense-in-depth exactly: for a still-Pending item, `workstreamId` is forced to stay whatever it already was (`editingItemForSave.workstreamId`, always `null`) rather than reading the (disabled) select's value.

**A still-Pending item's one "Scope Item Confirmed" milestone can also never be marked Not Applicable** — a related, later explicit user request. Marking it N/A would clear its Due/Actual dates and freeze its status badge to a plain "N/A" label (see "Not Applicable milestones" below) while leaving it permanently uncompletable, stranding the item in Pending forever with no way to trigger `maybeOfferScopeAssign()` at all — the same reasoning already applied to blocking that milestone's *removal* (see `removeMilestoneRow()`'s own Pending guard, and `renderMilestonesEditor()`'s inert Remove button, described above). Blocked at both toggle sites, board and modal, each the same way: `milestoneRowsHtml()`'s `naEditable`/`renderMilestonesEditor()`'s `naToggleHtml` both additionally check `!isPendingCategory(it.categoryId)` (rendering an inert `<span>` instead of a clickable button, same convention as everywhere else in this grid), and `toggleMilestoneNotApplicable()`/`toggleEditingMilestoneNotApplicable()` each refuse outright as defense-in-depth, mirroring `removeMilestoneRow()`'s own guard exactly. The inert span's *off*-state icon is additionally faded to `opacity:.35`, matching the Remove button's own disabled trash icon right next to it — a user-reported inconsistency (the N/A icon read as fully "on" even while genuinely disabled). The *on* state (a milestone that actually is Not Applicable, viewed below Editor) stays full-strength colored regardless — that's a real status worth staying legible, not a disabled control.

**Actual completion date and External Delivery are hidden outright in the item modal for a still-Pending item too** — a further explicit user request ("remove for unassigned items External Delivery and Actual Completion date"). Neither is meaningful yet: the item hasn't been scope-assigned to a real workstream/category at all, so there's nothing to record an actual finish date against, and "delivered by an external party" isn't a call worth making before the item's real scope is even known. `openItemModal()` computes `stillPending` once, up front (shared with the Category-select lock above), and toggles `#itemActualField`/`#itemExternalDeliveryField` display alongside the Journey-only field hides — same "hide outright, don't just disable" treatment. `#itemExternalDeliverySpocField` is re-asserted hidden immediately *after* `onItemExternalDeliveryChange()` runs (which would otherwise reveal it for the edge case of a Pending item that somehow already has `externalDelivery: true` — an import, a hand-edited file) rather than before, since that call happens later in the same function and would otherwise win. Both fields reappear the moment `applyScopeCategory()` moves the item out of Pending.

**The Pending category's one milestone was renamed from "Scope item confirmed" to "Scope Item Confirmed"** (Title Case) — a cosmetic, explicit user request. It's seeded as a plain name string in two places (`seedDefaults()` and `normalizeData()`'s reseed-if-missing fallback), and nothing in the app branches on the literal string itself (it's never used as a lookup key, only displayed) — so the rename was a two-line data change plus updating comments/tooltip text for consistency, not a schema migration. A pre-existing save with the old lowercase name on an already-created Pending item keeps it as-is (the same "orphaned value is harmless, only new ones get the new name" stance this file already takes elsewhere) — there's no backfill pass for it, since it's cosmetic text, not a value anything compares against.

**That same "nothing matches `null`" gap in `populateWorkstreamSelect()` was a genuine, user-reported bug when it showed up in the *full* item modal instead — `openItemModal()`, not scope-assign.** Editing an already-Unassigned item there and saving *anything at all* — a due date, a name tweak, never touching the Workstream field — silently moved it into `workstreams[0]`: with no `<option>` ever matching a `null` `selectedId`, the browser just defaults an ordinary populated `<select>` to its first option regardless of what the item's real `workstreamId` was, and `saveItem()` read that default straight back out as if the user had actively chosen it. Scope-assign's own copy of this gap (previous paragraph) is fine as-is — forcing a real pick *is* that modal's whole job, an Unassigned item is never staying Unassigned coming out of it. The full edit modal has no such excuse: most edits there have nothing to do with workstream assignment at all. Fixed with a third parameter on `populateWorkstreamSelect(selectedId, elId, includeUnassigned)`: `openItemModal()` passes `true` only when editing an item that's *already* `workstreamId == null`, prepending a matching `<option value="">Unassigned</option>` (`selected`) so the select actually reflects the item's real state instead of silently overriding it; a brand-new item (never Unassigned to begin with — quick-add is the only path into that bucket) and scope-assign's own call both still omit it, unchanged. `saveItem()` reads that empty string back as `document.getElementById('itemWorkstreamSelect').value || null` — every real workstream id is always non-empty, so this only ever converts the Unassigned sentinel back to the same `null` every other Unassigned check in the app already compares against.

"Apply" calls `applyScopeCategory(itemId, workstreamId, categoryId)` — a full swap, not a diff/sync like `applyCategoryMilestoneSync()` (that one reconciles an *existing* category's own template changing over time; this is a one-time jump from the placeholder Pending checklist to a real category's). It sets the item's `workstreamId`/`categoryId` (out of `null`/Unassigned, into a real workstream), tombstones the discarded "Scope Item Confirmed" milestone the same way any other removed milestone is (`deletedMilestoneIds`), replaces `it.milestones` wholesale via `milestonesForCategory(categoryId, it.dueDate)`, and recomputes `it.status`/plan dates from that fresh (all not-started) checklist.

## Journeys

**A Journey is a second item *type* — an explicit user request ("build another type next to scope item: 'Journey'") — but not a second data structure.** It's a plain entry in the same `items` array as every scope item, distinguished only by `itemType: 'journey'`. That reuse is deliberate and load-bearing: a Journey gets the row's Edit/Delete actions and `itemRowHtml()`'s entire rendering machinery for free, with no parallel implementation to keep in sync.

**A Journey has no category, no workstream, and no milestone checklist at all — an explicit user simplification** ("do not add milestones to it... you can remove the Journey category completely"), stripping out what an earlier version of this feature had: a reserved "Journey" category with a fixed 4-milestone template and a milestone-completion trigger. `categoryId` is `null` for a Journey (every other item still needs a real one) — `normalizeData()`'s categoryId backfill runs *after* the `itemType` backfill specifically so it can skip a Journey outright rather than repairing its `null` into `categories[0].id` the way a plain item's genuinely-missing categoryId is. The item modal hides its Workstream (`#itemWorkstreamField`), Category (`#itemCategoryField`), and Milestones (`#itemMilestonesField`) fields outright whenever the item being created/edited is a Journey — not left unpopulated, disabled, or showing an empty editor with nothing to add, since none of the three apply. `saveItem()` forces both `workstreamId` and `categoryId` to `null` for a Journey regardless of whatever the (hidden) fields report.

**A Journey is never assigned to a workstream at all — an explicit user correction** ("Journey should not be assigned to workstreams. They are overarching"). `workstreamId` is always `null` for a Journey, and unlike an Unassigned scope item (`workstreamId: null` too, but meaning "awaiting triage" — see "Quick-add scope items..." above), a Journey's `null` is permanent, not a placeholder. Two consequences follow directly:
- `unassignedItemsSorted()` (the Planning board's own Unassigned bucket) explicitly excludes `itemType === 'journey'` even though both share `workstreamId == null` — a Journey belongs in its own dedicated view, not mixed into a bucket that's specifically for scope items awaiting a real workstream. `buildScopeItemsSheet()` (the Excel export's Scope Items sheet) excludes it from its own Unassigned section the same way, for the same reason.
- **Journeys mode shares `#scopedBody`'s sidebar+main shell with Planning/Review/Dashboard, but `renderJourneys()` still ignores the shared `filterWorkstreamId` selector entirely** — it always lists every Journey in one flat list (`allJourneys()`, sorted by `order`), not one section per workstream the way Planning's own board is. Journeys mode used to get its own sidebar-less container (`#journeysBody`) and its own topbar button (`#tabJourneys`, sitting outside `.view-tabs` next to `#tabAdmin`) — the same "not workstream-scoped, so a shared sidebar filter would be a dead, misleading control" reasoning Admin mode still uses (see "Modes" above). A later, explicit user request ("move journeys in the left navigation bar, separate it from workstreams") moved its entry point into the sidebar instead, as its own section — a `sidebar-label` "Journeys" heading plus a single `#journeysNav` row (`renderSidebar()`, reusing the `.ws-row`/`.ws-row-name`/`.ws-row-count` classes a workstream row uses, just wired to `setMode('journeys')` instead of `setFilterWorkstream()`, with a route icon in place of a color dot and a live `allJourneys().length` count) — not a per-Journey list, since Journeys mode itself is still one flat list with nothing to scope by. A follow-up request ("move journey over workstream") swapped the two sections' order in the static HTML shell — Journeys now sits first, Workstreams below it — with no change to `renderSidebar()`'s own logic, since both sections are independent containers (`#journeysNav`/`#wsList`) filled by the same function regardless of their position in the markup. Since the entry point genuinely lives in the sidebar now, Journeys mode had to move into the shared shell alongside it (a sidebar visible only while showing its own, now-unreachable nav button would be pointless) — `render()`'s `scopedBody` visibility check dropped its `mode === 'journeys'` branch, and `renderJourneys()` now writes into the shared `#main` like the other three. This originally reopened the exact "dead, misleading control" concern the original sidebar-less design was written to avoid — the workstream list stayed visible, and clickable, while Journeys mode was showing, with clicking one changing only `filterWorkstreamId` (and that row's own highlight) with no visible effect on the still-showing Journey list — but two later, explicit user requests closed that gap: clicking any workstream row (or "All workstreams") now always switches to Dashboard scoped to that selection regardless of the current mode (`selectWorkstreamFromSidebar(id)`, see "The shared workstream selector" above), and neither the "All workstreams" row nor a specific workstream row shows as `active` while Journeys mode is showing (`renderSidebar()`'s `inWorkstreamScope = mode !== 'journeys'` gates both active-class checks) — a workstream row staying visually highlighted after switching to Journeys, where nothing on screen is actually scoped to it any more, read as a bug in its own right. `filterWorkstreamId` itself is left untouched by the mode switch (only its visual highlight is suppressed), so the same workstream reads as selected again on switching back to Planning/Review/Dashboard. `#journeysNav`'s own `.ws-row` sets its `active` class directly from `mode === 'journeys'` rather than through `render()`'s generic `MODES.forEach` id-toggle loop (which now explicitly excludes `'journeys'`) — that loop assumes a static `#tab<Mode>` element already sitting in the topbar HTML at first render, which no longer describes this row, since it's rebuilt fresh by `renderSidebar()` on every call anyway.

**Creating a Journey is a name-only inline capture, matching the Unassigned section's own "+ Add item" quick-add exactly** (`openJourneyQuickAdd()`/`cancelJourneyQuickAdd()`/`saveJourneyQuickAddItem()`, `journeyQuickAddOpen` module-level UI flag — see "Quick-add scope items, the Unassigned bucket, and the Pending category" above) — an explicit user request, replacing `renderJourneys()`'s own "+ Add Journey" button opening the full item modal (`openItemModal(null, null, 'journey')`). A Journey has nothing else worth asking for up front anyway (no workstream, no category, no milestones — see below), so the modal was never collecting more than a name here in practice; this just skips opening it. `saveJourneyQuickAddItem()` builds the same shape `saveItem()`'s own Journey-creation branch does (`itemType:'journey'`, `workstreamId`/`categoryId` forced `null`, no milestones, default green tags, `'not-started'` status), including the same `items.filter(i => i.workstreamId === null).length` order computation — so a Journey created either way sits at a comparable position. `openItemModal(null, null, 'journey')` itself is untouched and still reachable — it's still what editing an *existing* Journey opens (via the row's own Edit pencil), and its `presetItemType` parameter still exists for that path — only the creation entry point moved. `editingItemType` (module-level, `'scope'` | `'journey'`) is still the single source of truth `openItemModal()` sets for both the new-item and edit-existing-item cases (`it ? it.itemType === 'journey' : presetItemType === 'journey'`) and that `saveItem()` reads back (captured into a local `savingJourney` before `closeItemModal()` resets it back to `'scope'` for next time) — used to force `categoryId`/`workstreamId` to `null` regardless of what the (hidden) fields report, and, only on the "creating new" branch, to stamp `itemType` itself (never part of the shared `data` object also used for edits, the same "brand-new-only default, never resets on a plain re-save" treatment `itStatus`/`businessStatus`/`budgetStatus` already get).

**The row badge**: `itemRowHtml()`'s Name cell gets a small `fa-route` icon prefix (`.journey-type-badge`, `journeyBadgeHtml`) whenever `it.itemType === 'journey'` — not a dedicated grid column, since a Journey is a plain item under the hood and this is the only thing telling its row apart from an ordinary scope item's wherever the two might appear in the same list.

**A Journey connects to *existing* scope items — the reverse of an earlier version of this feature, which instead decomposed a Journey into brand-new ones.** `item.journeyId` (`String|null`) is the link — set on the *scope item*, pointing at the Journey it belongs to, so one Journey can have many connected scope items but a scope item belongs to at most one Journey at a time. `connectedScopeItems(journeyId)` returns every item whose `journeyId` matches, sorted by `order`. Since a Journey has nothing of its own to trigger a modal from (no milestones — see above), connecting it is a plain, always-available standing action rather than something that auto-pops up: `itemRowHtml()`'s `connectBtnHtml` adds a link icon (Editor+) to `.item-actions`, right next to the drag handle, whenever `it.itemType === 'journey'`, wired to `openJourneyConnectModal(it.id)`.

**The connect modal** (`journeyConnectModalBg`) lists every scope item not already claimed by a *different* Journey, grouped by workstream (plus an "Unassigned" group) the same way Planning's own status board is — familiar structure rather than an undifferentiated flat list. Each row is a checkbox, checked when `it.journeyId` already equals the Journey being managed. **`renderJourneyConnectList()`'s own candidates filter is `itemType !== 'journey'`, not `=== 'scope'`** — a user-reported bug ("linking scope items does not show all available scope items") traced to the stricter form excluding any item whose `itemType` hadn't been backfilled yet, since only `normalizeData()` (load/merge/import — see "Data integrity" below) ever does that backfill, not a plain `save()`. The concrete case: `saveInlineQuickAddItem()` (see "Quick-add scope items..." below) never stamped `itemType`/`journeyId` on the item it created at all, so a scope item quick-added earlier in the same session stayed invisible here until the next full reload. Fixed on both ends — `saveInlineQuickAddItem()` now stamps `itemType: 'scope', journeyId: null` explicitly, matching every other item-creation path in this file (`saveItem()` always sets `itemType` at creation) — and the filter itself switched to the same defensive `!== 'journey'` form `unassignedItemsSorted()`/`buildScopeItemsSheet()` already use, so an item that somehow still arrives with no `itemType` (an old import, a hand-edited file) is included here too rather than silently dropped from this one picker. Unlike the item modal's own "detached working copy, committed on Save" editors, this one writes straight to `items` the instant a checkbox changes (`toggleJourneyConnection(itemId, checked)` sets `it.journeyId` to the Journey's id or `null` and immediately `save()`s) — there's no natural "row" to stage here (the list is just every existing scope item), and every toggle is trivially reversible by unchecking again, so a deferred commit wouldn't actually protect against anything. `toggleJourneyConnection()` calls the top-level `render()` (so the Journeys/Planning views underneath stay current) and then re-renders the modal's own list separately (`renderJourneyConnectList()`) — `render()` doesn't reach into an open modal's own body, and a just-toggled item might now need to disappear from (or appear correctly checked in) the candidate list itself. "Done" (`closeJourneyConnectModal()`) just closes the modal — there's nothing pending to discard, every toggle already committed.

**The link is surfaced, read-only, on the connected scope item's own modal** — `itemJourneyLinkField`/`itemJourneyLinkBadge`, shown whenever `it.journeyId` resolves to an existing item, right below the Name field and above Workstream/Category. It's purely informational: nothing in the item modal itself ever writes to `journeyId` — the only place that ever does is `toggleJourneyConnection()`.

**A Journey's own row is expandable, the same chevron interaction a scope item's milestone checklist already uses — just showing its connected scope items instead, since a Journey has no checklist of its own.** `itemRowHtml()`'s chevron is normally only clickable when an item has at least one milestone (`total`); for a Journey it's clickable unconditionally (`expandable = total || isJourney`), even with zero connections, since there's no other on-row hint that expanding it does anything. `toggleItemExpanded()` — the same function, and the same `expandedItemIds` set, milestone checklists already use — drives it; no Journey-specific expand state was needed. A Journey with nothing connected yet shows a plain "No scope items connected yet." placeholder row rather than an empty list, so expanding one that hasn't been connected to anything still visibly confirms there's nothing there (as opposed to looking identical to a collapse). The row's own `milestone-count-badge` cell, empty for a zero-milestone scope item, instead shows the connected count for a Journey ("N scope items") whenever it's non-zero — the same "always a real element" column-alignment discipline every other cell in this row already follows (see "Column layout is a real CSS grid" above), just with Journey-specific content.

**A connected scope item's sub-row is a real `itemRowHtml()` row, not a bespoke summary line — an explicit user request ("show scope items like this under a journey"), replacing an earlier version that rendered a custom, stripped-down Scope Item/Due/Workstream/Status line via now-deleted `connectedItemsHeaderHtml()`/`connectedItemsRowsHtml()` functions.** `itemRowHtml(it, reviewCycle, viewOnly)` gained a third parameter for this: `subRows` branches on `isJourney` and, for a Journey, maps `connected.map(ci => itemRowHtml(ci, null, true))` — each connected item rendered through the exact same function that renders every ordinary Planning row, just forced read-only. This is safe from infinite recursion since a connected item is always `itemType: 'scope'` (the connect modal only ever offers scope items), so its own `isJourney` check is always false. Three things follow from reusing the real row rather than a summary:
- **Stays collapsed by default** — reusing `itemRowHtml()` means a connected item's own chevron/expand state is real too (governed by the same `expandedItemIds` set), so its own milestone checklist, if it has one, doesn't unfold automatically just because the parent Journey did; a user has to expand it separately, same as anywhere else in the app.
- **`viewOnly`, not just `reviewCycle`'s partial read-only mode, forces every editing affordance off regardless of role.** `const editable = !viewOnly && hasRole('editor');` (in `itemRowHtml()`, `milestoneRowsHtml()`) is the single flag every interactive control in these rows now checks instead of calling `hasRole('editor')` directly — the IT/Business/Budget tag badges, the inline Start/Due date pills, and the Actions cell (drag handle, Connect, Edit, Delete — all omitted, `.item-actions` rendered as a real-but-empty span for the usual column-collapse reason) all fall back to their existing below-Editor read-only rendering, just unconditionally. This is a distinct concept from `reviewCycle`'s own partial read-only mode (which still leaves Actual dates and the milestone status badge editable, plus adds a review-confirm column) — the two parameters are never passed together in current usage.
- **"MS Req." is omitted, not just disabled, when a connected item's own milestones are expanded.** `milestoneHeaderHtml(reviewCycle, viewOnly)`'s "MS Req." label becomes an empty string (the `<span>` cell itself stays, per the same column-alignment invariant) when `viewOnly`; `milestoneRowsHtml()`'s Not Applicable toggle button is omitted outright (not rendered as an inert span the way it is below Editor) for the same reason — there's nothing to toggle in a read-only context, so unlike the tag badges/date pills (which still show their value, just not editable) this control has no value worth showing at all.

**The Journeys list overrides `--item-grid-cols` for its own container, scoped via a `.journeys-list` wrapper class, rather than changing the shared global default Planning/Review still depend on.** A user-reported bug — "action item[s] reach out of the border" — traced (via direct `getBoundingClientRect()` measurement) to `.item-actions` being a plain flex row with no width cap: at anything narrower than roughly 1150px, its 4 icons (drag/connect/edit/delete — one more than a plain scope item's row ever has, thanks to Connect) overflowed the shared grid's 56px Actions track, and neither `.item-row` nor `.ws-section` clips overflow (see "Status board" above), so the icons visibly spilled past the card's own right edge instead of being hidden or scrolled to. Two of the shared grid's tracks (the old Owner column, one blank spacer) are always empty on every row in this view — neither a Journey nor a connected scope item ever puts anything in them — so `.journeys-list { --item-grid-cols: 20px minmax(140px,1.3fr) 10px 90px 190px 10px 115px 100px 90px 120px; }` shrinks those two (160/20 → 10/10) and spends the reclaimed width on a wider Actions column (56 → 120px), leaving Milestone/Due/Actual/Status at their original widths since a connected item can still expand its own real milestone checklist underneath. (This override predates two later, unrelated column changes to the shared default grid — the Milestones-count badge moving from column 3 to column 4, and the old "Actual" placeholder column being removed outright — both applied here too, in step with `--item-grid-cols`' own current 10-column shape; see "Column layout is a real CSS grid" above.)

**A Journey's own "end date" (and start date) is computed live, at render time, from every connected scope item's own milestones — never persisted, never manually editable.** `computeJourneyDateRange(journeyId)` flattens every non-`notApplicable` milestone's `dueDate`/`actualDate` across `connectedScopeItems(journeyId)` (falling back to a connected item's own `startDate`/`dueDate` when that item has no milestones at all) and returns the earliest/latest as `{startDate, dueDate}`, or `null` if nothing connected has a date to contribute yet. This is deliberately *not* persisted onto the Journey's own `startDate`/`dueDate` the way an ordinary item's computed range is written back at save time (see "Item plan date range roll-up" above) — persisting it would mean hooking every place a connected item's own dates could possibly change (its own milestone edits, a category-template sync, being connected/disconnected from the Journey) just to keep a cached value from going stale, for no real benefit over just computing it fresh; the same "no persisted state, always fresh at render time" choice Dashboard mode already makes, for the same reason. Both `itemRowHtml()`'s `planDatesHtml` (a computed-badge display, same visual treatment as an ordinary item's own milestone-derived range, showing "—" when nothing connected has a date yet) and the item modal's own Plan-dates section (`updateItemStatusFieldMode()`, extended with a Journey-specific branch) read from this function rather than the item's own stored fields. **Status, like Plan dates, is also computed live from connected scope items — a later, explicit user request** ("Journey should calculate their status based on the status of the included scope items"), reversing this doc's own earlier stance (a plain manual dropdown, since a Journey has no milestones of its own to roll a status up from). `computeJourneyStatus(journeyId)` is `computedStatusFromMilestones()`'s counterpart for a Journey: the same weakest-link reduce over `STATUS_SEVERITY`, just over `connectedScopeItems(journeyId)`'s own already-resolved `status` fields instead of a milestone list — a Journey with any Red-status scope item connected reads Red overall, same "one active problem always surfaces" reasoning. Returns `null` when nothing is connected yet, same convention as `computeJourneyDateRange()`; every caller falls back to `'not-started'`, the same neutral default a brand-new item already starts at. Deliberately never persisted onto the Journey's own `status` field either, for the identical "avoid hooking every place a connected item's status could change" reason `computeJourneyDateRange()` isn't — `saveItem()` writes whatever `status` a Journey already had (or `'not-started'` for a brand-new one) rather than reading the now-hidden `#itemStatusSelect`, and that stored value is simply never read back for display; `itemRowHtml()`'s status badge and `updateItemStatusFieldMode()`'s modal badge both call `computeJourneyStatus()` directly instead of `it.status`. `updateItemStatusFieldMode()`'s Status half now checks the same `hasMilestones || isJourney` condition its Plan-dates half already used, so both fields move in lockstep again for a Journey too, the same way they always have for every other item — the one difference is *which* source each is computed from (`editingMilestones` for a plain item's own checklist, `connectedScopeItems()` for a Journey's connections). A brand-new, not-yet-saved Journey has no id to look up connections by, so both its Status and Plan-dates badges show their respective "nothing yet" fallback (`'not-started'` / "No connected scope items yet") until it's actually saved.

**`normalizeData()` backfills** both new fields the same way every other item field is self-healed: `itemType` resets to `'scope'` unless it's already exactly `'journey'` (an unrecognized/legacy value falls back safely, same as `status`/`categoryId`); `journeyId` resets to `null` unless it resolves to an existing item that's actually `itemType === 'journey'` — a reference to a deleted item, or one that's no longer a Journey, is cleared rather than left dangling, the same orphaned-reference treatment a stale `workstreamId` already gets.

## Review mode

A review cycle is scoped to exactly one workstream (`activeReviewCycle(wsId)` finds the one cycle for that workstream with both `completedAt` and `cancelledAt` still `null` — `startReviewCycle()` is a no-op if one's already active, so there's never more than one open cycle per workstream at a time). Review mode has no workstream picker of its own any more — it reads the shared `filterWorkstreamId` (see "The shared workstream selector" above), which is guaranteed non-null whenever Scope Item Review specifically is showing (`reviewTab === 'scope'`) — the Action Log tab is the one exception, deliberately usable with no workstream selected at all (see "The shared workstream selector" above and "Action Log" below). The shared sidebar (`renderSidebar()`, `#wsList` — same one Planning and Dashboard use) shows each workstream a small badge regardless of which of the three modes is active: amber "In review" if it has an active cycle, red "Overdue" if `isReviewOverdue(w.id)` (no completed cycle in the last `REVIEW_STALE_DAYS` (30) days, or never reviewed at all), otherwise no badge — so review staleness is visible while planning, not just while reviewing. **`isReviewOverdue(wsId)` first checks whether the workstream has any scope items at all** (`items.some(it => it.workstreamId === wsId)`) **and returns `false` immediately if not** — an empty, just-created workstream has nothing to review yet, so it shouldn't read as "Overdue" from the moment it's added (every item is backfilled with a `startDate`/`dueDate` the instant it's created, by `normalizeData()`, so "no items" and "no items with any dates" are the same condition here — there's no in-between state of an item existing with no dates to check for separately). This guard is shared by both consumers of `isReviewOverdue()` — the sidebar badge and Dashboard's "Overdue for Review" card below.

**Confirmation is milestone-level, not just item-level.** An item with at least one milestone has *no independent stored confirmation at all* — `isItemConfirmedInCycle(cycle, it)` derives it as confirmed only once every one of `it.milestones` has its own entry in `cycle.milestoneConfirmations` (`toggleMilestoneConfirm(cycleId, milestoneId)`, a plain toggle). This mirrors the rest of the app's "computed vs manual" pattern (status, plan dates): there's no separate item-level flag that could drift out of sync with its milestones' actual confirmation state, so "a scope item can only be confirmed once all its milestones are confirmed" is an invariant by construction, not something enforced by a check that could be bypassed. `toggleConfirmAllMilestones(cycleId, itemId)` is a bulk convenience, not a separate source of truth — it confirms every not-yet-confirmed milestone on the item in one click, or un-confirms all of them if every one is already confirmed (same toggle shape). A zero-milestone item still confirms directly via `toggleReviewConfirm(cycleId, itemId)` into `cycle.confirmations`, exactly as it did before milestone-level confirmation existed — there's nothing to derive from.

**A milestone (or zero-milestone item) whose own status is already `'complete'` auto-confirms — no manual click needed, with or without an actual entry in `cycle.milestoneConfirmations`/`cycle.confirmations`.** An explicit user request ("mark completed task as reviewed, no need to review them again"): once something is genuinely finished, a reviewer shouldn't have to re-click through it every single review cycle just to satisfy the "everything confirmed" gate — only milestones/items still actively open need attention. `isMilestoneConfirmedInCycle(cycle, m)` (its signature changed from taking a bare `milestoneId` to the whole milestone object, so it can read `m.status`) checks `m.status === 'complete'` *before* falling back to the stored-entry lookup — a milestone finished long before this review cycle even started, and never explicitly clicked in any cycle, still reads as confirmed today. `isItemConfirmedInCycle()`'s own zero-milestone branch gets the same treatment (`it.status === 'complete' || cycle.confirmations.some(...)`). This is deliberately the same shape as the existing `notApplicable` exclusion just below — "this doesn't need a reviewer's attention" — but for a different reason (genuinely done, vs. genuinely out of scope), so it's a separate check, not folded into the `notApplicable` one.

`toggleConfirmAllMilestones()` needed no logic change at all beyond passing the milestone object through — its existing `if (!isMilestoneConfirmedInCycle(cycle, m))` guard, before pushing a real confirmation entry, now naturally skips an already-Complete milestone the exact same way it already skipped an already-manually-confirmed one, so a bulk "confirm all" never writes a redundant entry for one. **Rendering-wise, a Complete milestone/zero-milestone-item gets its own inert, already-checked indicator** (`milestoneRowsHtml()`'s and `itemRowHtml()`'s review-cell branches both gained a `m.status === 'complete'` / `it.status === 'complete'` case, checked before the normal clickable-toggle branch) rather than the clickable circle a still-open, manually-confirmable milestone/item shows — the same "nothing here needs interaction" treatment `notApplicable` milestones already get in this exact column, just with the filled `fa-circle-check` icon instead of `fa-ban` (it *is* confirmed, not excluded). Only the zero-milestone case gets this treatment at the item level — an item *with* milestones keeps its real, clickable "confirm all" bulk button regardless of whether every underlying milestone happens to already be auto-confirmed, since clicking it in that case is just a harmless no-op, not worth a second inert-rendering branch.

**Completion gate, and why it needs no extra bookkeeping for mid-cycle adds.** `canCompleteReviewCycle(cycle)` checks that *every item currently in `cycle.workstreamId`* is confirmed per `isItemConfirmedInCycle()` — it re-derives the live item (and, for each, live milestone) list each call rather than snapshotting anything when the cycle started. This is what makes both "an item added mid-cycle automatically becomes an unconfirmed blocker" *and* "a milestone added mid-cycle to an already-confirmed item un-confirms it" fall out for free (per the product requirement this was built against): there's no separate "what does this cycle cover" list to keep in sync, so a newly-added item or milestone simply has no confirmation entry yet and the `.every()` checks naturally fail until someone confirms it. The flip side: an item (or milestone) *deleted* mid-cycle just stops being checked (its stray confirmation entry, if any, is harmless orphaned data — never pruned, never causes a crash since nothing indexes into `confirmations`/`milestoneConfirmations` by array position).

`completeReviewCycle(cycleId)` re-checks `canCompleteReviewCycle()` itself (defense in depth — the UI already disables the button via the same check, but the guard lives in the mutating function, not just the render), snapshots the confirmation count (below), and sets `completedAt` — permanent once set, a cycle is never un-completed. The "Complete review" button itself reflects `canCompleteReviewCycle()` beyond just the `disabled` attribute — `.btn:disabled` is explicitly dimmed (`opacity:.4`) rather than relying on default/absent browser styling for a custom-colored button, and its `title` explains why it's inert when it is, so a reviewer isn't left wondering whether the button does nothing because of a bug or because something's still unconfirmed.

**A cancelled cycle isn't tracked at all.** `cancelReviewCycle(cycleId)` goes through the confirm modal (as before), but on confirm it splices the cycle out of `reviewCycles` entirely rather than marking a `cancelledAt` and keeping it — a review that got abandoned isn't a record worth keeping, unlike a completed one. This still frees the workstream for `startReviewCycle()` to open a new one, since `activeReviewCycle()` simply no longer finds a cycle there at all. `cancelledAt` still exists as a field (`normalizeData()` still backfills it, `activeReviewCycle()` still checks `!c.cancelledAt`, `reviewHistoryRowHtml()`'s callers still filter on it) purely so a cycle cancelled *before* this behavior existed — sitting in an older `pulse-data.json` with `cancelledAt` already set — stays correctly excluded from history and can't reactivate; nothing new ever sets that field again.

**History rows freeze a confirmation count at the moment a cycle closes, rather than recomputing it live.** `completeReviewCycle()` calls `snapshotReviewCycleCounts(cycle)` immediately before setting `completedAt`, storing `itemCountAtClose` and `confirmedCountAtClose` on the cycle itself. `reviewHistoryRowHtml()` then shows "X of Y confirmed" from these frozen numbers (omitted entirely for a cycle closed before this field existed — there's no way to know in hindsight what it would have shown). This can't be computed live from current data the way the *active* cycle's progress bar is: `isItemConfirmedInCycle()` derives confirmation from an item's *current* milestones, so a milestone added to an item long after some old cycle closed would otherwise make that closed cycle's history retroactively — and wrongly — show the item as unconfirmed for a review that happened before the milestone even existed. Snapshotting both the numerator and the denominator at close time is what keeps a completed cycle's history entry accurate regardless of anything that happens to the data afterward — including the item or its milestones being edited, or deleted entirely.

**Only the 5 most recent history entries show by default.** `renderReview()` sorts `reviewCyclesForWs(wsId).filter(c => c.completedAt)` newest-first and slices to `HISTORY_PAGE_SIZE` (5) unless `historyShowAllWs` (a `Set` of workstream ids, UI-only, mirroring `expandedItemIds`/`expandedHistoryIds`) has that workstream — `toggleHistoryShowAll(wsId)` flips it. Since the list is already sorted newest-first, `slice(0, 5)` naturally keeps the most recent ones and hides the oldest, so "Show N more" (N = however many are hidden) needs no separate query to know what it's revealing; once fully expanded the same button becomes "Show less" to collapse back, symmetric with every other expand/collapse control in the app.

**History also shows the actual changes made during the review, not just a count.** `logReviewChange(workstreamId, itemName, milestoneName, changeText, extra)` appends an entry to whichever cycle is currently `activeReviewCycle()` for that workstream — a no-op if none is active, which covers the overwhelming majority of edits made outside a review. `changeText` is always a plain-language fallback (used as the row's `title` tooltip); `extra` carries one of three structured shapes that `reviewHistoryRowHtml()` renders as something more visual than text:
- `tagChange: {field, oldValue, newValue}` — set by `cycleItemAttr()`. Rendered as the tag's own icon (`TAG_FIELD_ICONS[field]`) shown *twice*, once colored by `oldValue` and once by `newValue`, with an arrow between — the icon's shape identifies which of IT/Business/Budget changed, and seeing both colors side by side (not just the new one) makes the shift itself legible at a glance.
- `statusChange: {oldValue, newValue}` — set by `cycleMilestoneStatus()`. Rendered the same way but with two `.status-badge` pills (label + color, `cursor:default` overriding the base class's pointer cursor since these aren't clickable) instead of an icon — the same badge shown in the row itself, old value then new.
- `dateChange: {label, oldValue, newValue}` — set by `updateMilestoneDateField()`/`updateItemDateField()`. Rendered as two real `<input type="date" disabled>` fields with an arrow between, not formatted text — "no editable" is enforced by the browser itself refusing input, and it's the same date-field look used everywhere else in the app rather than a bespoke text format. For an actual-date change, the "former" value is whatever actual date was already there, or — the first time one's set — the milestone's own plan (due) date, so there's always a real reference point rather than "set to X" in isolation; clearing an actual date instead logs the plain `changeText` `"Cleared actual date"` with no `dateChange` at all (there's no meaningful before→after to show as fields).

Each entry's label is `"<item> — <milestone>"` for a milestone-level change (`e.milestoneName` set) or just the item name for an item-level one (tag/item-date changes have no milestone) — the same `"<item name> — <milestone name>"` convention Dashboard's attention feed already uses, so a milestone-level change is never ambiguous about which scope item it belongs to.

**Displayed order follows the scope item's own milestone order, not the order changes were logged in.** Every entry also carries `itemId`/`milestoneId` (stable ids, alongside the display-only `itemName`/`milestoneName`) purely so `orderedChangeLog(changeLog)` can re-sort for display: it groups entries by `itemId` (preserving each item's first-appearance order, so different items' changes are never interleaved) and, within one item's group, sorts by that milestone's *current* index in `it.milestones` — the same order the row itself displays them in. A reviewer jumping around a checklist rather than working straight down it would otherwise produce a change log that reads out of sequence relative to the item it's describing. An item-level entry (no `milestoneId`) or one whose milestone can no longer be found (deleted since) sorts to the front of its group (`indexOf` returns `-1` for both), with ties broken by original logged order since `Array.prototype.sort` is stable and there's nothing more meaningful to order them by.

It deliberately fires regardless of whether the edit came from Planning's own rows or Review's — the record is of what changed *while the workstream was under review*, not only edits made through the Review screen specifically. Because it looks up the *active* cycle each time (not one passed in), nothing is ever logged against a cycle that's already completed or cancelled — an edit made afterward just isn't attributed to anything. `reviewHistoryRowHtml()` renders each entry's `changeLog` behind a chevron (reusing `.item-chevron` and the same collapsed-by-default pattern as an item's milestone list, `expandedHistoryIds`/`toggleHistoryExpanded()` mirroring `expandedItemIds`/`toggleItemExpanded()`) since a long-running cycle can accumulate many entries — the chevron itself only renders when `changeLog.length > 0`.

**Meeting minutes attach to a specific (completed) cycle, not the workstream or the programme.** `reviewCycle.minutes` is `null` until someone adds any (backfilled by `normalizeData()`'s reviewCycles pass, and set on the object literal at `startReviewCycle()` time too — both, since a freshly-created-this-session cycle is read before ever round-tripping through `normalizeData()`), otherwise `{summary, actionItems, decisions, nextSteps, importedAt}`. `summary`/`decisions`/`nextSteps` are plain strings; `actionItems` is an array of `{id, text, owner, dueDate}` — see below for why that one's structured and the other three aren't. `reviewHistoryRowHtml()` renders one icon-only `.row-icon-btn` per history row: an outline `fa-regular fa-file-lines` titled "Add meeting minutes" when `c.minutes` is null, or a filled, accent-colored `fa-solid fa-file-lines` titled "View meeting minutes" once it isn't — both call the same `openMinutesModal(cycleId)`, pre-filled from whatever's already there (or blank), so "add" and "view/edit" are the same modal and the same flow, not two separate UIs.

**The modal is one grid, not a form with a paste box bolted on top of it** (`.minutes-grid`, `grid-template-columns: 1fr 1fr`, plain source order so the DOM order *is* the visual order): row 1 is the paste-to-auto-fill box (with its own "Auto-fill" button inside the same cell) beside Meeting Summary; row 2 is Action Items, spanning the *full* width via `.minutes-action-items-field { grid-column: 1 / -1 }` — its three-column table needs the room a half-width cell can't give it; row 3 is Decisions beside Next Steps. Five cells total, laid out to a hand-drawn wireframe the user provided (an earlier iteration also had a same-width "Open Points" field paired with Next Steps in row 3 — dropped in a later revision, see the same wireframe-driven request; **there is no Open Points field anywhere in this app, and it must not come back as one** — confirmed explicitly more than once). The modal itself is a fixed `900px` (not `.modal-wide`, widened from an original `700px` after the paste box grew taller — see below — so the other fields kept comfortable width rather than being squeezed narrower).

**`MINUTES_SECTIONS` recognizes `openPoints`/`attendees`/`discussionPoints` headers, despite there being no field anywhere in this app to put their content in.** Without recognizing one of these at all, that heading in a real source document wouldn't read as a section boundary, so `current` would stay whatever it was before, and everything under it would keep getting appended to *that* section instead of being excluded. `openPoints` was the original case (a real bug report: many minutes templates have an Open Points section between Action Items/Decisions and Next Steps, and it was leaking into whichever of those came first). `attendees`/`discussionPoints` is the same shape of bug, reported later: a narrative-style minutes doc with an "Attendees" list and a "Discussion Points" section, but no literal "Summary" header anywhere, matched *neither* recognized word at all — so `anyHeaderFound` stayed `false` and the "no headers recognized anywhere" fallback (below) dumped the intro paragraph *and* the attendee list *and* every discussion bullet into Summary wholesale ("meeting summary currently takes too much... other sections bleed into summary"). The fix generalizes the same mechanism to all three: `MINUTES_EXCLUDED_SECTIONS` (a `Set` of `'openPoints'`/`'attendees'`/`'discussionPoints'`) are recognized keys in `MINUTES_SECTIONS` (so the header still ends whatever section came before it, and still counts toward `anyHeaderFound`) but have no entry in `parseMeetingMinutes()`'s `buckets` object — the header-match branch skips pushing its own inline "rest" text (`!MINUTES_EXCLUDED_SECTIONS.has(current)` guard) and the per-line push is skipped outright (`if (MINUTES_EXCLUDED_SECTIONS.has(current)) return;`) for every line until the next *real* header. Net effect: content under any of these three is read past and discarded, never stored, never leaked into a neighboring section — and, for a doc like the Attendees/Discussion-Points one above that has no actual Summary/Decisions/Action-Items/Next-Steps header at all, every field correctly ends up empty rather than stuffed with the wrong content, same as any other structured-but-Summary-less document (see "unlabeled lead-in text before the first recognized header is dropped" below) — the unlabeled intro paragraph is still discarded rather than guessed at, since recognizing Attendees/Discussion Points as real headers means this document no longer counts as "no headers recognized anywhere" either.

**The paste box also accepts a dropped file, not just pasted text** — including a real `.docx`, not just plain text. `.minutes-dropzone` wraps `#minutesPasteInput` (`ondragover`/`ondragleave` toggle a `.drag-over` class for the dashed-outline highlight, `ondrop` calls `handleMinutesFileDrop(event)`, `async`); it reads the file as plain text (`file.text()`) unless the name ends in `.docx`, in which case it goes through `extractDocxText()` first. No upload, no network, same local-only spirit as the rest of the app. `#minutesPasteInput` itself is sized (`height: 130px`, up from an original cramped `56px` min-height that clipped its own placeholder after just two lines) so its placeholder — the longest text ever shown in it, explaining both the paste and drop paths — renders in full without needing to scroll; the same `130px` is shared, via `.minutes-grid .field > textarea { height: 130px }`, by Meeting Summary/Decisions/Next Steps, so all four boxes in this modal start out the same size as each other rather than Summary in particular growing lopsidedly taller than its neighbors from manual resizing.

**The raw extracted text is deliberately never shown in the paste box for a dropped file — and, since a small revision, neither is any confirmation text.** `applyParsedMinutesText(text)` — the actual "fill Summary/Decisions/Next Steps/Action Items from this text" logic — is factored out of `parseMinutesPaste()` specifically so `handleMinutesFileDrop()` can call it directly on the extracted text without ever putting that text into `#minutesPasteInput` first. Originally the box was left with a `"✓ ${file.name} processed"` string written into its `value` as a confirmation — since replaced with `setMinutesDropzoneStatus(filename)`, which instead leaves the box genuinely empty (so its placeholder — or a fresh paste — is usable immediately) and shows a small `#minutesDropzoneStatus` badge (`<i class="fa-solid fa-circle-check">` plus `${filename} processed`) sitting in normal document flow directly below the textarea — deliberately *not* absolutely-positioned on top of it, an earlier version that visually collided with the placeholder text showing through underneath the badge. `setMinutesDropzoneStatus(null)` hides the badge; it's called from `openMinutesModal()` and `clearMinutesFields()` (so a stale badge from a previous cycle/drop never lingers into a fresh one) and from `#minutesPasteInput`'s own `oninput` (so typing/pasting something new after a drop immediately drops the now-stale "processed" claim). This matters most for `.docx`: the raw extracted text (every paragraph and table row, `\n`-joined) can be long and not particularly meaningful to read as a wall of text, so showing it would just be noise the user has to scroll past. `parseMinutesPaste()` (the manual paste-then-click flow) still shows the raw pasted text in the box as before, and never touches the badge — that path is about typing/pasting text a person is meant to see and edit, a genuinely different case from "silently expand this file I just dropped."

**`.docx` support is a hand-rolled, minimal zip reader plus native decompression — deliberately no library, matching this app's zero-dependency design.** A `.docx` is a zip archive; its real text lives in a compressed `word/document.xml` entry, which is why just reading the raw file as text produces binary/XML noise instead of anything readable. `zipFindEntry(buf, entryName)` is *not* a general-purpose zip library — it only locates one named entry, by reading the End Of Central Directory record (scanned backward from the end of the file, since it can be followed by up to a 65535-byte comment — Word-generated files have an empty one, so this is normally a one-iteration scan) to find the central directory, then walking central directory entries (46-byte fixed header each) until it finds `word/document.xml`, then re-reading the name/extra-field lengths from that entry's own *local* file header (offsets 26/28, fixed 30-byte header) — those aren't guaranteed to match the central directory's copy — to compute exactly where the entry's data bytes start. `inflateRaw()` hands the compressed bytes to `DecompressionStream('deflate-raw')` (native in Chrome/Edge, zip's compression method 8 is plain deflate with no zlib/gzip wrapper, which is exactly what `'deflate-raw'` expects) — method `0` (stored/uncompressed, rare but legal) skips this and uses the bytes as-is. Legacy binary `.doc` (not `.docx`) isn't a zip file at all and isn't supported — there's no parser for that older format here, and none of this ZIP/XML machinery would even locate a comment file inside it.

**`extractDocxText()` walks the document body in order rather than just grabbing every `<w:p>` in the file — a real Word *table* (the exact shape an Action Items list is usually authored in) would otherwise get silently flattened wrong.** Every table cell (`<w:tc>`) has its own paragraph(s) too, so naively collecting every `<w:p>` in document order turns one 3-column row into 3 separate one-column lines — this was a real bug, caught by a user pasting an actual Word table and getting Owner/Due Date back as blank again despite the tab-separated-text path already working. The fix: iterate `body`'s *direct* children only — an ordinary `<w:p>` becomes one line (`docxParagraphText()`, joining that paragraph's `<w:t>` run texts with no separator; a manual mid-paragraph `<w:br/>` isn't distinguished from a plain space, an acceptable tradeoff since a real section header is always its own paragraph, never a mid-paragraph break); a `<w:tbl>` becomes one line per `<w:tr>`, its cells joined with a **real tab character** (`docxTableRowsToText()`) — deliberately the same shape `linesToActionItems()`/`splitActionItemLine()` already expect from a tab-separated Excel/Word clipboard paste, so a table dropped in as a `.docx` and one pasted as plain text both funnel through the identical downstream parsing. A cell containing more than one paragraph joins them with a space (still one cell's worth of text, not multiple table rows).

**List numbering (bullets *and* real numbers/letters/roman numerals) is reconstructed properly, not flattened to a bullet.** A list item's rendered marker (`"•"`, `"1."`, `"a)"`, `"iii."`) is never part of its `<w:t>` run content — Word computes it at render time from the paragraph's numbering properties (`<w:pPr><w:numPr><w:numId/><w:ilvl/></w:numPr></w:pPr>`) plus a *second*, separate zip entry, `word/numbering.xml`, which maps `numId` → `abstractNumId` → per-level `{numFmt, lvlText}`. `parseDocxNumbering(arrayBuffer)` reads and parses that file the same way `extractDocxText()` reads `document.xml` (own zip lookup, own inflate if needed) into `{numToAbstract, abstractFormats}`; returns `null` on any failure (missing file, parse error) rather than throwing, so a numbering-info problem degrades a list item to a flat `"•"` instead of failing the whole minutes import. `docxParagraphNumPr(p)` reads a paragraph's own `numId`/`ilvl` (defaulting `ilvl` to `'0'` when absent, matching Word's own default). `docxListMarker(numFmt, lvlText, count)` renders the marker: a `bullet`-format level always renders as a plain `"•"` — never the literal `lvlText` character, which for a real bullet level is typically a private-use-area codepoint meant to be displayed in a symbol font (Wingdings), so using it raw outside that font would show the wrong glyph entirely — every other format substitutes `formatListCounter(numFmt, count)` (`decimal`/`lowerLetter`/`upperLetter`/`lowerRoman`/`upperRoman`, via `toLetterSequence()`/`toRomanNumeral()`) into `lvlText`'s own `%1`-style template (e.g. `"%1."`, `"(%1)"`). `makeListCounterTracker()` closes over one `{numId:ilvl -> count}` map and increments per call, mirroring Word's own top-to-bottom numbering — a shallower-level item resets every deeper level's counter for that same list (Word's usual restart-on-outdent behavior for the common case; true `w:lvlOverride`/`startOverride` document-level customizations on top of the base numbering definition aren't modeled, an accepted gap for meeting-minutes-style lists, which are usually flat or one level deep at most).

Unlike the rest of the `.docx` pipeline, all of this numbering logic *is* unit-tested, despite the missing `DOMParser` in the JXA harness: `toRomanNumeral()`/`toLetterSequence()`/`formatListCounter()`/`docxListMarker()`/`makeListCounterTracker()` are all plain JS with no DOM dependency at all, and `docxParagraphText(p, numbering, getNextCount)`/`docxParagraphNumPr(p)` only ever call `p.getElementsByTagName(...)` (and, on what that returns, `.getAttribute()`/`.textContent`) — a plain object-literal graph (`fakeDocxParagraph()`/`fakeAttrEl()` in `tests/cases/review.test.js`) stands in for real DOM elements well enough to exercise the real logic, with a hand-built `numbering` object (plain `{numToAbstract, abstractFormats}`, no DOM needed there either) standing in for a real `parseDocxNumbering()` result. Only `parseDocxNumbering()`/`extractDocxText()` themselves — the parts that actually touch `DOMParser`/`zipFindEntry`/`inflateRaw` — remain untested for the reasons already documented above.

**Testing caveat**: none of the drag-and-drop or `.docx` path is exercised by the test suite — the JXA harness has `ArrayBuffer`/`DataView` (so `zipFindEntry()`'s pure offset arithmetic *could* theoretically run) but not `TextEncoder`/`TextDecoder`/`DecompressionStream`/`DOMParser`, all of which real usage depends on, and there's no real `DataTransfer`/`File` to construct a drop event from either. This was verified correct by careful manual review against the ZIP spec (APPNOTE.TXT) rather than by a test — if this ever misbehaves, suspect the EOCD-comment-length scan range or the central-vs-local header field mismatch first, since those are the two spec details most zip-reading code gets subtly wrong.

`parseMeetingMinutes(text)` is what "processing" a pasted paste means here — **there is no AI/network call anywhere in this app**, this is a small heuristic line-scanner: it walks the pasted text line by line, and a line that (after stripping leading `#`/`*`/`_`/`>`/`-` decoration, so `## Summary` or `**Decisions**` still match) starts with one of `(meeting|executive )?summary`/`action item(s)`/`decision(s)`/`next step(s)`/`open point(s)`/`(meeting )?attendees`/`discussion (points)?` — optionally followed by a colon/dash and more text on the same line — begins a new section and everything that follows belongs to it, until the next recognized header (the last three of those have no field of their own and are discarded outright — see `MINUTES_EXCLUDED_SECTIONS` below). `summary`'s own pattern optionally accepts a leading `meeting` or `executive` specifically so a paste headed "Meeting Summary" (the modal's own label) or "Executive Summary" (a common real-world minutes-template heading — user-reported: their source documents use one or the other) still matches; the two prefixes are mutually exclusive alternatives, not stackable ("Meeting Executive Summary" isn't a real heading anyone writes, so there's no need to match it). **Summary only ever contains text that was genuinely under a Summary/Meeting Summary header** — unlabeled lead-in text before the first recognized header is dropped, not folded into Summary (an explicit user correction: "meeting summary should only include the summary" — a paragraph of context above a "Decisions" header isn't necessarily the summary). The one exception is a paste with *no* recognizable headers anywhere (`anyHeaderFound` stays `false`) — there's nowhere else for that text to go, so the whole paste becomes Summary rather than silently vanishing. **A line containing a tab or `|` is never treated as a section header, full stop** — a pasted table's own column-header row (`Action Item<TAB>Owner<TAB>Due Date`) would otherwise itself match the `actionItems` pattern and get parsed as *another* section boundary, corrupting everything after it; table rows only ever get bucketed as plain content under whatever section is currently active. `parseMeetingMinutes()` always returns `actionItems` as a single joined string bucket, same as the other three — `linesToActionItems(text)` is the separate step that turns that bucket into table rows. **Line endings are normalized (`text.replace(/\r\n?/g, '\n')`) before ever splitting on `\n`** — a user-reported bug ("meeting minutes parsing does not work"), traced to content pasted from Word/Outlook (which use CRLF) leaving a literal `\r` embedded at the end of every stored line except the last one in a multi-line section: each non-header line is pushed as `rawLine` into its bucket as-is, and the final `join(lines) => lines.join('\n').trim()` only trims the *outer* edges of the whole joined string, not each individual line — so an interior `\r` survived straight into the saved Summary/Decisions/Next Steps/Action Items text without ever being visible in a plain read of the value.

**`parseMinutesPaste()`/`handleMinutesFileDrop()` both show a toast on their empty/no-op paths now, rather than silently doing nothing** — the other half of the same bug report. Clicking "Auto-fill" with nothing pasted yet, or dropping something that isn't a real file (dragged text, a link), used to just return with zero feedback of any kind — indistinguishable from the control being broken outright, since every *other* no-op guard in this modal (the role gate, `saveMinutes()`'s own "nothing to save") already showed one and these two didn't. `showToast('Paste some meeting notes into the box first', true)` and `showToast("That drop didn't contain a file", true)` respectively.

**`linesToActionItems(text)` extracts Owner/Due Date whenever the source had real column structure, and only falls back to "whole line as text" when it doesn't.** Free-form prose genuinely can't be parsed this way (minutes phrase it too inconsistently — "Alice — due Friday", "[Bob] 08/01", "Action: …" — there's no reliable rule), but the single most common real case isn't prose, it's a pasted *table*: copying an actual table out of Excel/Word/Outlook puts tab-separated plain text on the clipboard (one row per line), and a markdown table (`| a | b | c |`) is pipe-separated. `splitActionItemLine(line)` checks for a tab first, then `|` (trimming each cell, and for the pipe form dropping only the empty cells at the very edges — `| a | b | |` keeps its genuinely-empty middle-last cell), falling back to `[line]` (one column) if neither delimiter is present — this is what makes the earlier "no reliable way to parse it" case still degrade gracefully to text-only rows instead of erroring. `looksLikeActionItemsHeaderRow(cols)` checks the first column against `action item(s)`/`task`/`item` and drops that row entirely — a pasted table's own header row (`Action Item | Owner | Due Date`) must never become a bogus first action item. Column 2 is `owner` (trimmed as-is); column 3 goes through `parseFlexibleDate()` before being stored, so a row survives with `owner` set and `dueDate: null` rather than erroring if a due-date cell is missing or unparseable (e.g. "Marcus Webb" with a blank due-date column in the source table).

**`parseFlexibleDate(str)` resolves a handful of common due-date shapes to `YYYY-MM-DD`** — already-ISO passes straight through; `"Jul 22"` / `"22 Jul"` (with or without a trailing year, `,`/ordinal suffixes tolerated); and `M/D` / `M/D/YYYY` (US month/day order, matching the month-name forms). Anything else returns `null` rather than guessing. **A year-less date is the common case** (nobody writes the year for something due next week), so `inferActionItemYear(monthIndex0, day, refDate)` picks the *nearest* real occurrence: the current year, unless that lands more than ~30 days before `refDate` (today), in which case it rolls forward to next year — a "Jan 5" written in July is almost certainly next January, not one that already passed. `isoFromDateParts()` is what actually catches an invalid combination (Feb 30, a bogus month) — `Date`'s own constructor silently rolls an out-of-range day/month forward into the following month instead of erroring, so the parts are compared back out against what was asked for and `null` returned on any mismatch, rather than silently storing a wrong date.

`parseMinutesPaste()` runs `parseMeetingMinutes()` then `linesToActionItems()` over the modal's paste textarea, filling the four plain-text fields and replacing the Action Items table wholesale — a one-shot convenience triggered by its own button, not something that runs automatically on every keystroke, and every field/row stays fully hand-editable afterward regardless of how (or whether) the auto-split worked.

**Action Items renders as a real table** (`.minutes-action-items`, a header row of labels — Action Item / Owner / Due Date — over a body of `.minutes-action-item-row`s), following the same "detached working array, edited in place, only committed on Save" pattern as the item modal's own milestone editor: `editingMinutesActionItems` (module-level, mirrors `editingMilestones`) is populated from `cycle.minutes.actionItems` when `openMinutesModal()` opens (or `[]` for a cycle with none yet), and each row's text/owner inputs write directly into it via `oninput` — no re-render on every keystroke, only `addMinutesActionItemRow()`/`removeMinutesActionItemRow(idx)` (structural changes) call `renderMinutesActionItemsRows()` again. The Due Date cell reuses `dateInputHtml()` (the same icon+input structure every other date field in the app uses, `onblur` not `onchange` for the same partial-keystroke reason documented on that helper) rather than a plain `<input type="date">` — but its `.date-pill` background/padding/radius are stripped in this table specifically (see below), so it behaves identically to every other date in Pulse without looking like a pill here.

**The Action Item, Owner, and Due Date cells are all deliberately flat, not styled as pills/chips** (`.minutes-action-item-row input[type="text"], .minutes-action-item-row textarea` — no border, no background, no radius at rest; a background highlight only appears on `:focus`) — an explicit user correction against the rounded-pill look used for dates elsewhere in the app, since these already sit inside a bordered table row and a per-cell "pill" on top of that read as visually noisy. **Action Item is a `<textarea>`, not a single-line `<input>`**, since a real action item's description is often long enough to wrap — clipping it to one line (as a plain input does) hides the rest of what someone typed, but it should still *read* as a normal single-line table cell for the common short case, only actually growing once content needs more room. Sizing is `field-sizing: content` on `.minutes-action-item-row textarea` (Chrome/Edge 123+, which this app already targets for File System Access sync) with `min-height: 26px` as the floor — not JS measuring `scrollHeight` (tried first, unreliably) — but the real bug behind every row looking multi-line-tall regardless of content turned out to be a **specificity collision**, not a sizing-mechanism problem: `.minutes-grid .field textarea { min-height: 84px }` (meant only for the big Summary/Decisions/Next Steps boxes, which sit as *direct* children of their own `.field`) was, without a child combinator, *also* matching the per-row Action Item `<textarea>`s nested several levels deeper inside `.minutes-action-items-field` (itself a `.field`) — and at two classes plus a type selector, it out-specified `.minutes-action-item-row textarea`'s own `min-height: 26px` regardless of source order. Changed to `.minutes-grid .field > textarea` (direct-child combinator) so it only ever reaches the top-level section textareas. `resize: none` on the Action Item textarea itself, since manual dragging would fight with content-based sizing. `.minutes-action-item-row`'s `align-items` stays `center` (matching every other row-style list in the app) — a genuinely multi-line Action Item cell just centers the shorter Owner input/date pill/remove button within the row's new (taller) height, rather than pinning them to the top. The Owner column is `100px` (widened from `78px` — the narrower column was clipping ordinary names like "Sofia Bergman"). The Due Date column is a **fixed `96px`** — the pill's own minimum content width (icon + gap + the 80px `dd.mm.yyyy` input) — deliberately NOT `auto`, even though `auto` sizes to that same minimum in principle: `.minutes-action-item-row` is re-used for the header row too, and each row is its own independent CSS Grid instance, so an `auto` track is measured per-row against that row's own content only. The header row's column 3 holds a plain "Due Date" text span (narrower than a data row's icon+input pill), so header and data rows computed *different* auto widths there — which shifted how much leftover space column 1 (the only flexible `1fr` track) absorbed in each row, visibly misaligning every column under the header (this is the same "any implicit/divergent-width column shifts the shared flexible track" CSS Grid gotcha documented elsewhere for the milestone header and Action Log tables). A fixed px value sidesteps it since it's identical regardless of a row's content. (An earlier version used a fixed `132px` to stop the un-stripped pill's own background/padding from clipping the year, e.g. rendering "22.07.2026" as "22.07.202"; stripping the pill chrome dropped the minimum needed width to `96px`.) `.minutes-action-item-row .date-pill` overrides `background`/`padding`/`border-radius` to none (and its `:hover` background too) so it reads as a plain icon+input pair like the rest of the row, and gets `justify-self: start` so it hugs the left edge of the column instead of stretching.

`saveMinutes()` trims each row's `text`/`owner` and drops any row that ends up with no text, no owner, *and* no due date (an untouched blank row added by mistake) before writing the array back — a row with just an owner filled in (say, claimed before the description is written) still survives, and a multi-line `text` (with its embedded `\n`s) round-trips through save/reload intact. `saveMinutes()` refuses to save at all if Summary/Decisions/Next Steps are all blank *and* the action items table is empty (nothing to attach), and `importedAt` is stamped once on the *first* save and left alone on every edit after that — it marks when minutes were first attached, not last touched. `removeMinutes()` goes through the same confirm-modal pattern as other destructive actions in this app (workstream/category delete) and, on confirm, clears `cycle.minutes` back to `null` **and** calls `removeActionLogForCycle(cycle)` — see "Action Log" below for why removing minutes entirely cascades to the log while every other edit path deliberately doesn't.

**`clearMinutesFields()` (a "Clear all fields" button next to "Auto-fill") is a distinct, lighter action from `removeMinutes()`.** It blanks the paste box, all three plain-text fields, and the Action Items table — but only the *open modal's* working form, not anything already saved: `cycle.minutes` itself is untouched until `saveMinutes()` is actually clicked afterward. No confirm modal, unlike `removeMinutes()`, since nothing durable is being destroyed — it's the same "reset what I'm mid-typing" tier of action as the item modal's Cancel button, not a delete.

**Migration**: `actionItems` used to be a single free-text field, before the table existed. `normalizeData()`'s reviewCycles pass folds a leftover string into a one-row table (`[{id, text: <the string>, owner: '', dueDate: null}]`, or `[]` if the string was blank) rather than dropping it — the same "don't silently lose data across a schema change" instinct as every other backfill in this file. It also backfills `id`/`text`/`owner`/`dueDate` on each row the same way a milestone's own fields are backfilled, and regenerates an unsafe `id` via `isSafeId()` (see "Data model" above) since action-item ids are interpolated unescaped into the row's `oninput` handlers same as everything else.

**The checklist reuses Planning's own row markup, not a Review-specific one.** `renderReview()` writes into the shared `#main` (not a Review-only element): it renders, in order: the workstream header for `filterWorkstreamId`, either a "Start review cycle" button (no active cycle) or the live checklist — `itemRowHtml(it, cycle)` per item, the *exact same* function Planning's status board uses, just with the active `cycle` passed as its second argument — plus a progress bar and Complete/Cancel buttons (active cycle), then a "History" section listing every `completedAt`/`cancelledAt` cycle for that workstream newest-first (`reviewHistoryRowHtml()`), regardless of how the active-cycle section above rendered. `itemRowHtml`/`milestoneHeaderHtml`/`milestoneRowsHtml`'s optional `reviewCycle` parameter is what this is built on: when passed, it (1) forces Plan dates to the read-only computed display even for a zero-milestone item, which Planning would otherwise render as editable inline inputs, and locks each milestone's own Due date the same way (`milestoneRowsHtml()`'s `dueHtml`) — Review is a confirmation pass, not a place to edit the plan; a milestone's Actual date stays editable regardless, since recording when something actually finished is exactly what a review is for; (2) hides the item row's Edit/Delete actions (`.item-actions` renders as an empty, still-real element rather than being omitted, for the usual column-collapse reason) — restructuring or removing an item isn't a review action, and the item's own status badge is still clickable if something genuinely needs correcting; and (3) appends one extra cell to each row, placed via an explicit `grid-column:12` rather than a 12th slot in `--item-grid-cols` itself, so Planning's own layout is completely unaffected by a column that only ever exists in Review. On the item's own row that cell is the item-level Confirm/Confirm-all button described above; on each milestone sub-row it's that milestone's individual confirm toggle. Both render as `.review-confirm-toggle` — an icon-only, borderless control (an outline circle that fills into a green `fa-circle-check` once confirmed) rather than a labeled button, specifically so the item-level control never has to fit a text label ("Confirm all") into the narrow trailing column; `.item-level` just bumps its font-size up slightly so it reads as the more prominent of the two. `.review-checklist` gives this reused markup the same card look `.ws-section` has (border/radius/background, no `overflow:hidden` — a row wider than the card must stay reachable via `.main`'s own `overflow:auto`, never silently clipped, per the "Status board" incident described above) without carrying over `.ws-section-header`'s page-wide-header baggage, which Review has no use for. `renderReview()` defensively falls back and re-renders if `filterWorkstreamId` points at a workstream that's since been deleted — nothing should actually reach `renderReview()` in that state, but a stale reference (an import, a hand-edited file) is cheap to guard against directly rather than trusting it never happens.

**Review mode has two sub-tabs — Scope Item Review and Action Log.** `reviewTab` (`'scope'` | `'actionLog'`, module-level, UI-only, not persisted — reset to `'scope'` by the harness's `resetState()`) is toggled by `setReviewTab(t)`. **The `#tabReviewScope` button's own visible label and position both flex live with the shared workstream selector** — the same "UI label differs from internal naming" split documented for Admin/Settings above still applies (`reviewTab === 'scope'`, `#tabReviewScope`, and every code comment keep calling the concept "Scope Item Review" throughout, matching the code's own internal naming), but the *rendered* text and left-to-right position are no longer fixed:
- With a specific workstream selected, this tab shows that workstream's own review checklist — the natural first thing to reach for — so it reads as the short **"Review"** and sorts (via CSS `order`, not a DOM move — `.view-tabs` is `display:flex`) *ahead* of Action Log/Decision Log/Change Log, i.e. leftmost.
- With "All workstreams" selected, it instead shows `reviewDatesOverviewHtml()`'s staleness ranking (see below) — a different, less central kind of view, not a checklist at all — so it reads as **"Review Status"** and sorts *after* Change Log, i.e. rightmost (its original position from before this became dynamic).

Both the label and the `order` inline style are set in `render()`'s own `mode === 'review'` branch (`scopeTab.innerHTML = filterWorkstreamId ? '...Review' : '...Review Status'`, `scopeTab.style.order = filterWorkstreamId ? '-1' : '1'`) — the other three tabs never set `order` at all and stay at the flex default (`0`), so this one tab's `-1`/`1` is what places it before or after all three of them; their own relative order and ids are otherwise unchanged. `reviewTab` still *defaults* to `'scope'` regardless of where its button currently sits or reads. `#reviewToolbar` is a `.planning-toolbar`/`.view-tabs` block (`#tabReviewScope`/`#tabReviewActionLog`) sitting above `#main` in the shared Planning/Review/Dashboard shell (the same `.planning-toolbar`/`.view-tabs` classes Planning's own topbar mode pill also uses); `render()` shows/hides it (`display: mode === 'review' ? '' : 'none'`) and toggles its tabs' `.active` class, immediately before calling `renderReview()`. Inside `renderReview()`, everything described above (the checklist, progress bar, Complete/Cancel buttons, History) is the `'scope'` tab's content and renders only when `reviewTab === 'scope'` *and* a workstream is selected — with no workstream selected, `'scope'` instead shows `reviewDatesOverviewHtml()` (see below); when it's `'actionLog'`, `renderReview()` instead writes just a header (the workstream's name/color dot, or "All workstreams" with no dot — see below) plus `actionLogHtml(w)`/`allWorkstreamsActionLogHtml()` and returns early — sub-tabs are mutually exclusive views, never stacked on the same page.

**Scope Item Review's own "All workstreams" view — `reviewDatesOverviewHtml()` — is a prioritized, color-coded list of every workstream's last completed review, an explicit user request ("track the review dates of the workstream... rank by oldest to newest").** Where Action Log/Decision Log's "all workstreams" rollups merge every workstream's *entries* into one flat list, Scope Item Review's has no per-item entries to merge with no workstream selected — a review cycle is still one workstream at a time — so this is a different shape: one row per workstream, not one row per scope item, and it replaces what used to be a plain "Select a workstream to review its scope" dead end.

For each workstream, `lastCompletedReview(wsId)` (already used by `isReviewOverdue()` — see below) gives the timestamp of its most recent `completedAt` review cycle, or `null` if it's never had one. Rows are colored by how long ago that was, three tiers per the user's own spec:
- **Red** — never reviewed, or the last review was more than 4 weeks (28 days) ago.
- **Amber** — 2–4 weeks (14–28 days) ago.
- **No color** — under 2 weeks ago.

A workstream with no scope items at all is excluded from coloring regardless of its review date — the same "nothing to review yet" guard `isReviewOverdue()` already uses (see below), so a brand-new empty workstream doesn't read as urgently red just for existing. It still gets a row (showing "Never reviewed"), just an uncolored one, same as a genuinely fresh review.

**Ranked oldest (or never-reviewed) first** — sorted ascending by `last ?? -Infinity`, so a `null` (never reviewed) sorts ahead of any real timestamp, and the workstream most overdue for attention always sits at the top; the most recently reviewed workstream sits at the bottom. This is a deliberate priority ordering, not alphabetical or sidebar order.

Each row is clickable (`onclick="setFilterWorkstream(w.id)"`) — picking a workstream this way lands directly on its own Scope Item Review (the "Start review cycle" button or its live checklist), the same place clicking it in the sidebar would. Rows reuse `.attention-row` (the same row Dashboard's Overdue/Upcoming feeds use) via a `.review-date-row` class that adds the click affordance and the `.stale-amber`/`.stale-red` background tint + bold date-color — deliberately no tint at all for the "under 2 weeks" tier, so coloring only ever draws the eye toward what actually needs attention rather than tinting every row.

**The Action Log is a workstream-wide, review-cycle-spanning list — not scoped to whichever cycle is currently active, and not cleared when a cycle completes or its minutes are edited.** This is the one place in Review mode that deliberately breaks from "a review cycle is the unit of everything": an action item is *authored* inside one cycle's meeting minutes, but once imported it's meant to be tracked and completed independently of that cycle's own lifecycle, the same way a real action item log outlives the meeting that produced it. It lives at `workstream.actionLog`, an array of `{id, text, owner, dueDate, completed, completedAt, cycleId, addedAt}` — `normalizeData()`'s workstreams pass backfills a missing/non-array `actionLog` to `[]` and each row's fields the same way an action item row or milestone is backfilled elsewhere in this file.

**`allWorkstreamsActionLogHtml()` merges every workstream's own `actionLog` into one list, tagged with an extra Workstream column — an explicit user request for an "all workstreams" rollup of the Action Log, mirroring the per-workstream one.** It builds `entries`, a flat array of `{w, a}` pairs (one per action item, `w` its owning workstream) across every workstream, then sorts it with the same open-first/soonest-due-first, then completed-most-recently-first ordering `actionLogHtml()`'s own `sortedActionLog()` already used — generalized to take an optional `keyFn` (`sortedActionLog(list, keyFn)`, defaulting to identity) so it can sort by `x => x.a` over the wrapped pairs without unwrapping the list first, rather than duplicating the same open/done split logic a second time for the wrapped case. Each row still renders via the same `actionLogRowHtml(w, a, showWs)` the per-workstream table uses, just with `showWs: true`: this inserts one extra `.action-log-ws` cell (a `.ws-dot` in that workstream's own color, matching the sidebar/review-header convention, plus its name, ellipsis-truncated) at column 2 and shifts Owner/Due Date/Source/Created/Closed/Delete/Confirm one slot right accordingly — `.action-log-row.with-ws`/`.action-log-header.with-ws` declare the corresponding 9-column `grid-template-columns` override (`minmax(160px,1fr) 130px 100px 90px 80px 90px 90px 40px 40px`), narrowing Action Item's own flexible minimum slightly to make room. `actionLogCountHtml()` was changed to take the raw action item list directly rather than a workstream (`w.actionLog` at one call site, `workstreams.flatMap(w => w.actionLog)` at the other) so the "`X` open of `Y`" badge in `.review-header` works identically for both the single-workstream and all-workstreams cases through the same helper. Delete/the confirm toggle in this merged view still call `deleteActionLogItem`/`toggleActionLogItem` with that row's *own* workstream id (not whichever one happens to be filtered — there may be none), so managing an item from the aggregate view behaves exactly like managing it from that workstream's own tab; the same `hasRole('reviewer')` gate applies either way, since `actionLogRowHtml()` itself doesn't distinguish the two contexts beyond `showWs`.

**`syncActionLogFromMinutes(cycle, actionItems)`, called at the end of `saveMinutes()` (after `cycle.minutes` itself is set), is the only thing that writes to `actionLog`.** For each action item just saved to the cycle's minutes, it looks for an existing `actionLog` row with the same `id` on `wsById(cycle.workstreamId)`: if found, it updates that row's `text`/`owner`/`dueDate` in place and leaves `completed`/`completedAt` untouched — re-saving minutes (e.g. fixing a typo in an action item's text) must never silently un-complete something already marked done; if not found, it appends a new row (`completed: false`, `completedAt: null`, `cycleId` recording which cycle it came from, `addedAt` for a stable insertion-order fallback). This is additive across cycles — saving a second review cycle's minutes appends its action items to the *same* `actionLog` array rather than replacing it, which is what makes the log "overarching" rather than just this cycle's own action items shown a second time. There is deliberately no reverse sync from an in-progress *edit*: deleting one action item row from the minutes modal and re-saving (the other rows unchanged) does not delete that row's already-synced `actionLog` entry — the log entry becomes orphaned from that point of view, same as any id `syncActionLogFromMinutes()` no longer sees in the saved `actionItems`. The one path that *does* remove synced entries is removing the minutes wholesale — see `removeActionLogForCycle()` below, called from `removeMinutes()` — since at that point there's no ambiguity about intent: the whole source record is gone, not just edited.

**`removeActionLogForCycle(cycle)` is `syncActionLogFromMinutes()`'s cascade-delete counterpart, called only from `removeMinutes()`.** It filters `wsById(cycle.workstreamId).actionLog` down to rows whose `cycleId !== cycle.id`, i.e. it deletes every action item that came from *this* cycle's minutes and leaves every other cycle's synced rows on the same workstream untouched — an explicit user request ("if I delete meeting minutes from a history, also delete the corresponding action items"), so an orphaned action item can no longer linger in the log with no way back to the (now-gone) minutes it was transcribed from.

**Completion is a plain toggle, independent of any review cycle's own confirm state.** `toggleActionLogItem(wsId, itemId)` flips `completed` and stamps `completedAt` (or clears it back to `null` on un-toggle) directly on the `actionLog` row — there's no cycle-confirmation gate the way `isItemConfirmedInCycle()` gates a scope item's review confirmation; an action item can be completed (or reopened) at any time regardless of whether the cycle it came from is still active, already completed, or long since replaced by a newer one.

**The "`X open of Y action items`" count lives in the shared `.review-header`, next to the workstream name — not floating above the table.** `actionLogCountHtml(w)` (called from `renderReview()`'s `actionLog` branch, appended right after the `<h2>`) returns `''` when `w.actionLog` is empty (no badge at all — nothing to count) or a `.review-progress` span otherwise (reusing the same class the Scope Item Review tab's own "`X of Y confirmed`" line uses, so both tabs' section-level status reads consistently). This works specifically because `.review-header`'s `<h2>` is `flex: 1` — anything placed *after* it in that flex row lands at the header's far right for free, no extra positioning needed, the same way a section-wide status badge would. An earlier version rendered this line directly above `.action-log-list` instead; moved after a user request that it read more like a section-level status than a disconnected label floating over the table.

**`actionLogHtml(w)` renders the table itself, separately from the count above**: an empty state ("No action items yet — they're added automatically when meeting minutes with action items are attached to a review cycle") when `w.actionLog` is empty, otherwise `.action-log-list` (same card look as `.review-checklist`), which opens with one `.item-row.action-log-row.action-log-header` labeling the columns followed by one `.item-row.action-log-row` per item via `actionLogRowHtml(w, a)`.

**`milestoneHeaderHtml()`'s Confirm column (grid-column:12, shown only when `reviewCycle` is passed) is an invisible icon placeholder, not a visible "Confirm" text label — a user-reported alignment bug.** Each row here (the header and every milestone data row) is its own independent CSS Grid instance, and column 2 is the grid's only flexible track (`minmax(140px,1.3fr)`); a multi-character text label at column 12 is wider than the bare icon `milestoneRowsHtml()`'s own `.review-confirm-toggle` cells actually render there, so it ate into a different amount of the header row's own width than the data rows below it did — visibly shifting Due/Actual/Status out of alignment (reported via screenshot: the header's own labels sat noticeably left of the data below them). Fixed the same way as the identically-shaped bug in the Action Log's own header (see below): `<span class="review-confirm-toggle" style="grid-column:12;visibility:hidden"><i class="fa-solid fa-circle-check"></i></span>` — same class, same icon, same column, just hidden, so the implicit column-12 track resolves to the same width in both the header and every row beneath it.

**Action Log has its own fully bespoke 8-column grid — Action Item / Owner / Due Date / Source / Created / Closed / Delete / Confirm — no longer derived from `--item-grid-cols` at all.** `.action-log-row`/`.action-log-header` override `grid-template-columns` outright with `minmax(220px,1fr) 100px 90px 80px 90px 90px 40px 40px`: Action Item (the row's one variable-length field) at column 1, Owner/Due Date at 2/3, Source at 4 — every action item today is transcribed from a review's meeting minutes (`syncActionLogFromMinutes()` is the only thing that ever writes a row here), so this just reads the plain word "Review" rather than the earlier, more elaborate "From review started `<date>`" string; that fuller string is kept as the cell's `title` tooltip rather than dropped outright, and the cell (and its lookup of `a.cycleId` in `reviewCycles`) still reads blank if the source cycle's since been deleted — `actionLog` rows are never pruned when their source cycle disappears, same "orphaned reference is harmless" stance the review confirmations themselves take. Created (`fmtDate(dateStrFromTs(a.addedAt))`) and Closed (`a.completedAt ? fmtDate(dateStrFromTs(a.completedAt)) : ''`) sit at columns 5/6 — immediately after Source, reading as "logged, then closed, right next to where it came from" — and a Delete button (`deleteActionLogItem`, see below) plus the complete/reopen toggle (`.review-confirm-toggle.item-level`) sit last, at columns 7/8, kept trailing since they're actions, not data, same convention as every other row-style list in this app.

**An earlier version instead reused `--item-grid-cols`' first 9 tracks for columns 1–9** (`20px minmax(140px,1.3fr) 90px 160px 190px 20px 20px 115px 100px`, padded with three always-empty filler columns at 1/6/7, plus the Action Item text spanning `grid-column:2/6` to swallow three more borrowed-but-otherwise-unused tracks), specifically so Action Item/Owner/Due Date lined up with Scope Item Review's own checklist "directly above it" — an explicit early user request. That reasoning didn't hold up in practice, though: `reviewTab` is either `'scope'` or `'actionLog'`, never both (see "Review mode has two sub-tabs" above), so the two tables are never on screen at the same time and the alignment was never actually visible. What it did cost was width: those 9 borrowed tracks alone put the row's minimum content width north of 1200px before Created/Closed/Delete/Confirm were even added, and adding those (each its own bespoke trailing column, 10–14) pushed it past 1300px — wide enough to overflow `.action-log-list`'s card on anything but a very wide window, visibly pushing Delete/Confirm outside its rounded border (a user-reported bug, screenshot-confirmed, since `overflow: hidden` had already been removed from the card below — the overflow was now visible rather than silently clipped). Asked directly whether any of those columns were actually unused, the honest answer was yes: three of the nine borrowed tracks (1/6/7) held nothing at all, and three more (3/4/5) were only ever absorbed into the Action Item span rather than displaying anything of their own — none of it was buying real alignment with anything on screen. The fix was to drop the borrowed layout entirely and size each column for what it actually shows, cutting the row's minimum width by roughly 500px. Every column here still has a *pinned* width (not `auto`) for the same reason `milestoneHeaderHtml()`'s own fix above does: this is a full `grid-template-columns` override rather than extra implicit tracks via `grid-auto-columns`, so the header row's own labels never need an invisible icon placeholder to keep its auto-sizing in step with the data rows below it — that failure mode (documented for the Minutes Action Items table's Due Date column above) only exists for `auto` tracks, and this table doesn't use any. Delete/the confirm toggle (7/8) originally shipped with no header label at all, matching Scope Item Review's own Actions column (which has never had header text, since the checklist has no header row to put one in) — but that comparison didn't actually hold: Action Log *does* have a header row, and every other column in it has a label, so the omission read as a genuine gap rather than a deliberate match. Fixed with one `Actions` label spanning both columns (`grid-column:7/9`, `text-align: center`) rather than two separate one-word labels over two 40px columns, which would have been cramped.

**`.action-log-list` has no `overflow: hidden` — a user-reported bug (Delete/the confirm toggle had become entirely invisible) traced to exactly the "Status board" incident `.review-checklist` (just above it) already has a fix for.** Adding Created/Closed widened every row by another 180px, and on a narrower window the resulting row now exceeds the card's own width — `overflow: hidden` was clipping Delete/the toggle off the right edge completely, not just requiring a scroll to reach them. Removed, matching `.review-checklist`'s existing precedent exactly: `.main`'s own `overflow: auto` is what makes a too-wide row reachable via horizontal scroll instead of silently disappearing. Removing the parent's `overflow: hidden` uncovers a second-order problem, though: `.action-log-header`'s own `--panel-2` background no longer gets clipped into the container's rounded corners either, so it now sets its own `border-radius: var(--radius) var(--radius) 0 0` — the same pattern `.ws-section-header` already uses for the identical reason.

`sortedActionLog(list)` orders the rows for display: every open (`!completed`) item first, soonest `dueDate` first with undated ones sorted last, followed by every completed item, most-recently-completed first — a completed action item sinks to the bottom rather than disappearing, since this is meant to read as a running log, not a checklist that empties out as things get done. A completed row gets the class `.review-confirmed` — the exact same green `--stat-green-bg` tint a confirmed Scope Item Review row gets, not a bespoke "done" style — reinforcing the same visual vocabulary across both tabs.

**`deleteActionLogItem(wsId, itemId)` removes a row from `actionLog` outright, through the same confirm-modal-only pattern as `removeMinutes()`** ("Delete this action item?" / "This cannot be undone.", no undo toast) rather than `deleteItem()`'s tombstone-plus-undo-toast pattern — an action log entry is a lightweight leaf record with nothing cascading from it, unlike an item with its own milestones. This is deliberately one-directional: deleting a log entry does **not** touch the source cycle's own `cycle.minutes.actionItems` — re-saving that cycle's minutes unchanged (or with only an unrelated field edited) would re-add the deleted row via `syncActionLogFromMinutes()`'s id match, the same way `syncActionLogFromMinutes()`'s own doc comment already notes there's no reverse sync from the log back to the minutes.

**`shortenOwnerName(name)` shortens an imported Owner to "`<first initial>. <rest>`"** ("Peer Rexroth" → "P. Rexroth", "Mary Jane Watson" → "M. Jane Watson") — applied only inside `linesToActionItems()`, i.e. only to an Owner column parsed out of pasted/dropped minutes text (plain lines, a tab-separated table, a markdown table, or a `.docx` table — all funnel through this one function), never to an Owner typed or edited directly in the modal's Action Items table (`saveMinutes()` stores that verbatim). A single-word name has nothing to shorten and passes through unchanged (`"Alice"` stays `"Alice"`), and a name whose first word already looks like an initial (`"P."` or bare `"P"`) is left alone rather than re-shortened into `"P.. Rexroth"` — this matters because `syncActionLogFromMinutes()` re-syncing an already-shortened Owner on a re-saved cycle must be idempotent, not compound the shortening further.

**Review mode has a third sub-tab, Decision Log — Action Log's counterpart for the Decisions section of meeting minutes, an explicit user request ("similar to action points, also provide a workstream and all workstream decision log").** `reviewTab` now also takes `'decisionLog'`, toggled the same way (`setReviewTab('decisionLog')`, `#tabReviewDecisionLog`), and `renderReview()` dispatches to it exactly like `'actionLog'` — a `.review-header` plus `decisionLogHtml(w)`/`allWorkstreamsDecisionLogHtml()`, returning early. It lives at `workstream.decisionLog`, backfilled by `normalizeData()` the same way `actionLog` is.

**A decision is not shaped like an action item, and the log follows from that.** A meeting's Decisions are saved as one plain text block (`cycle.minutes.decisions`), not a structured table — there's no per-decision owner, due date, or done/reopened state, just a line of text and when it was logged. Two consequences follow directly:
- **`linesToDecisions(text)` splits that block into individual decisions — one per non-blank line** (an explicit user choice: split into lines, not one log entry per meeting), stripping a leading bullet marker (`•`/`*`/`-`/`–`/`—` — the minutes parser leaves these in place, since `parseMeetingMinutes()` only strips `#*_>-` decoration from a *header* line, not from the body text underneath it) and trimming. Used only by `syncDecisionLogFromMinutes()` — the Decisions field itself still round-trips through `cycle.minutes.decisions` as one block; the splitting only happens on the way into the log.
- **There is no confirm/complete toggle** (another explicit user choice: a plain historical record, not a checklist) — `decisionLogRowHtml()` renders Decision / Source / Logged / Delete, nothing else, and `.decision-log-row`/`.decision-log-header` declare their own short `grid-template-columns` (`minmax(260px,1fr) 90px 90px 40px`, `minmax(220px,1fr) 130px 90px 90px 40px` with `.with-ws`) rather than reusing Action Log's 8-column one — there's no Owner/Due Date/Closed/Confirm column to size for. Both share `.action-log-list`'s card chrome and `.action-log-header`/`-text`/`-source`/`-ws`'s text styling outright (identical look), only the grid differs. `sortedDecisionLog(list, keyFn)` (the `keyFn` param mirrors `sortedActionLog()`'s, for `allWorkstreamsDecisionLogHtml()`'s wrapped `{w, d}` pairs) sorts purely by `addedAt`, most recent first — there's no due date or open/closed split to sort by first the way Action Log's own sort does.

**`syncDecisionLogFromMinutes(cycle, decisionsText)` is `syncActionLogFromMinutes()`'s counterpart, with one real difference forced by decisions having no id of their own.** An action item keeps the same `id` across edits within the minutes modal (it's an object in `editingMinutesActionItems`, not re-derived from text each time), so `syncActionLogFromMinutes()` can match "the same action item" by id. A decision is just a line inside one shared textarea — there's nothing to key on except the text itself — so this matches by **exact text**, scoped to that cycle's own existing rows only (so a decision reworded elsewhere in the same save, or one that happens to read identically in a different cycle, is never confused with this one): a line whose text still matches one of this cycle's existing rows keeps that row (same `id`/`addedAt`, so re-saving unrelated minutes edits doesn't make an unchanged decision look freshly logged); a line with no match is a new decision (fresh `id`/`addedAt`); any of this cycle's existing rows whose text no longer appears in the resaved text is dropped. `removeDecisionLogForCycle(cycle)`, called from `removeMinutes()` right alongside `removeActionLogForCycle()`, is the same cascade-delete counterpart Action Log has, for the same reason (no orphaned log entries once the source minutes are gone). `deleteDecisionLogItem(wsId, itemId)` follows `deleteActionLogItem()`'s own confirm-modal-only, one-directional pattern exactly (deleting from the log never touches `cycle.minutes.decisions`).

**Review mode has a fourth sub-tab, Change Log — a single, chronological, cross-workstream feed of every change logged during a review cycle, an explicit user request ("a cross workstream change log, orchestrating the changes from the reviews in one view").** `reviewTab` now also takes `'changeLog'` (`setReviewTab('changeLog')`, `#tabReviewChangeLog`), and `renderReview()` dispatches to it exactly like the other three — a `.review-header` plus `changeLogHtml(w)`/`allWorkstreamsChangeLogHtml()`, returning early.

**This introduces no new data of its own.** A change already lives on the review cycle it was logged against (`cycle.changeLog`, written by `logReviewChange()` — see above), and until now was only ever visible nested behind that one cycle's own History row (`reviewHistoryRowHtml()`, expand-on-click). `workstreamChangeLogEntries(wsId)` just flattens `reviewCyclesForWs(wsId).changeLog` across every cycle (active or completed — a cancelled cycle is deleted outright, see `cancelReviewCycle()`, so there's nothing to filter out) into one list, sorted by `changedAt` descending. This is deliberately *not* `orderedChangeLog()`'s own item-grouped order (used for a single cycle's own expanded history row) — that ordering only makes sense relative to one item's milestone list; a feed spanning every cycle of every workstream has no single item list to order against, so plain chronological is the only ordering that stays meaningful at this scope. `allWorkstreamsChangeLogHtml()` is `allWorkstreamsActionLogHtml()`'s counterpart: flattens `workstreamChangeLogEntries()` across every workstream into `{w, e}` pairs, re-sorts the merged list by `changedAt` (a per-workstream sort doesn't imply a correct merged-sort order), and renders through the same row renderer with `showWs: true`.

**The rendering itself was extracted, not reimplemented — `changeLogValueHtml(e)`/`changeLogEntryLabel(e)` are the exact tag-icon-pair/status-badge-pair/date-input-pair/plain-text logic `reviewHistoryRowHtml()` always had, pulled into shared functions so both views render a change identically.** `reviewHistoryRowHtml()` was refactored to call them instead of inlining the same `if (e.tagChange) … else if (e.statusChange) … else if (e.dateChange) …` chain a second time — one definition of what a change "looks like", regardless of which of the two views (one cycle's own expanded history, or the cross-workstream feed) is showing it.

**`changeLogRowHtml(w, e, showWs)` reuses `.review-history-row`'s own flex layout rather than a fixed-column grid** — unlike Action Log/Decision Log's plain-text cells, a change's own value is inherently variable-width (an icon pair, a badge pair, a pair of date inputs, or a plain string), which doesn't sit well in a fixed grid column the way a text cell does; flexbox with the label at `flex:1` (pushing the value and timestamp to the right, the same spacer trick `reviewHistoryRowHtml()`'s own top-level row already uses) sidesteps that entirely. `showWs` prepends a workstream dot+name using the exact same `.action-log-ws` markup/class Action Log's own `showWs` branch uses, just as an inline-styled flex row rather than a grid cell (`style="width:130px;flex:0 0 auto"`) — same look, different layout mechanism underneath. `changeLogCountHtml(list)` mirrors `actionLogCountHtml()`/`decisionLogCountHtml()`'s own `.review-progress` count badge ("N changes"), shown in `.review-header` next to the workstream name (or "All workstreams").

## Dashboard mode

`renderDashboard()` is read-only — nothing on it mutates state, it only computes and displays — and, like Review, is scoped by the shared `filterWorkstreamId`: `visibleWorkstreams()` (the same helper Planning's status board already used) narrows everything on the page to just the selected workstream, or the whole programme if "All workstreams" is selected. `allMilestonesFlat(itemList)` takes an optional pre-filtered item list for this reason (defaults to the global `items` if omitted) rather than always flattening every milestone in the programme. Three cards up top: **Item Status** (item count *within the current scope* + a `.dash-bar` stacked bar of RAG counts, colored via the same `--stat-*` variables as everywhere else, plus a text legend), **Milestone Completion** (`% complete` across the scoped items' milestones), and **Overdue for Review** (count + names of *scoped* workstreams where `isReviewOverdue()` is true — the same helper the shared sidebar's badge uses, shared rather than duplicated; scoping to one workstream makes this card either 0 or 1). Below that: a per-workstream summary table (item count + milestone completion % — only rows for workstreams in scope), then two side-by-side attention-needed feeds — **Overdue** (scoped items/milestones with `status !== 'complete'` and `dueDate` before today) and **Upcoming** (same, but `dueDate` within the next 7 days) — each entry sorted by date and, for a milestone, labeled `"<item name> — <milestone name>"` so it's clear which item it belongs to without a nested list.

There's no persisted dashboard state and no separate "refresh" action — every value is recomputed from `items`/`workstreams`/`reviewCycles` (filtered through `visibleWorkstreams()`) at render time, so it's automatically current whenever `render()` calls it (i.e. every time `setMode('dashboard')` runs, `setFilterWorkstream()` changes the scope, or any other mutation happens while already in Dashboard mode).

A Journey (see "Journeys" above) never shows up in any of this, with no special-casing needed: `scopedItems` is filtered to `wsIds.has(it.workstreamId)`, and a Journey's `workstreamId` is always `null` — the same reason Review mode's own per-workstream item list never picks one up either.

## Color scheme system

Ported wholesale from this author's mytasks app (see its own CLAUDE.md's "Color scheme system") — same two-axis design, same five schemes, same picker mechanics, adapted to Pulse's own CSS variable names and category-color model rather than mytasks'.

Two independent axes control appearance: `data-theme` (`light`/`dark`, the original sun/moon button, `toggleTheme()`, unchanged since before schemes existed) and `data-scheme` (picked from the palette-icon button's modal, `setColorScheme()`). Each scheme defines its own light *and* dark CSS variable block, so the two axes combine freely — e.g. `[data-scheme="dracula"][data-theme="dark"]`.

- **`THEME_SCHEMES`** (top of the `<script>` block) is the single source of truth for which schemes exist — each entry has `id`, `name`, `desc`, and `swatches` (three hex values shown as dots in the picker). `id` must exactly match a `[data-scheme="..."]` selector; nothing enforces this automatically except `tests/cases/theme.test.js`'s "every THEME_SCHEMES entry has a distinct, expected id" test, which will fail loudly on a typo but won't catch a selector that exists with no matching `THEME_SCHEMES` entry (a harmless orphan, not a crash).
- **`:root`** and the bare **`html[data-theme="dark"]`** block are the original, untouched palette — this is what renders when `data-scheme` is absent entirely (or explicitly `"standard"`, since `:root` already covers that case with no separate `html[data-scheme="standard"]` block needed), so a load with no scheme saved yet looks exactly as this app always has.
- Every other scheme is `html[data-scheme="x"] { ... }` (light) and `html[data-scheme="x"][data-theme="dark"] { ... }` (dark) — the dark block's extra attribute selector always wins on specificity over the bare `html[data-theme="dark"]`, so block order in the file doesn't matter for correctness. A scheme only redeclares the tokens that actually vary by hue (`--bg`/`--panel`/`--panel-2`/`--border`/`--text`/`--text-dim`/`--text-faint`/`--accent`/`--accent-bg`/`--danger`, every `--ws-*`/`--ws-*-bg` pair, every `--stat-*`/`--stat-*-bg` pair) — structural tokens (`--radius`, `--shadow`, `--item-grid-cols`) are deliberately left undeclared per scheme and keep cascading from the blocks above, since they aren't part of "color scheme".
- **Token mapping from mytasks' 6-slot system to Pulse's own**: mytasks only needed `blue`/`teal`/`amber`/`red`/`green`/`purple` (its category-chip + semantic colors); Pulse's `WS_COLORS` needs 8 (adds `pink`/`grey`) and its `STATUSES` needs a `not-started`/`complete` pair on top of green/amber/red. `--accent`/`--stat-complete` both reuse the scheme's "blue" hue (mirroring Standard's own existing convention, where `--accent` and `--stat-complete` are already two near-identical blues), `--ws-grey`/`--stat-not-started` derive from the scheme's own secondary/tertiary text tiers (`text-dim`/`text-faint`) rather than a separate invented neutral, and `--ws-pink` is either a real extra token where the source product actually has one (GitHub's own Primer data-visualization pink, fetched from primer.style — see below) or an honestly-labeled derivation (an even RGB blend of that scheme's own red+purple) where it doesn't.
- **Accuracy convention** (same as mytasks): when a scheme claims to replicate a real product's theme, its core anchor colors are the same values mytasks already verified via fetch (VS Code Light/Dark Modern, Dracula/Alucard's official spec, GitHub Primer's semantic palette, GitHub Dark Dimmed's real compiled values) — not reconstructed from memory a second time. The one value fetched fresh for this port specifically was GitHub Primer's real data-visualization pink token (`--data-pink-color-emphasis: #ce2c85`, `--data-pink-color-muted: #ffe5f1`, from primer.style/primitives/colors/) for `--ws-pink`, since mytasks never needed a separate pink slot; that token's dark-mode pair isn't published on the same page, so GitHub/GitHub Dimmed's dark `--ws-pink` is an extrapolation following the same light→dark lightening Primer's other real tokens show (e.g. red `#cf222e` → `#f85149`), flagged in the CSS comment as an extrapolation rather than a second verified value.
- Each scheme may add its own one-off "signature" rule, kept in its own block separate from the variable definitions (same convention as mytasks): Modern/Dracula/GitHub/GitHub Dimmed all set numerics (`.milestone-count-badge`, `.rag-pill`, `.review-progress`) to a monospace stack; Dracula adds a soft accent-colored glow to the brand icon; GitHub and GitHub Dimmed turn `.btn-primary` into GitHub's solid green.
- Persistence mirrors how `theme` already works: `colorScheme` (state, defaults `'standard'`) folded into `load()`/`save()`/`doFileSyncWrite()`'s payloads, same as `theme` — but, like `mode`/`theme`, it's deliberately **not** read back out of an *incoming* synced file during a live merge (see `mergeData()`'s caller in the file-sync poll) — these are per-device display preferences, round-tripped for a fresh device opening the file, not something one device's edit should silently flip on another device's already-open session.

To add a scheme: add its light+dark CSS variable blocks, add any signature rules, add a `THEME_SCHEMES` entry, and add its `id` to the sorted list in `tests/cases/theme.test.js`'s last test. To remove one: reverse all of the above and grep the whole file for its id/name to catch stray comments.

**A real bug this port introduced and fixed**: the "Color scheme system" comment block above originally described `THEME_SCHEMES` as living "in the `<script>` block" — a literal `<script>` substring sitting inside a CSS comment. `tests/harness.js` (and any other tool) that extracts the inline script via a naive `indexOf('<script>')`/`indexOf('</script>')` scan latches onto the *first* occurrence of that literal text anywhere in the file, including inside a comment — so this accidentally moved the extraction's start point up into the middle of the `<style>` block, turning a few thousand characters of CSS into "JavaScript" and breaking the entire test suite with an opaque parse error. Fixed by rewording the comment to avoid the literal substring ("the inline script block below"). **Never write the literal text `<script>` or `</script>` anywhere in this file outside the real tags themselves** — not in a CSS comment, not in a JS comment, not in a string — since `tests/harness.js`'s extraction (and this exact failure mode) has no other safeguard against it.

## Conventions from this project's history

- Font Awesome 6.5 (`fa-solid`) via CDN, matching PromptLab/mytasks.
- `button:focus:not(:focus-visible) { outline: none; }` is global — focus rings only show for real keyboard navigation, not post-click.
- IDs are generated by `genId()` (timestamp + random suffix); `isSafeId()` plus `normalizeData()`'s regeneration passes are the guard against a crafted id from an external `.json` file (import, linked file) breaking out of an `onclick` attribute — see "Data integrity" above.
